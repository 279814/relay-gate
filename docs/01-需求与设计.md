# relay-gate 需求与开发规范 v1.0.0

- 文档版本：v1.0.0
- 文档状态：设计已确认，尚未进入代码实现
- 更新日期：2026-08-05
- 部署形态：单副本，Go，SQLite，内存运行状态，Docker Compose
- 目标客户端：Claude Code、CC Switch 及兼容 Anthropic/OpenAI 原生协议的客户端
- 适用仓库：relay-gate

本文件是 v1.0.0 的唯一需求与开发基线，整体替代旧版需求文档中混杂的 M0–M7 实施日志、旧探测矩阵和已经被实测推翻的结论。历史内容仍可通过 Git 查看，不再作为实现依据。

> 安全说明：真实上游 API Key、Relay Key、管理员密码、Master Key、私有上游地址以及未经脱敏的请求样本不得写入本仓库。在线验收使用被 Git 忽略的本地配置文件。

## 1. 背景、目标与优先级

### 1.1 背景

用户维护多个 New API、One API、sub2api 及其他兼容中转站。公益站可能临时不可用、限流、模型下线、协议兼容不完整，或者只接受接近原生 Claude Code 的请求特征。

CC Switch 的按请求顺序重试只能在真实请求撞上故障后切换，可能让 Claude Code、subagents 和静态工作流在已经消耗大量 Token 后中断。relay-gate 的目标是在服务器持续维护上游状态，让真实请求尽量直接进入当前可用且优先级最高的 Route，同时在必要时提供受控重试、快速恢复和完整诊断证据。

### 1.2 核心目标

1. 支持以下协议和同名上游端点，不做协议互转：

   - POST /v1/messages
   - POST /v1/responses
   - POST /v1/chat/completions
   - POST /v1/messages/count_tokens
   - GET /v1/models

2. 一个 ModelName 可以绑定多个 Route；Route 包含上游、模型映射、优先级、权重、并发限制及独立健康状态。
3. 支持主动探活和严格零合成请求的懒探活。
4. 默认严格透传；仅修改上游认证、可选模型映射、目标地址以及协议栈必须管理的字段。
5. 在客户端尚未收到任何响应字节时，按明确的风险策略执行跨 Route 重试。
6. 提供本地与 Linux 公网 IP 两种一行部署方式。
7. 首次部署自动生成管理员密码、Relay API Key 和 32 字节 Master Key。
8. 提供能力矩阵、样本、请求日志、安全诊断、邮件告警及显式启用的声明式流量转换。

### 1.3 P0 硬门禁

问题 0“探活兼容性”是整个项目的 P0 基础。第一阶段只允许实现探活及其不可缺少的出站连接、端点解析、能力状态和测试基础设施。

在 P0 验收通过前，不得把凭据轮换、内容安全、流量转换等后续功能混入同一个实现 PR。公益站本身可能临时故障，因此 P0 不要求在线站点永远全绿；它要求网关能正确兼容、正确归因，并能区分：

- 网关解析或模板错误；
- 上游配置错误；
- 上游限流或容量不足；
- 上游临时故障；
- 上游确实不支持某端点；
- 网络不可达。

### 1.4 非目标

v1.0.0 明确不做：

- Anthropic 与 OpenAI 之间的协议转换；
- 多副本一致性、分布式数据库或集群调度；
- 计费、额度售卖、用户体系或多租户 RBAC；
- 自动修改本机 Claude Code 或 CC Switch 的持久配置；
- 在真实响应已提交给客户端后自动重放整个模型请求；
- 使用外部大模型判断注入风险；
- 自动阻断或篡改被判断为可疑的真实响应；
- 执行 JavaScript、Lua、Shell 等任意用户脚本；
- 承诺兼容所有未知中转站实现；未知变体通过可审计的自定义配方扩展。

未在本规范列出的既有功能和行为不做无关重构。

## 2. 术语与不可破坏的约束

### 2.1 核心术语

| 术语 | 含义 |
|---|---|
| Upstream | 一个物理中转站，保存根地址、上游凭据、代理设置、探活模式及端点配置 |
| Endpoint | messages、responses、chat_completions、count_tokens、models 中的一个具体端点 |
| ModelName | 客户端请求中的逻辑模型名，包含协议及匹配方式 |
| Route | ModelName 与 Upstream 的绑定，是模型健康、优先级、映射和并发限制的最小单位 |
| Reachability | Upstream 的 DNS、TCP、TLS、HTTP 连接是否可达 |
| Capability | 指定 Upstream 或 Route 是否支持某个 Endpoint 及当前配置 |
| RouteHealth | Route 的模型语义健康状态 |
| Probe Recipe | 探活请求的端点、方法、查询、请求头、请求体、Secret 与判活规则 |
| Active | 允许发送受控合成探活请求 |
| Lazy | 不发送任何合成探活请求，只使用真实流量判断 |
| Attempt | 一次客户端请求向一个 Route 发出的单次上游请求 |
| Semantic Evidence | 非空文本、思考、工具参数、拒绝内容或正数输出用量等能证明模型实际工作的证据 |
| RecoveryGate | 与 max_concurrency 独立的每 Route single-flight 半开恢复闸 |

### 2.2 三个互相独立的状态维度

系统不得再把“站能连接”“端点存在”“某模型能生成”合成一个布尔值。

1. Upstream Reachability：

   - unknown
   - reachable
   - unreachable

2. Endpoint Capability：

   - unknown
   - supported
   - unsupported
   - transient_error
   - config_error

3. Route Health：

   - unknown
   - alive
   - recovering
   - dead

Reachability 只描述网络连接。Capability 描述指定 URL、鉴权、模型和配方是否能使用。Route Health 描述模型实际生成能力。三个维度分别存储、展示和迁移。

### 2.3 严格透传的精确定义

HTTPS 在 relay-gate 终止后，Go 的 HTTP 协议栈会重新生成请求；因此不能承诺 TLS 密文、HTTP/2 帧、头顺序或头名大小写完全一致。v1.0.0 的严格透传定义如下：

| 范围 | 未启用流量转换时的保证 |
|---|---|
| 请求体 | 除唯一顶层 model 的可选字节级替换外，其他字节保持一致 |
| 请求头 | 端到端头的名称和值保持一致；入站认证字段被移除并按上游认证配置写入 |
| 请求目标 | 使用解析后的上游 URL；Host、Content-Length 和连接管理字段由协议栈生成 |
| 响应状态码 | 与最终上游响应一致 |
| 响应体 | 按收到的字节顺序直接转发，不做 JSON 重编码、解压或重压 |
| 响应头 | 端到端头名称和值保持一致；逐跳头及传输层字段按 HTTP 规范处理 |
| 流式时序 | 收到并提交后立即 Flush；仅允许重试预读窗口造成有界延迟 |

成功的上游响应不得新增 X-Relay-Attempts、X-Relay-Half-Open 等网关诊断头。重试和半开信息进入请求日志及管理界面。只有 relay-gate 自己生成的错误响应或本地 count_tokens 估算响应可以带 X-Relay 诊断头。

### 2.4 安全硬约束

- 上游 API Key、Relay Key、Probe Secret、SMTP 密码及转换 Secret 使用 Master Key 加密。
- 管理员密码只保存 Argon2id 哈希，不可恢复明文。
- Master Key 不存入 SQLite 自身，持久化在仅服务 UID 可读写的版本化 Keyring 文件；长期容器进程不得以 root 运行。
- 未经脱敏的凭据不得进入日志、样本、错误文本、邮件或 API 响应。
- 管理页面展示的所有上游文本必须按纯文本渲染，禁止 innerHTML。
- 后台记录、扫描、邮件或统计失败不得阻塞真实转发。
- 客户端取消、用户暂停或进程关闭不得计为上游健康失败。

## 3. 已验证事实与旧设计修正

### 3.1 原生 Claude Code 请求证据

在不修改本机 Claude Code 和 CC Switch 持久配置的前提下，使用隔离的本地 HTTP 接收器捕获了 Claude Code 2.1.220 的最小原生请求。该证据只用于设计内置模板和回放 fixture。

已观察到：

- 请求路径为 /v1/messages?beta=true，而不是单纯 /v1/messages；
- Accept 为 application/json，不是固定 text/event-stream；
- User-Agent、Stainless 包版本、运行时版本和会话 ID 会随客户端版本或会话变化；
- body 可能包含 model、messages、system、tools、metadata、max_tokens、thinking、context_management、output_config 和 stream；
- 工具关闭时 body 仍明显不同于当前项目的最小 1+1 JSON；
- beta 头可能随工具和客户端版本变化。

因此，内置探活不能把一次抓包中的版本号、会话 ID 或 beta 列表永久写死；必须结合内置模板、安全学习和手动固定配方。

### 3.2 当前误判的根因

已复现或确认：

- agentRouter 返回有效 ping，但载荷含 error:null；旧解析器只要看见 error 字样就误判流式错误。
- anyrouter 需要 context-1m-2025-08-07 等请求特征；缺少时返回明确配置错误，补齐后可能进入容量或限流错误。
- SeekAI 会先返回 message_start 和 ping，随后才有非空 text_delta；旧解析器可能把 message_start 中的 output_tokens:0 当成成功并提前断流。
- GET /v1/models 在多个站点均可返回 200，但这不能证明具体模型可以生成。
- 旧 L2 丢失真实请求中的 RawQuery，固定头和固定 body 也不等于原生 Claude Code。

文档中将原问题里的 “Decode” 统一视为 DoCod 的笔误。在线验收目标使用本地私有矩阵中的站点名称，不在仓库保存它们的 Key。

### 3.3 必须废弃的旧结论

- 旧文档声称能力矩阵已经完成，该结论不成立。
- /models 的 401、404、405 或业务 5xx 不能使整个 Upstream 下的 Route 连坐死亡。
- 固定最小 JSON 不能被称为原生 Claude Code 请求。
- 任意 output_tokens 字段不能作为成功证据。
- 固定 120 秒的原生长思考首语义 Token 超时不符合至少 5 分钟的要求。
- full_url_mode 同时声称支持 query、又在校验中拒绝 query 的行为必须迁移。
- 域名、ACME 邮箱和登录 IP 白名单不再是公网部署前提。

## 4. 总体架构

### 4.1 逻辑分层

1. 接入层

   - 模型端点；
   - 管理 API；
   - 会话、CSRF、登录限速和敏感操作重新认证。

2. 代理层

   - 原始请求读取；
   - 唯一 model 校验；
   - 路由、并发和恢复闸；
   - 重试；
   - 流式提交；
   - 样本和旁路观察。

3. 出站基础层

   - EndpointResolver；
   - AuthResolver；
   - TransportManager；
   - 分阶段超时。

4. 探活层

   - ClientFingerprintLearner；
   - ProbeRecipeResolver；
   - ProbeTemplateRenderer；
   - ProbeExecutor；
   - ResponseClassifier；
   - CapabilityRegistry；
   - Scheduler。

5. 健康层

   - Reachability；
   - Capability；
   - RouteHealth；
   - RecoveryGate；
   - 配置语义版本。

6. 后台层

   - 样本与请求日志；
   - 安全扫描；
   - 主动 canary；
   - SMTP；
   - 数据保留与成本统计。

7. 持久层

   - SQLite；
   - data/secrets/keyring.json；
   - 事务化 Schema Migration；
   - Keyring 与 SQLite 跨文件轮换恢复协议。

### 4.2 依赖方向

- proxy 与 probe 同时依赖 outbound，不再由 probe 导入 proxy。
- proxy 通过接口上报健康观察，不依赖具体探活实现。
- transform 是纯规则编译与字节/事件转换包，不读取数据库、不发送网络请求。
- security 只消费只读观察 DTO，不参与响应主链。
- store 负责持久化，不承载选路、探活或转换业务规则。
- api 只通过服务接口调用 credential、probe、security 和 transform。

### 4.3 不可变快照和语义版本

一次真实请求开始时固定：

- Upstream、Endpoint、ModelName、Route；
- 认证配置版本；
- Endpoint URL 版本；
- Retry Policy；
- Transform 发布版本；
- Settings 快照；
- Route 语义令牌。

一次探活固定：

- Upstream、Route、模型映射；
- 解析后的 URL 哈希；
- Auth Profile 版本；
- Probe Recipe 版本；
- Settings 快照；
- Route 语义令牌。

配置在请求中途发布或回滚，不影响在途请求。所有异步结果携带语义令牌；结果回写时令牌不匹配则丢弃，避免旧探活或旧真实请求污染新 Route。

### 4.4 运行状态

运行状态分为：

- running：接受新流量并按配置执行任务；
- paused：拒绝新模型请求、count_tokens、half-open 和合成探活；
- maintenance：仅用于 Master Key 轮换等一致性操作。

paused 是用户意图并持久化。maintenance 是内部操作状态，不覆盖 paused。

暂停时：

- 新模型请求和 count_tokens 返回 503 与 Retry-After；
- 取消在途合成 L1/L2、主动 canary 和其他耗 Token 作业；
- 不强杀已开始的真实响应，避免已花费 Token 被浪费；
- 管理 API、证书续期、必要 SQLite 落盘和恢复逻辑继续运行。

paused 的 Retry-After 默认 60 秒。无可用 Route 时使用当前最短 cooldown 剩余秒数；无法计算时同样使用 60 秒。

恢复时保留暂停前的 dead、recovering、cooldown 和有效负状态；alive 降为 unknown 并按全局限流和抖动逐步复核。不得把已知 dead 直接清成可并发选路的普通 unknown，也不得瞬时齐发。

## 5. 数据模型与持久化

### 5.1 既有核心实体

#### Upstream

核心字段：

- id、name、base_url、proxy_url、enabled；
- api_key_secret；
- probe_mode：active 或 lazy；
- revision；
- created_at、updated_at。

base_url 表示根地址或公共路径前缀，不允许 query 或 fragment。具体端点的完整 URL 进入 UpstreamEndpoint。

#### UpstreamEndpoint

每个 Upstream 可为以下端点保存独立覆盖：

- messages；
- responses；
- chat_completions；
- count_tokens；
- models。

字段包含：

- upstream_id；
- endpoint；
- url_override；
- auth_profile；
- fixed_query_template；
- default_probe_recipe_id；
- revision；
- needs_review。

未配置 url_override 时使用 base_url 加规范端点路径。url_override 可以带固定 query，但 Secret 必须通过加密引用进入。

#### ModelName

保留：

- name；
- protocol；
- match_mode；
- is_fallback；
- enabled；
- revision。

旧 probe_prompt 和 probe_max_tokens 迁入 Probe Recipe，不再作为 ModelName 的长期探活模型。

#### Route

保留并扩展：

- model_name_id；
- upstream_id；
- priority；
- weight；
- upstream_model；
- max_concurrency；
- enabled；
- revision。

Route 是模型健康和半开恢复的最小单位。

#### UpstreamReachability

保存：

- upstream_id；
- state；
- consecutive_ok、consecutive_fail；
- last_ok_at、last_error_at、last_error；
- last_connect_ms、last_tls_ms、last_header_ms；
- observed_revision。

#### EndpointCapability

保存：

- scope_type：upstream 或 route；
- scope_id；
- endpoint；
- state；
- resolved_url_hash；
- model_revision；
- auth_profile_revision；
- recipe_revision；
- request_transform_binding_revision；
- observed_at；
- expires_at；
- status_code；
- error_class；
- redacted_detail。

#### RouteHealth

保存：

- route_id；
- state；
- recovery_required；
- consecutive_ok、consecutive_fail；
- cooldown_until；
- last_real_ok_at；
- last_probe_ok_at；
- last_error；
- last_ttft_ms；
- observed_revision。

内存状态为实时真相，SQLite 保存管理界面和重启恢复所需快照。重启后，匹配当前 Observation Token 的 dead、recovering、cooldown 和 config_error 负状态继续生效；旧 alive 降为 unknown。这样既不把陈旧正结论当作已验证，也不让重启绕过 RecoveryGate 冲击已知故障站。

### 5.3 探活实体

新增：

- probe_recipe；
- probe_recipe_version；
- probe_secret；
- client_probe_profile；
- probe_execution；
- endpoint_capability。

Probe Recipe 版本一经发布不可修改；修改生成新草稿版本。Route 只指向已发布版本。

### 5.4 样本和请求日志

一个客户端请求形成一个 Sample Group：

- sample_request：入站方法、路径、RawQuery、脱敏头、原始业务 body 和接收时间；
- sample_attempt：每次 Attempt 的 Route、上游、出站 URL、脱敏头、出站 body、响应状态、响应头、响应 body 和四阶段时间戳；
- request_log：每次 Attempt 的轻量元数据、重试原因、写入证据和健康结论。

这样既不会为每次重试重复保存完整入站 body，又能保留所有实际发送给公益站的请求和所有上游响应。

凭据无条件脱敏。业务 body 默认完整保存，仍受用户配置的磁盘保留数、保留天数和可选体积上限控制。记录属于诊断旁路；磁盘满或队列耗尽不得中断真实响应，但必须显示丢弃计数和高优先级告警。

样本正文属于敏感数据，不能只依赖文件权限。首次初始化生成独立 Sample Data Key，使用 Master Key 包装；sample_request、sample_attempt 和未脱敏 security evidence 的敏感 BLOB 使用 Data Key 信封加密。Master Key 轮换只重新包装 Data Key，不重加密全部大样本。

默认保留策略：

- 7 天；
- 300 个 Sample Group；
- 总磁盘配额 5 GiB；
- 最多置顶 50 个 Group；
- 请求仍受 32 MiB 入站上限；
- body 字段默认不截断；
- 达到总配额时优先删除最旧未置顶 Group；
- 单个响应本身超过剩余总配额时保存可配置的头尾、标记 truncated，并产生高优先级告警。

URL、RawQuery、请求头、响应头、body 和错误文本都要扫描已知 Secret。查看、导出、置顶和批量删除未脱敏样本需要重新认证并写审计记录。

### 5.5 凭据和审计实体

新增：

- admin_credential；
- relay_key；
- audit_event；
- smtp_config。

Relay Key 支持 active、grace、revoked 状态。审计事件记录敏感查看、轮换、回滚、配方发布、强制启用、Route 手动停用和未脱敏证据查看。

### 5.6 安全与转换实体

新增：

- security_finding；
- security_rule_override；
- security_diagnostic_run；
- transform_profile；
- transform_version；
- transform_binding；
- transform_execution。

安全发现与 Route Health 分离；风险发现不能自动改变选路状态。

### 5.7 数据库迁移

Schema Migration 使用单调递增版本并在 SQLite 事务中执行。首次打开旧库时：

1. 停止业务写入并使用 SQLite Backup API 创建一致性数据库快照；
2. 复制当前 Keyring 和 keyring.previous；
3. 生成包含 Schema 版本、Key ID、rotation_id、文件大小和 SHA-256 的配对 manifest；
4. 检查旧表和旧列；
5. 建立 schema_version；
6. 迁移结构；
7. 执行所有旧 Secret 的全量解密预检；
8. 迁移 Endpoint、Probe、Capability 和 Credential 数据；
9. 将旧 sample 每行迁成一个 sample_request 和一个代表旧最终尝试的 sample_attempt，保留 legacy_sample_id、req_id、pinned、时间戳和 truncation；历史中未保存的重试 body 不得伪造；
10. 校验行数、外键、manifest 和所有新密文的全量解密；
11. 提交版本；
12. 保留可用于回滚的配对备份。

数据库迁移失败时拒绝以新版本继续运行，不允许带着半迁移结构提供服务。

## 6. 真实请求处理

### 6.1 入站鉴权

客户端可以使用：

- x-api-key；
- Authorization: Bearer；
- Api-Key。

网关从允许位置提取 Relay Key，使用不可逆摘要与内存快照比较。未配置 Relay Key 时一律拒绝，不能退化为匿名访问。

出站前删除所有入站认证别名，只按 Endpoint Auth Profile 写入目标站需要的认证。其他端到端头保持不变。

公网 Nginx 为登录限速和 Secure Cookie 传入的客户端 IP、原始协议等元数据必须使用受保护的内部头。relay-gate 只信任来自内部 Edge 网络的这些头，并在构造上游请求前删除；不得把 Nginx 新增的 X-Forwarded-For、X-Real-IP 或其他内部元数据泄露给上游。

### 6.2 公共前置流程

所有 POST 模型端点及 count_tokens 执行：

1. Relay Key 校验；
2. paused 检查；
3. 读取 Settings 快照；
4. 按 MaxRequestBody 读取原始 body；
5. 扫描完整顶层 JSON 对象；
6. 校验恰好一个字符串 model；
7. 读取不可变配置快照；
8. 匹配 ModelName 和协议。

缺失 model、重复顶层 model、非字符串 model、非法 JSON 或超过上限均返回协议对应的 400。此类请求不发送上游、不触发重试、不影响健康状态。

### 6.3 唯一 model 的字节级改写

定位器必须扫描完整顶层对象，不能在找到第一个 model 后立即返回。

- 不映射时直接复用原始 body slice，不复制、不重编码。
- 映射时只替换唯一 model 值对应的原始字节区间。
- 新值使用合法 JSON 字符串编码且不做 HTML 转义。
- 其他键顺序、数字格式、空白、Unicode 转义和重复非 model 键全部保持。
- 每次重试都从原始入站 body 重新开始，禁止在上一站改写结果上再次改写。

### 6.4 Route 选择

正常候选必须满足：

- ModelName 匹配且协议一致；
- Route 与 Upstream 均启用；
- Upstream Reachability 不是 unreachable；处于恢复窗口时必须获得 RecoveryGate 许可；
- Endpoint Capability 不是 unsupported 或 config_error；
- Route Health 不是 dead，或者当前请求获得 RecoveryGate 许可；
- 不在 429 cooldown；
- 未在本次请求尝试过；
- 能原子获取 max_concurrency 配额。

选择顺序：

1. priority 数字越小越优先；
2. 同优先级按 weight 加权；
3. RecoveryGate eligible 的高优先级 Route 可获得一次恢复机会；
4. 其余并发请求选择健康替代 Route。

### 6.5 每次 Attempt 的构造顺序

1. 从原始入站头和 body 克隆；
2. EndpointResolver 解析目标 URL；
3. 移除入站认证并写入上游认证；
4. 执行 Route 模型映射；
5. 执行已发布的可选请求转换；
6. 保护层重新写入上游认证，并只替换已经存在的唯一 Route 模型值；
7. 再次校验恰好一个字符串 model；
8. 重新计算 Content-Length；
9. 使用对应 Transport 和剩余总预算发送。

本地错误分两类：

- request-global：非法客户端 body、协议不匹配或全局设置错误，立即终止整个请求；
- route-local：该 Route 的 URL、Auth Secret、模型映射或 Transform 配置错误，标记对应 Capability 为 config_error，并继续选择下一个 Route。

route-local 失败没有发送上游，不消耗 retry_max_attempts 的网络 Attempt 次数，但必须加入 tried 集合，记录一次 local_candidate_failure，并设置最大跳过数为本次快照中的候选 Route 数，避免循环。两类错误都不改变上游健康。

保护层不得凭空补一个缺失的 model。完整 body 模板若删除 model、改变其类型或制造重复 model，必须 fail_closed。

### 6.6 响应提交

发送与提交分离：

- Send：请求已经发送，最多读取有界前缀，但尚未向客户端写任何响应；
- Commit：复制最终上游状态、端到端头和响应字节；
- Discard：放弃本次 Attempt，排水有界错误体并关闭连接。

一旦 Commit 向客户端写出第一个响应字节：

- 不得切换 Route；
- 不得重放请求；
- 不得把本地错误 JSON 插入已有 SSE；
- 后续断流只记录和关闭连接。

### 6.7 压缩与流式

严格模式下 Transport 禁止 Go 自动注入 gzip 和自动解压。客户端的 Accept-Encoding 原样发送，上游响应原样返回。

模型请求 body 的 Content-Encoding 规则：

- identity 或未设置：按正常字节定位和替换；
- gzip 或 br：在解压大小限制内创建只读解码副本，用于唯一 model 校验和选路；
- 压缩请求不需要模型映射且未启用请求 body 转换时，原压缩字节和原 Content-Encoding 直接转发；
- 压缩请求需要模型映射时，严格模式返回 415，因为解压、改写、重压无法保持原始压缩字节；
- 用户显式启用解压/重编码转换时允许处理，但该 Route 退出严格模式；
- 未支持的 Content-Encoding 返回 415；
- 编码体和解码体都受独立大小上限，防止解压炸弹。

启用需要读取响应 body 的转换规则时，该 Route 明确退出严格模式，并可由保护层将 Accept-Encoding 设置为 identity。仅修改响应头的规则不改变压缩协商。

真实压缩响应始终把原始字节转发给客户端。健康和安全观察器可以对旁路副本进行有界 gzip/br 解压；解压失败、超限或编码不支持时标记 observer_incomplete，并退化为状态码和传输错误级判断，不得修改主响应。

所有流式提交每次写入后立即 Flush。健康观察、安全扫描、样本复制和统计发生在旁路 tee 中，不得改变写入内容或 Flush 顺序。

### 6.8 真实流量健康观察

每个 Attempt 独立产生一次健康观察，包括被重试丢弃的 Attempt 和最终提交的 Attempt。真实流量观察器复用与 Probe 相同的协议事件解析器，但采用不同的完成规则：

- 2xx、存在 Semantic Evidence 且出现协议正常结束：成功；
- 非流式 2xx、完整 JSON 且存在 Semantic Evidence：成功；
- 提交前出现结构化错误：按错误码分类，并可进入重试决策；
- 已有语义输出后出现 error 事件、传输中断、异常 EOF 或缺失协议结束：partial_failure；
- 2xx 结束但从未出现 Semantic Evidence：fake_alive / transient failure；
- 4xx、5xx、429：按统一错误分类；
- 客户端取消：ignored；
- 网关暂停或关闭导致的取消：ignored。

partial_failure 会累计 Route 健康失败并保留“客户端已收到部分内容”标记，但由于已经 Commit，绝不触发重试。Probe 在首个语义证据后主动取消属于预期成功，不得套用真实流量的“缺少结束事件”规则。

## 7. 端点、鉴权与 TransportManager

### 7.1 EndpointResolver

默认端点映射：

| Endpoint | 方法 | 规范路径 |
|---|---|---|
| messages | POST | /v1/messages |
| responses | POST | /v1/responses |
| chat_completions | POST | /v1/chat/completions |
| count_tokens | POST | /v1/messages/count_tokens |
| models | GET | /v1/models |

解析规则：

1. 如果指定 Endpoint 有 url_override，使用该完整 URL；
2. 否则使用去尾斜杠的 base_url 加规范路径；
3. url_override 的固定 query 保持配置时的原始顺序；
4. 入站 RawQuery 不解析、不排序，按原始字符串追加；
5. 固定 query 已存在时使用 & 追加，否则使用 ?；
6. fragment 一律拒绝；
7. query 中的 Secret 使用加密引用渲染；
8. 解析结果供真实请求、探活、models 和 count_tokens 共用。

url_override 只能修改与 base_url 相同 scheme 和 authority 下的路径与 query。跨 origin 必须新建另一个 Upstream，避免一个站级 Reachability 结论错误代表不同网络目标。Upstream 的 Host Override、代理和 TLS 设置属于 network origin 的一部分，并对该 Upstream 的全部 Endpoint 一致生效。

若固定 query 与入站 RawQuery 含同名参数，两者均保留，顺序为固定 query 在前、入站 RawQuery 在后；界面预览明确提示由上游决定采用第一个还是最后一个。

### 7.2 Endpoint Auth Profile

Auth Profile 指定：

- header_bearer；
- x_api_key；
- api_key；
- fixed_query_secret；
- manual_headers；
- auto_calibrated。

auto 校准一次只尝试一个候选认证方式，不能无依据地同时发送多个认证头。校准结果绑定 Endpoint 和版本，并在脱敏预览中展示。

真实请求的 Auth Profile 优先于 Probe Recipe 中的普通头；探活自定义认证只能使用 UPSTREAM_API_KEY 或 Probe Secret 占位符。

### 7.3 TransportManager

连接池键至少包含：

- Upstream ID；
- proxy_url；
- TLS 最低版本和证书策略；
- 有效 connect timeout；
- 影响连接复用的网络配置。

真实请求、L1、L2 和 count_tokens 各自传入有效 connect timeout。值相同可以共享连接池；值不同必须使用不同池。配置改变时关闭旧池的空闲连接，在途请求持有旧引用直到结束。

### 7.4 默认超时

默认值面向高延迟公益站，可在管理界面热修改：

| 场景 | 设置 | 默认值 |
|---|---|---:|
| 真实请求连接 | real_connect_sec | 30 秒 |
| 真实请求响应头 | real_response_header_sec | 1200 秒 |
| 真实请求首字节 | real_first_byte_sec | 1200 秒 |
| 真实请求首语义 Token | real_first_semantic_sec | 1200 秒，硬下限 300 秒 |
| 真实请求流内静默 | real_idle_sec | 600 秒 |
| 真实请求总时长 | real_total_sec | 1800 秒 |
| L1 连接 | l1_connect_sec | 30 秒 |
| L1 总时长 | l1_total_sec | 90 秒 |
| L2 连接 | l2_connect_sec | 30 秒 |
| L2 响应头 | l2_response_header_sec | 300 秒 |
| L2 首字节 | l2_first_byte_sec | 300 秒 |
| L2 首事件 | l2_first_event_sec | 300 秒 |
| L2 首语义 Token | l2_first_semantic_sec | 300 秒 |
| L2 流内静默 | l2_idle_sec | 120 秒 |
| L2 总时长 | l2_total_sec | 600 秒 |
| count_tokens 连接 | count_tokens_connect_sec | 30 秒 |
| count_tokens 总时长 | count_tokens_total_sec | 180 秒 |

四个时间点分别记录：

- response_header_at；
- first_byte_at；
- first_event_at；
- first_semantic_at。

响应头、首字节、首事件和首语义上限都从请求 SentAt 起算，而不是四段顺序累加；total 是最外层硬上限。首语义之后才启用可重置的流内 idle 计时。

L2 使用原生长思考配方时，first_semantic 不得低于 300 秒。普通最小配方仍可手动配置更短的首事件观察，但不能绕过原生长思考的硬下限。

任何单次探活超时只影响该次探活，不得缩短真实请求超时。

## 8. P0 探活与能力系统

### 8.1 设计目标

探活必须覆盖 New API、One API、sub2api 及常见兼容实现的：

- /v1/models；
- /v1/messages；
- /v1/responses；
- /v1/chat/completions；
- /v1/messages/count_tokens。

“兼容任意中转站”不是可验证的绝对承诺。v1.0.0 的可验证目标是：

- 标准协议 fixture 全部通过；
- 已提供的实际站点在相同时间窗口与原生客户端对照一致；
- 未知请求要求可通过自定义 Probe Recipe 表达；
- 每个失败都有稳定、可理解、不会连坐错误范围的分类。

### 8.2 Probe Recipe 解析优先级

从高到低：

1. Route 对当前 Endpoint 的已发布手动配方；
2. Upstream 对当前 Endpoint 的已发布默认配方；
3. ClientFingerprintLearner 生成的安全学习配置；
4. 内置协议模板。

完整手动配方发布后为 pinned。学习器只能展示差异，不能覆盖。用户必须显式恢复自动模式。

### 8.3 内置模板

内置模板分为：

- compact-native：保留 Claude Code 或 OpenAI 客户端所需的协议形状、查询和安全头，使用最小业务输入及最小可接受输出；
- calibration-native：更接近真实请求，用于首次校准、手动诊断或特殊站点，不进入常规周期；
- basic-protocol：标准 Anthropic/OpenAI 最小请求，作为兼容实现的最后基线。

周期探活优先 compact-native，并在第一个 Semantic Evidence 出现后立即取消响应，减少输出 Token。

内置模板不得写死：

- 某次抓包的会话 ID；
- 某个客户端的永久版本号；
- 对话历史；
- 用户 system prompt；
- 真实工具定义；
- 用户标识；
- 真实文件路径。

### 8.4 ClientFingerprintLearner

学习器只观察成功的真实请求，并保存：

- 安全的协议头名称和值模式；
- query 形状和 beta 名称；
- 顶层字段是否存在；
- 合法的枚举和布尔配置；
- 客户端版本族；
- 需要动态生成的会话字段。

不得保存：

- messages 内容；
- system 内容；
- tool 描述或 schema；
- metadata 中的用户标识；
-认证值；
-文件内容；
-任意可还原私人工作上下文的文本。

学习结果先进入候选状态，经脱敏差异预览和一次测试后才能用于自动探活。

### 8.5 自定义请求头和请求体

作用域：

- Upstream + Endpoint 默认；
- Route + Endpoint 覆盖。

请求头和 body 均可完全自定义。body 是任意原始字节，不限于 JSON。只替换显式占位符，其余字节保持。

Header Template 使用有序的名称与多值列表表达，必须支持同名头的多个值；协议栈不保证最终头顺序或大小写。Body Template 在数据库中保存 BLOB，管理 API 对 UTF-8 文本使用 body_text，对任意二进制使用 body_base64，两者互斥；预览显示字节数和哈希。

支持的内置占位符：

- UPSTREAM_API_KEY；
- UPSTREAM_MODEL；
- MODEL_NAME；
- PROBE_PROMPT；
- SESSION_ID；
- TIMESTAMP；
- SECRET:name。

Secret 明文只在写入时接受，数据库保存密文，读取 API 只返回掩码。

以下字段由 Transport 管理，模板不能伪造：

- Content-Length；
- Transfer-Encoding；
- Connection 及其声明的逐跳头。

Host 只允许通过 Upstream 的专用 Host Override 配置，并一致作用于该 Upstream 的全部 Endpoint；不允许作为普通自定义头逐端点改写。

配方生命周期：

1. draft；
2. 脱敏预览；
3. 单次测试；
4. enable；
5. disabled 或 archived。

测试失败时允许二次确认后强制启用，但 UI 必须保留失败结果和审计记录；旧的 active 版本在新版本正式启用前继续生效。

### 8.6 ProbeExecutor

每次执行：

1. 固定配置和配方版本；
2. 渲染 URL、头、body 和 Secret；
3. 校验受保护字段；
4. 使用场景对应 Transport；
5. 记录连接、响应头、首字节、首事件、首语义时间；
6. 交给统一 ResponseClassifier；
7. 一旦得到确定结论立即取消；
8. 无自动重试；
9. 写入 ProbeExecution、Cost 和 Capability。

模板、URL、Secret 或头校验失败为 config_error，不发送请求，不改变健康。

Auth Profile 校准是单独、显式、逐次可见的操作，不属于 ProbeExecutor 的隐藏重试。周期探活只使用已经验证的 Auth Profile；未知认证方式时使用协议默认候选或等待人工校准，不在一次周期探活中轮流消耗多个请求。

### 8.7 CalibrationRun

首次配置、Route 语义变化或用户手动要求时，可以启动一个有限且完全可见的 CalibrationRun。它不是单次 Probe 的自动重试，而是由多个独立 ProbeExecution 组成的状态机：

- planned；
- running；
- succeeded；
- failed；
- canceled。

默认最多测试 3 个候选，每个候选最多发送一次模型请求，候选和预估成本在执行前展示。候选顺序根据已有证据确定，通常为：

1. 已学习的安全客户端配置；
2. compact-native；
3. basic-protocol 或 calibration-native 中更符合错误提示的一个。

只有明确的结构或认证兼容错误才进入下一个候选，例如缺少 beta、字段不被接受、鉴权头错误或端点协议形状错误。429、502、503、504、连接失败和语义超时属于瞬时或站点故障，CalibrationRun 停止并保留当前候选，不通过换模板掩盖故障。

成功后固定 Auth Profile、Recipe 来源和版本；失败显示每个独立 ProbeExecution、Token 估算和脱敏原因。Active 模式可在首次配置时自动启动受限 CalibrationRun；Lazy 模式只允许用户明确点击后运行一次。

本服务对客户端暴露的 GET /v1/models 始终返回本地已配置的逻辑 ModelName 列表，不代理上游。Probe 中的上游 /v1/models 仅用于 Reachability 和 models Capability，两者不得混淆。

### 8.8 流式与非流式解析

统一解析器必须支持：

- 标准 SSE；
- 一个事件包含多行 data；
- event 与 data 分离；
- CRLF 和 LF；
- 注释行；
- ping 和 keepalive；
- NDJSON；
- 普通 JSON；
- 数据跨网络 chunk；
- UTF-8 边界跨 chunk；
- Anthropic、Responses 和 Chat Completions 事件。

判活证据包括：

- 非空 text delta；
- 非空 thinking/reasoning delta；
- 非空 tool/input JSON delta；
- 非空 refusal delta；
- 正数 output usage；
- 非流式响应中的非空模型输出。

以下都不能单独判活：

- HTTP 200；
- message_start；
- response.created；
- ping；
- 空 delta；
- output_tokens:0；
- usage 对象存在但值为 0；
- error:null；
- 只有结束标记而没有模型输出。

结构化错误可出现在：

- HTTP 4xx/5xx body；
- HTTP 200 SSE error event；
- HTTP 200 普通 JSON；
- NDJSON 行；
- 正常事件中的非空 error 字段。

### 8.9 Reachability 与 /models

Active 模式对每个 Upstream 每轮最多调用一次 /models。

- DNS、TCP、TLS、连接建立失败：Reachability 失败。
- 收到任何合法 HTTP 响应：Reachability 为 reachable。
- /models 200 且结构可读：models Capability supported。
- /models 404/405：models Capability unsupported，但站仍 reachable。
- /models 401/403：鉴权校准后仍失败则为 config_error，但站仍 reachable。
- /models 429/5xx：transient_error，但站仍 reachable。

只有真正的 Reachability 失败才允许短路该轮昂贵模型探测。HTTP 业务状态不能把整个站连坐为网络不可达。

### 8.10 Route 模型探测

模型端点按 Route 执行，因为同站不同模型可能独立故障。

- 同一 Upstream 的模型探测串行；
- 全局并发默认 3；
- 每 Route、每 Endpoint 有独立 single-flight；
- 第一个 Semantic Evidence 后立即取消；
- 真实成功可以 piggyback，推迟下一次合成 L2；
- count_tokens 不进入周期探活，只在校准、手动测试或真实请求中观察；
- 一个周期内不对同一个站重复调用 /models。

默认 Active 调度：

| 状态 | 默认间隔 |
|---|---:|
| reachable Upstream 的 /models | 60 秒 |
| unreachable Upstream 的连接恢复检查 | 20 秒 |
| alive Route 的 L2 | 600 秒，近期真实成功则跳过 |
| dead 不超过 10 分钟的 Route | 30 秒 |
| dead 10–60 分钟的 Route | 120 秒 |
| dead 超过 60 分钟的 Route | 300 秒 |

所有周期增加正负 10% jitter。配置、手动操作和 Reachability 从 unreachable 恢复会触发即时调度，但仍受全局并发和同站串行限制。

长期死亡只放宽模型探测间隔，网络恢复检查保持快速。这样兼顾恢复速度和 Token 消耗。

下一次到期时间从本次 Probe 完成时计算。单次 Probe 仍在运行时只保留一个待执行标志，不因较短调度间隔形成完成后的瞬时连发。

### 8.11 Lazy 模式

Probe Mode 配置在 Upstream：

- Lazy 不调用 /models；
- Lazy 不调用 messages、responses 或 chat_completions；
- Lazy 不调用 count_tokens 做校准；
- Lazy 不执行周期 canary；
- Lazy 只消费真实请求结果、真实 count_tokens 结果、cooldown 和人工诊断结果。

人工点击“测试”属于用户明确触发，可以发送一次请求，但不会改变该站的长期 Lazy 设置。

Lazy Route 冷却到期后进入 half-open eligible。它按原有优先级参与选择，但每个 Route 的 RecoveryGate 只允许一个真实 Attempt：

- 成功：立即恢复为 alive；
- 失败：重新进入 cooldown；
- 其他并发请求：选择健康替代 Route；
- 没有替代 Route：返回 503 与 Retry-After；
- 同一客户端请求最多尝试一个 dead Route，失败且尚未提交时可按重试策略转到健康 Route。

Lazy 模式不承诺固定秒数恢复上界；恢复取决于下一次真实流量。

### 8.12 探活失败分类

| 现象 | 分类 | 健康动作 |
|---|---|---|
| 模板、URL、Secret、受保护头错误 | config_error | 不改变 RouteHealth |
| 401/403 | 先校准鉴权；仍失败为 config_error | 不连坐 Upstream |
| 404/405 on models/count_tokens | unsupported | 不改变模型健康 |
| model_not_found | Route config_error | 排除该 Route，等待配置修改 |
| 429 | transient_error / cooldown | 遵循 Retry-After，不判 dead |
| DNS/TCP/TLS 失败 | unreachable | 达阈值后暂时排除该站 Route |
| 502/503/504 | transient_error | 累计失败阈值 |
| 首语义超时或无语义 EOF | transient_error | 累计 Route 失败 |
| HTTP 200 结构化 error | 按错误码细分 | 不得按 200 判活 |
| 客户端取消、暂停、关闭 | ignored | 不计健康 |

### 8.13 Capability 生命周期

Capability 与 URL、认证、模型和配方版本绑定。任意关联配置改变后立即回到 unknown。

默认过期策略：

- supported：7 天无新观察后显示 stale，但仍可参与真实尝试；
- unsupported：24 小时后回到 unknown，由下一次真实调用或手动测试重新验证；
- transient_error：按 Retry-After 或 cooldown 过期；
- config_error：仅配置变更或人工重新测试后解除。

- output_tokens:0；
- 空 delta；
- 多行 SSE；
- NDJSON；

## 9. 健康状态、配置失效与恢复

### 9.1 Route 状态机

只有“从未出现有效负结论”的普通 unknown 才按乐观策略允许真实请求。由 dead 恢复而来的状态必须使用 recovering，并始终经过 RecoveryGate；UI 分别显示“未验证”和“恢复确认中”。

默认状态变化：

- 获得 RecoveryGate 的真实成功：recovering 或 dead 立即进入 alive；
- 普通 unknown 的真实成功：进入 alive；
- 合成成功：dead 首次成功进入 recovering，达到 OKThreshold 后才能进入 alive；
- transient 失败：达到 FailThreshold 后进入 dead；
- 429：只进入 cooldown；
- config_error：由 Capability 排除，不伪装成 dead；
- ignored：不改变任何计数。

真实成功的证据权重大于合成最小请求。

### 9.2 Route 修改失效矩阵

以下修改必须清除旧 RouteHealth、cooldown、RecoveryGate、Capability、调度预占和学习引用：

- ModelNameID；
- UpstreamID；
- UpstreamModel；
- ModelName Protocol；
- Endpoint 来源或 URL；
- Auth Profile；
- Probe Recipe；
- 请求 Transform 的绑定、发布、停用或回滚；
- Upstream 的 network origin、proxy_url、TLS 或 Host Override；
- Upstream 从 disabled 变为 enabled；
- Route 从 disabled 变为 enabled。

手动 Probe Recipe 和 Transform 版本不直接删除，但语义变化后解除绑定并降为未验证草稿，必须重新测试发布。

以下修改不清健康：

- priority；
- weight；
- max_concurrency；
- 显示名称或纯 UI 字段。

数据库更新、持久健康清理和语义版本递增在同一事务中完成。内存立即失效，不等待 livecfg 的缓存 TTL。

### 9.3 迟到结果保护

每次观察携带由以下版本组合得到的 Observation Token：

- Route；
- ModelName；
- Upstream；
- Endpoint；
- Auth Profile；
- Probe Recipe 或 Transform。

回写时 Token 与当前配置不一致则丢弃，并记录 stale_observation 计数。仅清 map 而不检查 Token 不足以解决并发竞态。

### 9.4 RecoveryGate

RecoveryGate 与 max_concurrency 分离：

- 每个 Route 同时最多一个 half-open Attempt；
- dead 或 recovering Route 无论对外显示为何种未验证状态都必须经过该闸；
- max_concurrency=0 也不能绕过 single-flight；
- 获得 RecoveryGate 后仍需获取普通并发配额；
- 所有错误、取消、panic 防护和提前返回路径都必须释放；
- 客户端取消不算恢复失败；
- 其他请求不排队，直接选择替代 Route 或返回 503；
- 成功立即解除 cooldown 并恢复；
- 失败按类别重新 cooldown。

## 10. count_tokens

### 10.1 默认行为

Claude Code 调用 POST /v1/messages/count_tokens 时，默认转发到选中上游的同名端点。请求认证、RawQuery、模型映射、URL 解析和严格透传规则与 messages 一致。

### 10.2 Route 级能力

管理界面必须显示每个 Route 的 count_tokens：

- supported；
- unsupported；
- unknown；
- transient_error；
- config_error；
- 最后测试时间和脱敏原因。

### 10.3 选路顺序

1. 健康且已知 supported 的 Route，按正常优先级选择；
2. 前一个 supported Route 临时失败时，尝试下一个已知 supported Route；
3. 没有 supported 时，可对一个健康 unknown Route 使用当前真实 count_tokens 请求进行观察；
4. 均失败或全部 unsupported 时使用本地估算。

count_tokens 的失败不改变 Route 模型健康，也不触发模型 L2。404/405 标记该 Route 的 count_tokens unsupported；401/403 进入端点配置错误；临时失败只影响该 Capability。

### 10.4 本地估算

本地估算保留：

- system；
- messages；
- tools；
- CJK；
- 超长无空白字符串和 base64；
- 保守偏高策略。

响应使用 Anthropic 格式，并用 X-Relay-Count-Tokens: estimated 标明本地估算。该头只出现在网关生成的响应中。

## 11. 自动重试与幂等风险

### 11.1 基本原则

连接失败、5xx 或首 Token 超时不能证明上游没有执行请求。每一次重试都可能产生重复模型调用和 Token 消耗。

系统不得宣称模型请求天然幂等，也不得自行添加新的 Idempotency-Key。客户端已有的幂等头原样保留。

### 11.2 策略

Retry Policy 为全局设置，默认 Balanced：

| 策略 | 自动重试范围 |
|---|---|
| Safe | 仅在证据表明请求尚未写入上游时的 DNS、TCP、TLS 或建连失败 |
| Balanced | Safe，加 429、502、503、504、明确 no_available_channel 等临时错误；必须尚未提交客户端 |
| Aggressive | Balanced，加提交前首响应体字节超时、通用 5xx、HTTP 200 的结构化流内错误 |

Balanced 和 Aggressive 的潜在重复执行风险必须记录。Safe 也只有在写入证据可靠时才能标记 duplicate_risk=false。

### 11.3 默认预算

- retry_max_attempts 默认 3，含第一次；
- 最大值 5；
- 同一 Route 每个客户端请求最多尝试一次；
- 所有 Attempt 共享 real_total_sec 总预算；
- 剩余预算不足一次 connect timeout 时停止重试；
- 客户端取消后立即停止；
- 已向客户端写出任何响应字节后永不重试。

### 11.4 写入证据

每次 Attempt 记录：

- 是否获取连接；
- 请求头是否开始写；
- body 是否开始读取；
- WroteRequest 回调及错误；
- 是否收到响应头；
- 是否收到响应 body；
- 是否向客户端提交；
- duplicate_risk；
- retry_reason。

Safe 策略只接受明确发生在 body 写入前的失败。无法证明时按“可能已执行”处理。

### 11.5 有界前缀检查

为了识别立即返回的 HTTP 200 错误，Send 阶段可以预读：

- 最多 64 KiB；
- 最多 2 秒；
- 只到完整事件或完整 JSON 判定边界；
- Commit 时按原字节顺序重放；
- 不能重新序列化。

Safe 和 Balanced 超过窗口仍不能确定错误时立即 Commit，即使此时只有响应头；之后的首字节或首语义超时只能终止和记健康，不能再重试。

Aggressive 可以把“等待首响应体字节”的提交前窗口扩大到 real_first_byte_sec，并在超时后换站，但必须在 UI 明示它会延迟响应头且可能重复执行。Aggressive 也不得为了等待首语义内容而缓存长时间 ping 或 keepalive；一旦选择把任何上游响应字节提交给客户端，后续首语义超时同样不能重试。

### 11.6 最终响应

发现可重试结果后，必须先确认存在下一个可用 Candidate，再 Discard 当前 Attempt。没有替代 Route 时提交当前上游原始错误，不能把有信息的上游响应变成空响应或本地笼统 502。

## 12. 部署、凭据与运行控制

### 12.1 本地模式

目标：

- Windows 和 Linux；
- 绑定 127.0.0.1；
- 默认端口 18787，可参数覆盖；
- HTTP；
- 不申请证书；
- 不允许局域网或公网直接访问。

一行命令：

- Windows：PowerShell 执行根目录 deploy.ps1；
- Linux：执行 ./deploy.sh --local。

### 12.2 Linux 公网 IP 模式

前提：

- 稳定公网 IPv4 或受支持的公网 IP；
- 外网可访问 80 和 443；
- Docker 与 Docker Compose 可用。

一行命令：

- sudo ./deploy.sh --public；
- 可用 --ip 显式指定，否则脚本自动探测并要求确认。

公网模式：

- 不需要域名；
- 不要求 ACME 邮箱；
- 不设置管理登录 IP 白名单；
- 80 跳转 443；
- 443 使用公网信任的 IP 证书；
- Nginx 对 SSE 禁用缓冲并设置至少 35 分钟上游超时；
- relay-gate 本体不直接暴露到公网。

Let’s Encrypt 已提供短期 IP 证书，证书有效期为 160 小时。公网部署使用支持 IP 证书的 Certbot 5.4+，持久化 ACME 状态，每日尝试续期，成功后自动 reload，并对剩余有效期告警：

- https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability
- https://letsencrypt.org/2026/03/11/shorter-certs-certbot

实现阶段必须通过 Certbot 功能探测和容器集成测试确定具体命令，不在脚本里假设旧版本参数。

首次签发采用失败关闭的启动状态机：

1. 自动探测或读取 --ip，要求用户确认，并校验本机对外监听地址与 ACME 目标一致；
2. 先启动临时 Nginx，只允许 `/.well-known/acme-challenge/`，其他 HTTP 路径一律返回 503；此阶段不得暴露管理页或模型端点；
3. 申请 IP 证书；
4. 校验证书 SAN 包含目标 IP、证书链有效、剩余有效期合理且私钥权限正确；
5. 通过配置测试后原子切换为正式 Nginx：80 只跳转 443，443 才反向代理 relay-gate；
6. 签发或校验失败时保持业务不可访问并给出可操作错误，禁止回退为明文 HTTP。

续期先写入 Certbot 管理的持久目录，验证新证书后再 reload；reload 失败保留仍有效的旧工作进程并告警。Nginx 必须覆盖而不是追加 `X-Forwarded-For`、`X-Forwarded-Proto` 等内部边缘元数据，relay-gate 只接受受控内部网络上的 Nginx，并在转发上游前剥离这些内部元数据。relay-gate 容器使用固定非 root UID 运行，数据卷和 Keyring 由该 UID 持有。

### 12.3 首次凭据

首次部署生成恰好三项：

1. 管理员密码；
2. Relay API Key；
3. 32 字节 Master Key。

官方部署脚本先通过一次性容器执行 credentials bootstrap，将三项明文只输出到当前终端，再启动长期容器。长期容器后续重启不得重复输出。

用户绕过部署脚本直接启动未初始化实例时，长期服务拒绝启动并提示运行一次性 credentials bootstrap；不得把初始凭据写入常驻容器日志。

bootstrap 使用数据目录独占锁和持久 journal，状态为 prepared、credentials_persisted、displayed。新安装在 credentials_persisted 后、displayed 前异常退出时，下次 bootstrap 撤销未交付的管理员密码和 Relay Key，生成新值，并连同现有 Master Key 重新输出三项；不得留下“数据已初始化但用户永远拿不到管理员密码”的状态。旧环境变量迁移使用独立 migration journal，优先导入旧凭据，不能同时生成另一套随机凭据。

### 12.4 Master Key

持久根：

- data/secrets 目录权限 0700；
- data/secrets/keyring.json 权限 0600；
- 文件所有者为 relay-gate 的固定非 root 服务 UID；
- 包含 key_id、active、pending 和恢复元数据；
- 不把 Master Key 存在 SQLite 内自加密；
- 数据库密文使用版本信封 v1:key-id:nonce+ciphertext。

UI 在重新输入管理员密码后可短时查看当前 Master Key。显示内容：

- 默认遮罩；
- Cache-Control: no-store；
- 不写 localStorage、sessionStorage 或前端日志；
- 超时自动清除；
- 记录审计事件。

### 12.5 管理员密码

- 只保存 Argon2id 哈希；
- 首次或重置时明文显示一次；
- 后续不可查看；
- UI 显示“不可查看，可重新生成”；
- 重置后立即撤销其他会话；
- 当前执行重置的 Cookie 会话换发新 Token，允许展示一次新密码；
- 服务器本地 CLI 提供锁定后的 reset-admin 兜底。

### 12.6 Relay Key

- 高熵明文使用 Master Key 加密，以支持重新认证后查看；
- 同时保存不可逆摘要用于热路径鉴权；
- 默认轮换时新旧 Key 并存 10 分钟；
- UI 显示 grace 倒计时；
- 可选择立即撤销旧 Key；
- 内存验证快照原子更新，无需重启；
- 所有查看和轮换均审计。

### 12.7 Master Key 轮换

流程：

1. 进入 maintenance；
2. 拒绝新模型流量；
3. 等待在途写操作收敛；
4. 创建一致性备份；
5. 生成 rotation_id 和 pending Key；
6. 以 phase=prepared 将旧 Key、新 Key 和 rotation_id 写入 Keyring；
7. 在 SQLite 事务中重加密 upstream、relay、probe、SMTP、transform 等所有直接 Secret，重新包装 Sample Data Key 和安全证据 Data Key，并写入相同 rotation_id；
8. 全量逐项解密校验；
9. 提交数据库并把数据库阶段写为 db_committed；
10. 原子切换 Keyring active Key，并写为 key_activated；
11. 再次全量校验所有 Secret；
12. 移除旧 Key并写为 cleaned；
13. 退出 maintenance。

Keyring 每次更新都使用同目录临时文件、文件 fsync、原子 rename 和目录 fsync，并保留一个校验通过的 keyring.previous。rotation_id 和阶段同时存在于 SQLite 与 Keyring。

恢复规则：

- prepared 且数据库未提交：删除 pending 并回滚；
- db_committed：旧新 Key 都仍存在，必须前滚完成 key_activated，不能声称回滚已提交数据库；
- key_activated：使用新 Key 完成全量验证和 cleaned；
- Keyring 主文件损坏：只在 keyring.previous 的校验和与数据库 rotation_id 匹配时恢复；
- 旧 Key 只有在所有 Secret 全量解密验证通过后才能删除。

UI 只在 cleaned 后显示轮换成功。进程重启发现未完成阶段时先执行恢复，恢复完成前保持 maintenance。

### 12.8 旧凭据迁移

旧部署只能由 migration journal、数据库 schema 和旧环境变量证据共同识别；不得只以“新 Keyring 和 Credential 表为空”作为迁移或全新初始化的判断。识别为旧部署后：

- 一次性读取 ENCRYPTION_KEY；
- 保留旧 SHA-256 派生方式解密现有上游 Key；
- 导入 ADMIN_PASSWORD 为 Argon2id 哈希；
- 导入 RELAY_KEYS 为新的 relay_key 记录；
- 写入迁移完成标志；
- 提示用户从环境变量删除旧 Secret。

后续启动不得再次导入并覆盖 UI 轮换结果。

### 12.9 会话安全

公网模式必须：

- Cookie 为 HttpOnly、Secure、SameSite=Strict；
- 管理写操作保留 CSRF 校验；
- 只信任来自内部 Nginx 网络的代理头；
- 登录按来源 IP 和全局进行退避；
- 登录失败不泄露账号状态；
- 敏感查看和轮换只接受 Cookie 会话加当次管理员密码，不能只凭通用 Bearer；
- HTTPS 响应包含适当安全头。

删除登录 IP 白名单不等于降低登录保护。

## 14. 上游内容安全与邮件告警

### 14.1 定位

安全诊断输出风险信号，不声称证明上游恶意。默认只告警、只记录，不自动阻断、不自动修改响应、不自动禁用 Route。

用户可以在诊断后手动禁用 Route。

### 14.2 被动本地扫描

所有真实响应在已提交客户端后的旁路观察通道中扫描。扫描内容包括：

- 协议外 HTML、JavaScript、广告或登录页；
- 异常角色或伪造系统消息；
- 未请求的工具、文件或命令指令；
- 索取凭据、系统提示或私有上下文；
- prompt injection 常见模式；
- Unicode 隐藏字符和编码载荷；
- 可疑外链；
- 已知 Credential 片段；
- canary nonce 或工具约束违例。

合法编程回答中出现 Shell、PowerShell、JavaScript 或 Python 代码，不能仅因“包含脚本”就判为高风险。规则需要结合协议位置、指令对象、上下文和多个信号。

### 14.3 执行隔离

- 扫描队列有界；
- 队列满时丢弃扫描任务而不是阻塞转发；
- 记录 dropped 数并告警；
- 样本关闭时仍可扫描；
- 样本关闭时只保存有限脱敏证据、哈希和元数据；
- 扫描器完全本地运行；
- 自定义规则为正则、字符串、Unicode 和结构条件，不执行代码。

默认资源边界：

- 每个响应最多扫描 1 MiB 解码后内容，同时保留首尾和滚动窗口；
- 单个 SSE/NDJSON 事件最大 256 KiB；
- gzip/br 只在旁路副本中有界解压；
- Base64、URL 编码和 Unicode 规范化最多递归 2 层；
- 解码后累计字节最多 4 MiB；
- 自定义正则仅使用 Go RE2，单模式最大 4 KiB；
- 单个响应扫描 CPU 预算默认 100 毫秒；
- 超限、解码失败或预算耗尽生成 incomplete finding，而不是宣称安全。

每条 finding 保存 scanner_version、rule_version、bytes_scanned、truncated、decode_depth 和 incomplete_reason，确保升级规则后可以解释旧结论。

### 14.4 主动 canary

主动诊断使用：

- 随机 nonce；
- 严格预期输出；
- 无副作用的 inert tool；
- 最小上下文；
- 单独 Token 统计。

默认仅手动触发。Active Upstream 可选择开启周期 canary，但默认关闭。严格 Lazy 下只允许用户明确点击的一次性诊断，禁止周期 canary；启用周期 canary 前必须先把该 Upstream 切换为 Active，确保“Lazy 零合成请求”始终成立。

主动诊断失败不自动改变模型健康，除非同一次执行同时满足正常 Probe 的独立判定条件。

### 14.5 Security Center

支持：

- 严重级别；
- Upstream、Route、规则、时间筛选；
- 脱敏证据；
- 关联样本和诊断；
- 重新认证后查看未脱敏证据；
- 标记误报；
- 对某规则或某 Route 建立忽略；
- 重新运行手动诊断；
- 手动禁用 Route。

所有证据按纯文本显示，防止存储型 XSS。

### 14.6 邮件

- 仅 STARTTLS 或 SMTPS；
- SMTP 密码加密；
- Critical 可立即发送；
- 中低级别默认聚合摘要；
- 同一发现去重并限速；
- 邮件只含元数据、脱敏摘要和管理页面链接；
- 不发送原始对话、完整响应、Secret 或未脱敏证据；
- SMTP 失败不影响转发。

### 14.7 安全验收

- 扫描前后响应状态、头和 body 不变；
- 合法代码不能仅因包含脚本被判为高危；
- 队列满时真实流量不阻塞；
- 页面不存在存储型 XSS；
- 邮件不含敏感正文；
- 未启用主动 canary 时无额外模型请求；
- 风险发现不会自动改变 RouteHealth。

## 15. 声明式流量转换

### 15.1 基本边界

- 默认关闭；
- 按 Route + Endpoint 显式绑定；
- 配置集可以显式绑定多个 Route，但不自动继承整个 Upstream；
- 同一个 Route + Endpoint 最多绑定一个 published 版本和一个 shadow 版本；
- 不执行任意脚本；
- 启用后该绑定明确退出严格透传模式；
- 未绑定规则时不得进入 JSON 解析、重序列化或响应事件转换路径。

### 15.2 生命周期

转换配置：

1. draft；
2. 脱敏预览；
3. 使用历史或手工样本测试；
4. shadow；
5. published；
6. disabled 或 archived；
7. rollback。

发布版本不可变。published 和 shadow 是绑定指针，不是对不可变版本的原地状态修改；rollback 只把 published 指针原子切回旧版本。shadow 只在旁路副本上计算差异，绝不改变或额外发送真实请求。一次客户端请求固定使用开始时的发布版本，发布和回滚不影响在途请求。

### 15.3 请求转换顺序

1. 从原始入站请求重建本次 Attempt；
2. 应用 Endpoint URL、认证和模型映射；
3. 执行请求规则；
4. 保护层重新强制写入认证，并只替换已经存在的唯一 Route 模型；
5. 重新验证唯一字符串 model；
6. 重算传输字段。

规则不能最终控制：

- 上游 API Key；
- Route 模型映射；
- Content-Length；
- Transfer-Encoding；
- Connection；
- 目标 URL 和 Host。

这些内容使用专用配置修改。

任何读取 Secret 或认证字段的值都带敏感污点。污点值不得进入条件捕获、预览、差异、执行记录、错误文本或审计详情。编译器同时拒绝头值 CR/LF、超出 body/事件上限的规则、无界正则和超过执行预算的配置。

默认资源上限为：每个版本 100 条规则、单个正则 4 KiB 且仅使用 Go RE2、单个 SSE 事件 1 MiB、一次转换新增字节 1 MiB、请求或非流式响应规则总执行预算 50 毫秒、单个流式事件预算 10 毫秒。上限可以下调；提高需要管理界面二次确认并记录审计。

### 15.4 请求规则

支持：

- 请求头设置、删除、重命名和条件替换；
- 修改已有 JSON Pointer 值；
- JSON Patch 增加、删除、复制；
- 原始字节精确查找替换；
- 完整 body 模板；
- Secret 引用；
- 按协议、端点、模型、请求头和 JSON 字段匹配。

修改已有 JSON 值时优先使用偏移替换，保持其他字节。增加、删除或复制字段可能重序列化整个 JSON，UI 必须明确警告“未修改部分不再保证字节一致”。

### 15.5 响应规则

非流式支持：

- 状态码映射；
- 响应头增删改；
- JSON 字段修改或删除；
- 错误结构转换；
- 原始字节替换；
- 完整响应体。

流式支持：

- Anthropic SSE；
- OpenAI Responses SSE；
- Chat Completions SSE；
- 按事件类型、状态、错误码和 JSON Pointer 匹配；
- 修改、删除或新增单个完整事件；
- 错误事件格式归一化；
- 协议状态明确时补齐结束事件。

流式规则逐事件执行和 Flush，不缓存整个流。

响应头和状态码规则必须在 Commit 前原子完成。规则不能直接设置 Content-Length、Content-Encoding、Transfer-Encoding、Connection 或其他逐跳字段；这些字段由响应保护层依据最终 body 和传输方式处理。非流式 body 转换需要在配置的最大缓冲上限内完整读取，默认上限 8 MiB，超限按 Commit 前失败策略处理。

### 15.6 中断修复

已经向客户端输出后：

- 不切换上游；
- 不重放模型请求；
- 不猜测或生成丢失内容；
- 可以显式配置补齐协议结束事件；
- 所有补齐记录 synthetic_completion=true。

“把截断内容标记为正常完整完成”是高风险选项，默认禁用，启用需要二次确认。它只能封闭协议，不能证明内容完整。

v1.0.0 不实现跨上游自动续写或流拼接，因为它会重复上下文、改变模型语义并无法保证连续性。

### 15.7 失败策略

- 请求转换默认 fail_closed：失败时不请求当前 Route，并按 route-local config_error 规则选择替代 Route；
- 响应转换默认 fail_open：在 Commit 前失败时提交原始状态、头和 body；
- 非流式转换在缓冲上限内保留原始 body，失败时可回退；
- 流式按完整事件原子转换，Commit 后 fail_open 原样传该事件；
- 流式 Commit 后的 fail_closed 只能终止连接并记录 transform_stream_failure，不能再返回本地错误或恢复原始已修改前缀；
- fail_closed 需要返回完整本地错误的情况必须发生在 Commit 前；
- 任何失败都记录配置版本、命中规则和脱敏差异。

### 15.8 转换验收

- 未绑定规则时请求和响应没有转换回归；
- 规则不能篡改最终认证、模型和传输字段；
- 完整 body 模板不能制造重复 model；
- 流式转换不等待完整响应；
- 不输出半个 JSON 或半个 SSE 事件；
- 新版本不影响在途请求；
- 回滚只影响新请求；
- synthetic completion 全部可追踪；
- 系统不存在任意代码执行入口。

## 19. 旧配置迁移

### 19.1 Probe 字段

- upstream.probe_headers：导入为 Upstream + Endpoint 的只读 legacy_compat Recipe；
- upstream.l1_path：导入 models Endpoint 设置；
- model_name.probe_prompt：导入 Recipe 的 PROBE_PROMPT 默认值；
- model_name.probe_max_tokens：导入 Recipe 的输出限制；
- legacy_compat 只在原字段确实启用且没有新发布 Recipe 时维持旧行为，并始终显示 needs_review；
- legacy_compat 不可直接编辑；用户通过“测试并转换”生成正常草稿，再按预览、测试、发布流程替换；
- 新发布 Recipe 永远覆盖 legacy_compat，学习结果和内置模板不能静默覆盖它；
- 用户也可以显式停用 legacy_compat 并恢复自动解析。

legacy_compat 不是 draft，而是迁移前已经执行行为的只读兼容版本。草稿永远不能参与 Resolver。迁移器必须把已知认证头和与上游 API Key 相同的值改为加密 Secret 引用；无法可靠判断是否含 Secret 的旧头进入 legacy_quarantined 且不可执行，要求人工审核后发布。

### 19.2 full_url_mode

旧 full_url_mode 的单 URL 无法无歧义映射五个端点。

迁移算法：

1. 读取该 Upstream 关联的 Route 协议集合；
2. 只有一个协议时，将旧 URL 复制到对应模型 Endpoint override，并标 needs_review；
3. 有零个或多个协议时保留 legacy_full_url 兼容记录，使已有 Route 暂时保持旧行为；
4. UI 禁止在未审核状态新增或改变绑定，并要求用户为每个 Endpoint 确认；
5. 审核完成后删除 legacy_full_url；
6. fragment 拒绝；
7. query 保留原始顺序；
8. 常见敏感 query 参数优先迁为加密 Secret 引用，无法识别的值遮罩并要求审核。

不得静默猜测一个旧完整 URL 同时代表 messages、responses 和 count_tokens。

### 19.3 Capability 和健康

旧 route_health 仅用于迁移后的历史展示。所有新 Reachability、Capability 和 RouteHealth 从 unknown 开始。

### 19.4 回滚

升级前备份整个 data。应用版本回滚时：

- 不允许旧二进制写入已升级且不兼容的 Schema；
- 需要使用升级前备份；
- Keyring 与数据库必须成对恢复；
- README 给出检查 Schema 和 Key ID 的命令。

## 24. 已知风险与明确取舍

1. 公益站在线状态不稳定

   在线矩阵不能作为永久真值；必须与同窗口原生请求比较，并以离线 fixture 锁定解析兼容。

2. 自动重试可能重复消费

   默认 Balanced 是可用性与成本的折中，不提供“绝对不重复”承诺。要求绝对保守时使用 Safe 或 attempts=1。

3. 严格透传不是 TLS 字节复制

   网关必须终止 TLS 并重新发起 HTTPS。保证对象是业务 body 和端到端头语义，不包括 TLS、HTTP 帧、头顺序和逐跳字段。

4. Lazy 恢复没有时间上界

   它以零合成请求换取恢复依赖真实流量。需要固定恢复时限时使用 Active。

5. synthetic completion 不能恢复内容

   它只能补齐协议结束，可能掩盖内容截断，因此默认禁用并强制审计。

6. 完整样本占用磁盘并包含隐私

   默认按数量和天数滚动，备份整个 data 目录时必须按敏感数据处理。

7. IP 证书有效期短

   公网模式依赖频繁自动续期。续期、reload 和到期告警是部署可用性的组成部分，不是可选运维项。

8. Master Key 与 SQLite 不能天然原子提交

   使用 pending Keyring、数据库事务、校验和启动恢复协议，禁止简单覆盖文件。

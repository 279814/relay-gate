# LLM 中转网关（代号 relay-gate）需求与设计

## 1. 背景与目标

多个公益性质的大模型中转站（New API / One API / sub2api 部署），可用性时好时坏。
当前用 ccswitch 手动切换或依赖它的「请求时逐个重试」路由，痛点是：

- 故障发现是**被动的**——等真实请求撞上去才知道站挂了，用户白等一次超时
- 切换粒度是**供应商级**的，不是「模型 × 供应商」级的（A 站的 opus-5 挂了但 gpt-5.6-sol 还活着）

本服务的目标：在服务器上常驻一个**主动探活 + 优先级路由**的透传网关。请求到达时，
目标渠道的健康状态**已经是已知的**，直接投递到当前存活且优先级最高的渠道。

三条主线：

1. **主动探活** —— 状态在请求到达前就已知（§4）
2. **严格透传** —— 除鉴权 key 与 model 外，一个字节都不改（§3.3）
3. **样本留档** —— 每次转发的入站请求、出站请求、上游响应全部存下来（§3.6），
   既用于验证第 2 条真的做到了，也用于让探活请求长得和真实请求一样

### 1.1 非目标（明确不做）

- 不做协议转换（Anthropic ↔ OpenAI 互转）。入站什么协议，出站就是什么协议。
- 不做计费、配额、多用户、团队管理。单人自用。
- 不做请求内容改写（除 model 与鉴权凭据）。不注入 system prompt、不裁剪 max_tokens、
  不过滤工具定义。

## 2. 核心概念与数据模型

原始设想是 `ModelName → 多个中转站`。该模型下同一物理站会在多个 ModelName 下重复出现
（配置重复、改 key 要改多处、站级探活重复执行 N 次）。改为三层：

```
Upstream (中转站)          1 ──── N  Route (绑定)  N ──── 1  ModelName (逻辑模型)
  name, base_url,                     priority,              name
  api_key(加密), protocols,           weight,
  proxy_url, enabled                  upstream_model,
                                      enabled
```

### 2.1 Upstream（中转站）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | int | 主键 |
| `name` | string | 显示名，如 `站A` |
| `base_url` | string | 站点根地址，如 `https://api.example.com`。**不含** `/v1/...` |
| `api_key` | string | 该站的密钥，AES-GCM 加密存储 |
| `auth_style` | enum | `auto` / `x-api-key` / `bearer`。`auto` = 按入站协议推断 |
| `full_url_mode` | bool | true 时 `base_url` 视为完整端点，不再拼接路径（应对非标准路径的站） |
| `proxy_url` | string? | 可选，出站 HTTP/SOCKS5 代理 |
| `enabled` | bool | 手动开关 |
| `l1_path` | string | L1 探活路径，默认 `/v1/models`，可设空表示只做 TCP/TLS |
| `probe_headers` | JSON? | 该站探活请求的附加/覆盖头。空 = 用全局模板（§3.6.4）。<br>给「按 UA 白名单拦截」这类站单独调指纹用 |

**为什么 base_url 不含路径**：入站 `/v1/messages` 要拼成上游 `/v1/messages`，
入站 `/v1/responses` 拼成上游 `/v1/responses`。同一个 Upstream 服务多种协议，
路径必须由入站请求决定。`full_url_mode` 是给非标准站的逃生舱。

### 2.2 ModelName（逻辑模型）

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | string | 客户端请求里写的 model，如 `claude-opus-5` |
| `protocol` | enum | `anthropic` / `openai-responses` / `openai-chat` |
| `match_mode` | enum | `exact`（默认）/ `prefix`（`claude-opus-5*`） |
| `is_fallback` | bool | 是否作为「未匹配任何 ModelName」时的兜底目标 |
| `probe_prompt` | string | 探活提问，默认 `1+1=?` |
| `probe_max_tokens` | int | 探活输出上限。anthropic/openai-chat 默认 1，openai-responses 默认 16 |
| 各类超时与间隔 | — | 见 §4.2 超时矩阵。全局默认 + ModelName 级覆盖 |

### 2.3 Route（ModelName × Upstream 的绑定）

| 字段 | 类型 | 说明 |
|---|---|---|
| `model_name_id` | int | 外键 |
| `upstream_id` | int | 外键 |
| `priority` | int | 1 最高。同优先级按 `weight` 加权随机 |
| `weight` | int | 默认 100 |
| `upstream_model` | string? | 模型映射。空 = 不映射，用 ModelName 原名 |
| `max_concurrency` | int | 0 = 不限。达到上限时溢出到下一优先级 |
| `enabled` | bool | 手动开关 |

Route 是探活与健康状态的**最小单位**。「A 站的 opus-5 挂了但 gpt-5.6-sol 还活着」
只有在 Route 粒度上才能表达。

### 2.4 RouteHealth（运行时状态，内存为准 + 异步落库）

分两层：**内存**是权威（选路只读它），**`route_health` 表**只是给 UI 看的快照。
两层的字段不完全相同 —— 纯调度用的中间量没有落库的价值。

| 字段 | 说明 | 内存 | 落库 |
|---|---|---|---|
| `state` | `unknown` / `alive` / `dead` | ✅ | ✅ |
| `consecutive_fail` | 连续失败次数 | ✅ | ✅ |
| `consecutive_ok` | 连续成功次数（用于恢复判定） | ✅ | ✅ |
| `last_ok_at` / `last_err_at` / `last_error` | 诊断信息 | ✅ | ✅ |
| `last_ttft_ms` | 最近一次首 token 延迟 | ✅ | ✅ |
| `next_l1_at` / `next_l2_at` | 下次探活的最早时刻（分层间隔算出） | ✅ | ❌ |
| `cooldown_until` | 429 冷却截止 | ✅ | ❌ |
| `last_real_ok_at` | 最近一次**真实请求**成功（piggyback 用，§4.6） | ✅ | ❌ |
| `last_reason` | 最近一次失败的类别，UI 据此区分「配置错」与「站挂了」 | ✅ | ❌ |

> **原稿的 `backoff_level` 已删除**：§4.4 明确不做指数退避（那会把恢复发现延迟拉到
> 分钟级，正好违背本项目的核心诉求）。dead 用固定短周期，唯一的温和保护是
> 「连续失败 > 60 次后只放宽 L2、L1 不变」，而那个判定直接读 `consecutive_fail`，
> 不需要单独存一个档位。
>
> **`next_probe_at` 拆成了 `next_l1_at` / `next_l2_at`**：两级探活的间隔不同
> （dead 时 L1 是 20s、L2 是 30s），一个字段存不下。它们也不落库 —— 重启后状态
> 一律回 `unknown`，而 `unknown` 的间隔是 0（立即探），存了也会被立刻覆盖。

**重启后所有 Route 置 `unknown`，且 `unknown` 视为可用（乐观）**。否则重启后无渠道
可用，服务直接不可用。同时立即触发一轮 L1 探活收敛状态。

> 实现上这是「不做什么」而非「做什么」：内存里没有该 Route 的记录时
> `State()` 直接返回 `unknown`，而 `unknown` 的探活间隔是 0，所以首个 tick
> 就会全量探。**绝不从 `route_health` 恢复 `state`** —— 一个崩溃前被判死的站
> 在重启后会继续被排除，而它可能早就好了。

## 3. 请求路由与透传

### 3.1 入站端点：路径 1:1 对应，不做任何转换

ccswitch 侧选什么协议，就打到本服务的对应路径，本服务再打到上游的**同名路径**。
路径不重写、协议不转换。

| ccswitch 协议 | 入站路径 | 出站路径 | ModelName.protocol |
|---|---|---|---|
| Anthropic Messages（原生） | `POST /v1/messages` | `{base_url}/v1/messages` | `anthropic` |
| OpenAI Responses API | `POST /v1/responses` | `{base_url}/v1/responses` | `openai-responses` |
| OpenAI Chat Completions | `POST /v1/chat/completions` | `{base_url}/v1/chat/completions` | `openai-chat` |

附加端点：

| 端点 | 出站 | 说明 |
|---|---|---|
| `POST /v1/messages/count_tokens` | 同名路径 | **Claude Code 每轮都调**，必须实现 |
| `GET /v1/models` | 本地应答，不转发 | 返回已配置的 ModelName 列表，供 ccswitch「获取模型」用 |
| `GET /healthz` | — | 存活探针 |

出站 URL 的构造规则：`base_url`（去尾斜杠）+ 入站的 `r.URL.Path` + 原样带上
`r.URL.RawQuery`。`full_url_mode` 时直接用 `base_url` 作为完整端点。

`count_tokens` 你未提及，但 Claude Code 启动时和每轮对话前都会调它做 token 预算，
不实现会报错。它复用同一套路由与映射，但**非流式、超时独立（默认 60s）、
失败不计入健康状态**（太轻量，失败信号噪声大）。

> **M4 实现方式：上游优先 + 本地兜底**（§10.3 的待决策已定）。先转发给选中的
> Route；上游回 4xx/5xx 或连不上时降级到本地粗算。M0 实测 4 个可用站只有
> 2 个支持，而同一 ModelName 下各 Route 支持情况不同，所以兜底不能按站开关
> （§5.1e）。降级时打 `X-Relay-Count-Tokens: estimated` 响应头。
> 估算的精度缺口与校准办法见 §10.3 末尾。

### 3.2 鉴权：入站与出站是两套凭据

**入站**：客户端用本服务发放的 `relay key`（前缀 `rk-`）。三个位置都要认，因为不同
协议的客户端习惯不同：

- `x-api-key: rk-xxx`（Anthropic 风格，Claude Code 走这个）
- `Authorization: Bearer rk-xxx`（OpenAI 风格）
- ccswitch 的 `ANTHROPIC_AUTH_TOKEN` 也会落到 `Authorization: Bearer`

**出站**：删除入站的所有鉴权头，按 `auth_style` 重新注入上游 key。

| auth_style | 注入 |
|---|---|
| `x-api-key` | `x-api-key: <上游key>` |
| `bearer` | `Authorization: Bearer <上游key>` |
| `auto` | anthropic 协议 → `x-api-key`；openai 协议 → `Bearer`。**同时**两个都发 |

`auto` 双发是刻意的：New API / One API 对 Anthropic 端点两种头都接受，sub2api 的行为
不一定。双发能覆盖绝大多数站，代价是极少数严格校验的站会拒绝——那种情况显式配
`auth_style` 即可。

### 3.3 改写范围：硬约束

#### 3.3.0 链路形态：两段独立的 TLS，网关是明文中间人

必须先说清链路，否则「保持一致」无从定义：

```
Claude Code ──HTTPS──▶ ccswitch ──HTTPS──▶ 【本网关】──HTTPS──▶ 公益站
                                            TLS 终结          新建 TLS
                                            ↓解密             ↑加密
                                        明文 HTTP 请求 ──改两处──▶
```

- HTTPS = TLS 只加密**传输**。网关持有自己的证书，是 TLS 的**终结点**，
  解密后拿到的是**完整的明文 HTTP 请求**：请求行、全部请求头、原始 body 字节。
- 网关到公益站是**另起一条** TLS 连接（用公益站的证书）。两段 TLS 互相独立，
  不存在「转发加密数据」这回事——中间必然经过明文。
- 所以「保持严格一致」的准确含义是：**解密后得到的明文 HTTP 请求，除下表两项外，
  逐字节重新发出**。TLS 本身不是需要保持的内容，它每段都会重新协商。

> 这一点纠正了早前的理解。之前隐含假设「内容是明文流过」，实际是
> 「解密 → 改两处 → 重新加密」。结论没变（只能改两项），但边界更清楚了：
> 我们**有能力**改任何东西，因此**约束是纪律问题，不是能力问题**，必须靠测试守住。

**允许改动的，只有两项：**

| 项 | 位置 | 规则 |
|---|---|---|
| 鉴权凭据 | **HTTP 头**（不在 body 里） | **必须**改为该 Route 所属 Upstream 配置的 key |
| `model` | body 顶层字段 | 配了 `upstream_model` 才改；未配则不动 |

**其余一切必须逐字节保持原样**：字段顺序、嵌套结构、数值字面量形式（`1.0` 不能变 `1`）、
字符串转义形式、Unicode 表示、空白与缩进、重复 key、未知字段、`null` 与缺失的区别。
响应方向**完全不碰**，字节流原样回传。

#### 3.3.1 三种协议的参数名（已核对）

| 协议 | 模型字段 | 鉴权头 | 备注 |
|---|---|---|---|
| Anthropic Messages | body 顶层 `"model"` | `x-api-key: <key>` | 另需透传 `anthropic-version` |
| OpenAI Responses | body 顶层 `"model"` | `Authorization: Bearer <key>` | — |
| OpenAI Chat Completions | body 顶层 `"model"` | `Authorization: Bearer <key>` | — |

三种协议的模型字段名一致，都是 body 顶层的 `model`；鉴权都在头里，**body 内不含 key**。
所以改写逻辑对三种协议是同一套，不需要分支。

> 少数中转站也接受 `api-key` 头或 `?key=` 查询参数。设计上按 `auth_style`
> 配置（§3.2），默认 `auto`。

#### 3.3.2 model 的字节级替换

不能用「反序列化 → 改 → 重新序列化」。`encoding/json` 的 round-trip 会改变 key 顺序、
把 `1.0` 写成 `1`、重写 Unicode 转义、丢弃重复 key、丢弃未知字段（用 struct 时）。
任何一条都可能改变上游行为。

做法：扫描定位顶层 `"model"` 的**值区间** `[valStart, valEnd)`，做字节切片拼接：

```go
// 只有这一段字节被替换，前后全部原样
out := make([]byte, 0, len(body)+16)
out = append(out, body[:valStart]...)
out = append(out, strconv.AppendQuote(nil, upstreamModel)...)
out = append(out, body[valEnd:]...)
```

定位必须用**流式 token 扫描**（`json.Decoder` + `Token()` + `InputOffset()`），
只认**深度 0 的** `model` 键——否则会误改嵌套在 `tools`、`metadata`、`messages` 里
同名字段的值。

若 `upstream_model` 为空：**body 的 `[]byte` 直接透传，一个字节都不读改**。
这是推荐配置，UI 上会标注。

#### 3.3.3 请求头处理：默认全量转发，删除项是**穷举的白名单**

目标站可能只接受「看起来像 Claude Code」的请求（M0 已实测到按 `user-agent` 白名单
拦截的站），所以请求头不是可有可无的附属信息，而是**能否被放行的关键**。
规则因此是**黑名单**而非白名单：**除下表穷举的几项外，入站有什么头就原样发什么头**，
不增、不删、不改值、不规范化值、不补默认值。

**唯一允许删除/替换的头（穷举，代码里是常量表）：**

| 头 | 处置 | 为什么必须动 |
|---|---|---|
| `x-api-key`、`Authorization`、`api-key` | **替换**为上游 key | 业务要求（§3.3.1）。入站是 relay key，对上游无效 |
| `Host` | 重写为上游域名 | HTTP 语义要求；不改的话上游 nginx 按错误的 vhost 路由，必 404 |
| `Content-Length` | 按新 body 长度重算 | 改了 `model` 后长度可能变；不改会截断 body 或挂起 |
| `Connection`、`Keep-Alive`、`Transfer-Encoding`、`TE`、`Trailer`、`Upgrade`、`Proxy-Authorization`、`Proxy-Authenticate` | 删除 | RFC 7230 §6.1 规定的 hop-by-hop 头，**禁止**跨连接转发。转发会导致协议错误 |
| `Connection` 里列出的自定义头 | 删除 | 同上，RFC 要求逐跳清理 |

**其余一律原样转发**。以下这些丢了会直接功能降级或被拒，M0 已验证其中两项是硬要求：

| 头 | 后果 |
|---|---|
| `user-agent` | **M0 实测**：有站按 `claude-cli/*` 前缀白名单拦截，改掉即 401 |
| `anthropic-beta` | 特性开关集合（交错思考、上下文管理、工具用法等）。丢了会降级甚至 400 |
| `anthropic-version` | Anthropic 协议必需，缺失直接 400 |
| `x-stainless-*` | SDK 指纹（lang / os / arch / retry-count），部分站据此识别客户端 |
| `x-app`、`anthropic-dangerous-direct-browser-access` | Claude Code 的固有特征头 |
| `accept`、`content-type`、`accept-encoding` | 内容协商，见 §3.3.4 |
| `openai-beta`、`x-request-id` | OpenAI 侧特性开关与链路追踪 |

注意 URL 上的 **query string 也必须原样带过去**：真实 Claude Code 打的是
`POST /v1/messages?beta=true`，不是裸路径，丢掉 `?beta=true` 会改变上游行为。

##### 已知的保真度残缺（诚实交代，非借口）

用 Go 标准库做代理，有两处**做不到逐字节一致**，属于协议层等价但不是字节层等价：

1. **头名大小写被规范化**。`net/http` 收到请求时即把头名转成 MIME 规范形式
   （`x-api-key` → `X-Api-Key`），原始大小写在服务端**不可恢复**。
2. **头的顺序丢失**。`http.Header` 是 `map`，写出时按 key 排序，不保留入站顺序。

判断：**风险可接受，且不打算为此重写 HTTP 栈**，依据有三条——

- HTTP/1.1 规范明确头名**大小写不敏感**；HTTP/2 更是**强制全小写**。
  真实 Claude Code 直连 Anthropic 走的就是 HTTP/2，本来就不存在「原始大小写」。
  任何按大小写做指纹的站，对真实 Claude Code 也会一并拒绝，自相矛盾。
- 公益站是 New API / One API / sub2api（Go / Node），从 map 里读头，与顺序无关。
- **M0 的经验证据**：探测脚本用的是 `curl`，其头顺序、大小写、TLS ClientHello（JA3）
  与 Node 全然不同，而各站照常放行。说明这些站**不做 TLS 指纹或头序指纹校验**，
  只做 `user-agent` 这类显式字段的校验——而显式字段我们是完整保留的。

若日后真撞上按头序/JA3 拦截的站，逃生舱是给该 Upstream 单独启用「裸转发模式」
（自己拼 HTTP/1.1 报文 + `utls` 伪装指纹）。**现在不做**，因为没有证据表明需要，
而 §3.6 的样本记录正是为了在真撞上时能立刻拿到证据。

#### 3.3.4 不要动压缩

设 `Transport.DisableCompression = true`，原样转发客户端的 `Accept-Encoding`，
响应体字节流原样回传。零解压、零重压，`Content-Encoding` 也无需改。
（若让 Go 自动协商 gzip，它会解压响应体，就必须删 `Content-Encoding`，
等于改动了响应——违反约束。）

#### 3.3.5 流式必须逐块 flush

每次从上游读到数据就立刻写出并 `Flush()`。任何缓冲都会破坏 SSE 语义，
表现为「长时间无输出后一次性刷出」。

**实现选择：手写转发循环，不用 `httputil.ReverseProxy`**（M2 已落地，
原稿曾定 ReverseProxy + `FlushInterval = -1`，实现时改了）。

理由是 §4.2 的三段超时**必须在读 body 的循环里切换 deadline**：首字节之前用
「首 Token 超时」（默认 20 分钟），首字节之后换成「流内静默间隔」（10 分钟）。
`ReverseProxy` 内部是 `io.Copy`，拿不到这个控制点 —— 它只能给一个统一的
`ResponseHeaderTimeout`，而那管的是响应头，长思考时响应头早就回来了，
卡住的是 body 的第一个 chunk。

代价是 hop-by-hop 头、`Host`、`Content-Length` 要自己处理（`PrepareOutboundHeaders`
已穷举，见 §3.3.3），换来的是三段超时能真正独立。

> M2 实测踩到的坑：空闲看门狗若用「每轮迭代起一个 goroutine + `context.WithDeadline`」，
> 主循环读成功时会同时 `close(done)` 和 cancel `readCtx`，`select` 两个 case 同时
> 就绪时 Go **随机**挑一个 —— 挑到 ctx 分支就把健康的流关掉，每个 chunk 约 50%
> 概率。正确做法是**单个可重置的 `time.AfterFunc`**。这个 bug 靠功能测试抓不到
> （测试里 chunk 之间没有时间间隔），是读代码发现的。

#### 3.3.6 保真度的自动化验证

M2 必须全绿，实际分布在三个测试文件里：

- `rewrite_test.go`（字节保真）
  - 不映射时：`out == in`（`bytes.Equal`，非语义等价）
  - 映射时：把 out 的 model 值换回原值后 `out == in`

    `"tools":[{"input_schema":{"properties":{"model":{}}}}]` 时只改顶层
  - 保留：`1.0`、`1e5`、`é`、`"a":1,"a":2`、超长 base64 图片、

### 3.4 选路算法

```
1. 取入站 model 值 M
2. 精确匹配 ModelName.name == M
   否则 prefix 匹配（按 name 长度降序，最长优先）
   否则取 is_fallback == true 的 ModelName
   否则 404 {"type":"error","error":{"type":"not_found_error",...}}
3. 校验 ModelName.protocol 与入站端点协议一致，不一致 400
4. 取该 ModelName 下 enabled 且 state != dead 的 Route
   （unknown 视为可用）
5. 按 priority 升序分桶。取第一个非空桶
6. 桶内：排除已达 max_concurrency 的，按 weight 加权随机
7. 全桶都满 → 降到下一优先级桶
8. 无任何可用 Route → 503，且响应头带 X-Relay-Reason 说明原因
```

### 3.5 请求内失败识别与重试

真实请求的失败识别与探活共用同一套判定逻辑（§4.3），差别只在超时值和后续动作。

- 仅在**尚未向客户端写出任何字节**时才能重试（流已开始写就无法回滚）
- 可重试：连接失败、TLS 失败、5xx、429、首 token 超时、200 但流内立刻 error
- 不重试：4xx（除 429）、已开始流式输出后的中断
- 最多 2 次，按 priority 顺序换 Route，不重复同一个
- **任何失败都立刻回写健康状态并触发该 Route 的即时探活**（§4.5），
  这是「尽快发现故障」的主路径——比定时探活快得多

### 3.6 请求/响应样本记录

#### 3.6.1 目的

把每次转发的**三份内容 + 时间戳**完整留档：

1. 收到的**原始入站请求**（Claude Code 经 ccswitch 发来的）
2. **实际发往公益站的请求**（即上面那份，改了 key 与 model 之后）
3. 公益站的**返回内容**

直接价值有两个：

- **验证「只改了两处」**。把 ① 和 ② 逐字段对比，任何计划外的差异立刻可见——
  这是 §3.3 那堆硬约束在**生产环境**的持续验证，比单测更有说服力。
- **给探活请求当模板**。M0 已实测到「按 `user-agent` 白名单拦截」的站：探活请求若
  长得不像 Claude Code，会把活站判成死站。样本让「真实请求到底长什么样」变成
  可查的事实，而不是猜测。这正是你说的「之后根据这些信息调整探活的请求头请求体」。

#### 3.6.2 数据模型（`sample` 表）

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `ts_recv` / `ts_sent` / `ts_first_byte` / `ts_done` | 四个时间戳（UTC 毫秒）。差值即排队、TTFT、总时长 |
| `endpoint` | `/v1/messages` / `/v1/responses` / `/v1/chat/completions` |
| `model_in` / `model_out` | 入站 model 值 / 映射后的值（未映射时相同） |
| `model_name_id` / `route_id` / `upstream_id` | 选路结果，可回溯「为什么走了这个站」 |
| `in_method` / `in_path` / `in_query` | 入站请求行（`?beta=true` 在这里） |
| `in_headers` / `out_headers` / `resp_headers` | 三组头，JSON 对象，**key 已脱敏** |
| `in_body` / `out_body` | 入站与出站的**原始 body 字节**（BLOB，非重新序列化） |
| `resp_status` / `resp_body` | 上游状态码与响应体（SSE 全文，可截断） |
| `outcome` | `ok` / `upstream_error` / `timeout` / `fake_alive` / `client_abort` |
| `error` | 失败描述，与 §4.3 的分类一致 |
| `truncated` | 位标记：哪几个字段被截断了 |
| `pinned` | 手动置顶，不被滚动清理 |

#### 3.6.3 五条硬约束

**a) 绝不影响转发路径。** 记录是**旁路**，不是管线的一环：

- 采集用 tee（边转发边攒副本），**不改变任何字节，不改变 flush 时序**
- 写库走**有界 channel + 后台单 writer**，代理协程只做一次非阻塞投递
- channel 满了就**丢弃该样本并计数**，计数暴露在 UI。
  宁可丢样本，也绝不让「记日志」拖慢或拖垮转发——这是主次关系，不能倒置

**b) key 必须脱敏。** 入站 relay key 与出站上游 key 在**落库前**替换为
`sk-abcd…wxyz`（前 4 后 4）。这是硬要求：不脱敏的话，样本库就是一份明文 key 库，
而它比配置表更容易被整体导出。

脱敏不损害用途——调探活时需要知道的是「key 放在**哪个头**、什么**格式**」，
而头名与 `Bearer ` 前缀都完整保留了，值本身由配置提供。

**c) 体积靠条数封顶，单条不截断。** Claude Code 的单次请求常有 50KB–1MB
（完整对话 + 工具定义 + 可能的图片），SSE 响应可达数 MB：

| 项 | 默认上限 | 说明 |
|---|---|---|
| `in_body` / `out_body` | **无**（`0` = 不限） | 完整留档，不截断 |
| `resp_body` | **无**（`0` = 不限） | 同上，SSE 全文 |
| 保留条数 | 最近 **300** 条 | 与天数取**先到者** |
| 保留天数 | 7 天 | 同上 |

`pinned` 的样本不参与清理。全部可配。

> **为什么把三个字节上限都改成不限**（原稿是 256KB / 头 64KB + 尾 8KB）：
> §3.6.1 给样本定的头号用途是「把 ① 入站请求与 ② 出站请求逐字段对比，
> 验证只改了两处」。而**截断过的样本没法做这件事** —— 差异恰好落在被砍掉
> 的那段时，比对结果是「看不出来」，而这与「没有差异」不是一回事。
> 一份 256KB 上限的样本能证明的东西，比它看起来的少得多。
>
> 代价是**内存**而非磁盘，且这一点必须说清：`resp_body` 的采集是边转发边攒
> （§3.6.3a 的 tee），不限长意味着每个在途请求都会在 RAM 里攒一份完整响应，
> 而大小**由上游决定**。磁盘侧则由「300 条 / 7 天」兜住，条数从 500 降到 300
> 正是为了补偿单条变大：按 Claude Code 的典型请求算，300 条的量级与原先
> 500 条封顶时相当。
>
> 换句话说，封顶的维度从「每条多大」换成了「留多少条」。前者会静默损坏
> 单条样本的可用性，后者只是让更早的样本更早被清掉 —— 而后者是可预期的、
> 且 `pinned` 提供了精确的逃生舱。真撞上内存问题，把三个上限调回非零即可，
> 有界模式的代码路径**一行没删**。

**d) 样本库含全部对话原文，按敏感数据对待。** 存在主 SQLite 文件里，文件权限 0600，
`data/` 已在 `.gitignore`。UI 提供「一键清空」。默认**开启**（这是你要的功能），可关。

**e) 响应方向仍然零改动。** 采集只读不写，§3.3 的「响应字节流原样回传」不受影响。

#### 3.6.4 用途闭环：从样本反哺探活

样本不只是「存着看」，要能直接变成探活配置，否则这个功能只完成了一半：

- 样本详情页提供 **「以此为探活模板」**：抽取该请求的**头集合**（脱敏后的 key 位置
  会被替换成占位符），写入探活请求头模板
- 探活头模板分两级：**全局默认** + **Upstream 级覆盖**。
  全局默认值取自真实 Claude Code 的指纹（`user-agent: claude-cli/*`、
  `anthropic-beta` 开关集、`x-stainless-*` 等，M0 脚本里已固化同一套）
- 样本可**导出为 `curl` 命令或 `.http` 文件**，便于脱离本服务手工复现问题

> 这条闭环解决的是一个已被 M0 证实的真实问题：探活请求与真实请求「不像」，
> 会导致活站被判死。有了样本，「像不像」是可比对的，不再靠猜。

### 3.7 请求日志（`request_log` 表，M6）

#### 3.7.1 它回答的问题

样本回答「发出去的到底是哪些字节」；请求日志回答**「这次请求经历了什么」**——
试了几个站、每个站怎么失败的、最后有没有救回来。

这是 §3.5 的重试**唯一的效果度量**。没有它，「换站重试」值不值得就只能靠感觉，
而它的代价是实打实的：每次重试都在别人的站上真花一次额度。

**每次尝试一行**，包括被丢弃的那些。只记最终那次的话，「前两个站为什么失败」
就永远查不到 —— 而那正是记日志的全部理由。

#### 3.7.2 为什么不并进 `sample` 表

三条，每一条单独都够：

1. **`sample` 只记最终那次尝试**。它的一行代表「客户端的一次请求」，
   把 N 次尝试记成 N 行会让样本浏览器显示成 N 个客户端请求，比不记更误导。
2. **`sample` 可以关，且会丢**（`sample_enabled`、队列满即丢、按 300 条滚动）。
   从一个会丢、可关、会截断的数据源算成功率，得到的是一个**会骗人的数字**。
3. **体量差三个数量级**。样本一条可达几 MB（§3.6.3c 起不封顶），日志一行几百字节。
   共用一个 `keep_count` 会让「多留点日志」的代价变成磁盘翻 GB，于是没人敢调大它。

所以是两套独立的旋钮：`request_log_enabled` / `keep_count`(5000) /
`keep_days`(7) / `queue_size`(512)。**样本关掉时日志照记** —— 那恰恰是
「样本太占地方所以关掉、只留统计」的场景，也正是最需要日志的时候。

#### 3.7.3 数据模型

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `req_id` | 把同一次客户端请求的多次尝试串起来。随机 80 bit，**不查库**——它在转发路径上生成 |
| `attempt` / `attempts` | 第几次 / 总共几次。后者冗余存在每一行，让列表页不必先拉整组才能显示「试了 3 次」 |
| `ts_recv` / `ts_sent` / `ts_first_byte` / `ts_done` | 四个时间戳，与样本同义 |
| `endpoint` / `model_in` / `model_out` | 端点与映射前后的模型名 |
| `model_name_id` / `route_id` / `upstream_id` | 选路结果 |
| `upstream_name` | **冗余**存一份：站被删掉后，日志仍要能说清当时走的是哪个站 |
| `resp_status` / `ttft_ms` / `bytes_written` | 上游状态码、首 Token 延迟、写给客户端的字节数 |
| `outcome` | 与 §3.6.2 同一套分类 |
| `retried` | 这次尝试**被丢弃并换了站**。见下 |
| `half_open` | 半开放行的试探（§4.4c） |
| `error` | 失败描述，**已脱敏** |

**刻意不存任何 body 与头**：那是样本的职责。两边各存一份只会让磁盘翻倍，
还多一处需要脱敏的地方 —— 而漏一处就是明文 key 落库。两张表靠 `req_id` 关联
（方向是 `sample` 存 `req_id`，因为样本 id 由后台 writer 落库时才分配，
而日志在转发路径上就要写出去）。

#### 3.7.4 `retried` 不等于「失败」

最后一次尝试失败时同样是失败，但它**没有被重试**（次数用尽、无站可换、
或本就不可重试如 4xx）。混为一谈就算不出「重试救回来了多少」。

`half_open` 同理要单独打标：它的失败预期就高，混进成功率会拉低整体数字，
让人误以为站的质量在下降 —— 而实际那是对已知 dead 的站做的试探。

#### 3.7.5 统计口径

`/admin/api/retry-stats` 汇总五个数，默认最近 24 小时：

| 指标 | 含义 |
|---|---|
| `requests` | 客户端请求数（按 `req_id` 去重） |
| `attempts` | 总尝试数。`attempts - requests` 就是重试的额外开销 |
| `retried` | **发生过**重试的请求数（组内 `MAX(attempts) > 1`） |
| `rescued_by_retry` | 首次失败但最终成功 —— 重试真正救回来的那些 |
| `failed_after_retry` | 重试过但最终仍失败。这个数偏高说明该改配置而不是再多试一次 |

**硬约束：`rescued_by_retry + failed_after_retry == retried`。** 用一条 CTE
一次算完五个数，而不是分五条查询 —— 后者可能来自不同时刻的快照，于是出现
「救回来的比重试过的还多」这种不自洽的展示，而那会让人立刻不再相信整个界面。

**`retried` 的判据是组内的 `MAX(attempts)`，不是组内行数。** 两者在日志
完整时相等，但队列满丢行时不等 —— 而那正是最需要这个统计的时候。只落库了
最后一行的三连重试，数行数会得到「1 次尝试、没重试过」，可那一行明明记着
`attempts=3`。用行数就等于**在高负载时段系统性低估重试的效果**，而度量那个
效果是这张表存在的全部理由。`attempts` 列在每行冗余存一份（§3.7.3）正是
为这种情形准备的。

`attempts` 这个数**仍然**按实际落库的行算，它偏低无解也不该修：它问的是
「留下了多少行」，不是「发生过多少次」。丢弃计数在 `/admin/api/runtime`
与日志页顶部都有出口。

默认 24 小时而不是全部历史：全量那个数字会被开服头几天的配置错误永久污染，
而一个永远不会变好的比例，看它做不出任何决定。

#### 3.7.6 清理按 `req_id` 整组

按行截会把一次三连重试切成「第 2、3 次尝试」，详情页少了第 1 次 ——
看起来像数据坏了，而第 1 次恰恰是「最初为什么失败」的答案。

日志**没有** `pinned`：单行日志离开它那一组就没什么意义，而按组置顶会让
「保留 N 条」变成一个无法预估的数字。要留证据就置顶样本，两者靠 `req_id`
关联得上。

### 4.1 两级探测

**L1 传输层（零 token）**
TCP + TLS 握手，然后 `GET {base_url}{l1_path}`（默认 `/v1/models`）带上游 key。
判定：连接失败 / TLS 失败 / 5xx / 401 / 403 → **整站 dead**，
该 Upstream 下所有 Route 一并标 dead，跳过 L2。

L1 是 Upstream 粒度的，N 个 Route 共享一次结果——这是分两级的主要收益。

> L1 返回 404/405 视为**通过**：很多站不提供 `/v1/models` 但 `/v1/messages` 正常。
> 只有 401/403/5xx/网络层失败才算失败。

**L2 模型层（消耗 token）**
用 Route 的真实配置发一次最小请求，路径与该 ModelName 的协议一致：

```json
// anthropic → POST {base_url}/v1/messages
{"model":"<上游模型名>","max_tokens":1,"stream":true,
 "messages":[{"role":"user","content":"1+1=?"}]}

// openai-responses → POST {base_url}/v1/responses
{"model":"<上游模型名>","max_output_tokens":16,"stream":true,"input":"1+1=?"}

// openai-chat → POST {base_url}/v1/chat/completions
{"model":"<上游模型名>","max_tokens":1,"stream":true,
 "messages":[{"role":"user","content":"1+1=?"}]}
```

**必须 `stream:true`** —— 否则无法测首 token 时间，非流式只能测总时长。

读到首个有效事件后立即 `cancel()` + `Body.Close()` 主动断流，不再消耗上游 token。

### 4.2 超时矩阵（按公益站高延迟重设，已用 M0 实测校准）

公益站延迟高，超时值整体放宽。三类场景分开配，**真实请求给足 20 分钟**。

| 场景 | 连接建立 | 首 Token | 流内静默间隔 | 总时长上限 |
|---|---|---|---|---|
| **真实请求**（`/v1/messages` 等） | 30s | **20min（1200s），下限 5min** | 10min（600s） | 30min |
| **L2 探活** | 30s | 120s | — | 150s |
| **L1 探活** | 15s | — | — | 25s |
| **count_tokens** | 20s | — | — | 60s |

#### 首 Token 超时的硬下限：5 分钟

真实请求的首 Token 超时**可以调，但不允许低于 300s**。低于该值的配置一律拒绝保存
（API 返回 400，UI 输入框限制最小值），而不是静默取整——静默修正会让人误以为改生效了。

理由是这个参数**调小的代价远大于调大的代价**，不对称：

- 调大的代价：一个真死的站会多占住一个连接，最多拖 20 分钟。但有探活在旁路
  独立判死（L2 只等 120s），死站会被标 dead 并从选路中剔除，**不影响后续请求**。
- 调小的代价：正常的长思考被拦腰砍断，客户端拿到的是「上游超时」，
  而这个站其实是好的。更糟的是它会被计入失败 → 标 dead → 好站被踢出池子。

**M0 实测校准**（详见 `docs/02-上游能力矩阵.md`）：

| 场景 | 实测首 Token |
|---|---|
| `1+1=?` 简单请求 | 3.3s / 3.3s / 3.5s / 5.5s |
| 长思考题（`max_tokens=64`） | 22.4s / 28.6s / 31.8s / 32.0s |

最坏实测 32s。5 分钟 ≈ 实测最坏值的 **9 倍**，20 分钟 ≈ **37 倍**。

> 注意实测值是**乐观下界**：探测用的是空上下文 + `max_tokens=64`，没开扩展思考。
> 真实场景是「几十 KB 上下文 + 工具定义 + Opus 5 高 effort + 公益站排队」，
> 首 Token 到分钟级完全可能。所以实测 32s **不能**用来论证「超时设 1 分钟就够」——
> 它只证明「站正常时很快」，没有覆盖排队与长思考的尾部。5 分钟下限就是防这个误判。

其余要点：

- 三段超时必须独立。只设一个总超时会杀掉 Opus 5 max effort 的正常长思考
- **流内静默 10min**：首 token 出来之后，两个 chunk 之间超过 10 分钟才判死。
  长思考过程中 Claude 会持续吐 `thinking` delta，静默不会真的到 10 分钟
- L2 探活 120s 而非 20min：`1+1=?` 实测 3–6s，给 120s 已是 20 倍余量，
  容忍排队但不让死站占住 20 分钟探测窗口。**探活与真实请求的超时必须分开**，
  这正是「快速判死」与「容忍长思考」能同时成立的原因
- 全部可在 UI 调整，上表是默认值；仅首 Token 超时有 300s 硬下限


### 4.3 失败识别：分三类，动作不同

不是所有失败都等价。按上游返回的**具体信息**分类：

| 类别 | 触发条件 | 动作 |
|---|---|---|
| **致命**（立即 dead） | 401 / 403；400 且响应含 `model_not_found` / `model not found` / `invalid model` / `no such model`；404 且 body 指向模型不存在 | 立即置 dead，UI 标「配置/鉴权错误」而非「服务不可用」 |
| **服务不可用**（累计 dead） | 连接失败、TLS 失败、5xx、502/503/504、首 Token 超时、200 但流内 `event: error`、200 但无任何有效 delta（假活） | 连续 2 次 → dead |
| **限流**（冷却，不 dead） | 429；或 body 含 `rate_limit` / `too many requests` / `overloaded` | 冷却 `retry-after` 秒（无该头则 60s），冷却期内不选它；**不计入失败计数** |

「200 但流内报错」和「200 但空内容」是公益站最常见的假活，必须靠解析 SSE 内容识别，
只看 HTTP 状态码会漏判。

### 4.4 死亡渠道的快速恢复（你的重点要求）

三条机制并行，让恢复尽快被发现：

**a) 激进的固定短周期探活**
dead 状态的 Route 用**固定 20 秒** L1 + **30 秒** L2 重探（可配），不做长指数退避。
最坏情况 30 秒发现恢复。L1 零成本，跑 20s 无压力；L2 的 `1+1=?` 约 21 token，
单个死站每分钟 2 次 ≈ 60k token/月，可接受。

> 我原稿写的是「30s→10m 指数退避」，这与你的要求冲突，已改。
> 保留一个**温和的**上限保护：连续失败超过 60 次（约 30 分钟没恢复）后
> L2 间隔放宽到 2 分钟，L1 仍保持 20 秒。因为 L1 一旦转通，立刻触发 L2 —— 
> 站真恢复时 L1 会先于 L2 察觉，所以放宽 L2 不影响发现速度。

**b) L1 转通即触发 L2（事件驱动，不等周期）**
整站 dead 时只跑 L1（零成本）。L1 一旦从失败转为成功，**立即**对该 Upstream 下
所有 dead 的 Route 触发一轮 L2。站级恢复的发现延迟 ≈ L1 周期（20s）。

**c) 半开放行：dead 也允许少量真实流量试探**
若某 ModelName 下**全部 Route 都 dead**，不直接返回 503，而是选优先级最高的
dead Route 放行一次（半开）。成功则立即转 `unknown`（可用）。
避免「全挂 → 只能干等探活」的窗口。

**恢复判定：**
- 首次 L2 成功 → `unknown`（**乐观，立即可承接真实流量**）
- 连续 2 次成功 → `alive`
- `unknown` 期间真实请求成功 → 直接升 `alive`

单次成功就放行是刻意的：宁可偶尔撞一次失败（有重试兜底），也不要让恢复的站
空等第二次探活。

### 4.5 即时探活（事件驱动）

以下事件立即触发对应 Route 的探活，不等定时周期：

| 事件 | 触发 |
|---|---|
| 真实请求失败 | 该 Route 立即 L1 + L2 |
| L1 从失败转成功 | 该 Upstream 下所有 dead Route 的 L2 |
| 配置变更（新增/改 key/改映射） | 该 Route 立即 L1 + L2 |
| UI 手动点「测试」 | 立即，结果直接展示 |
| 服务从暂停恢复 | 全量 L1，再对 unknown 的跑 L2 |

### 4.6 调度策略：分层 + Piggyback

| 状态 | L1 间隔 | L2 间隔 |
|---|---|---|
| `alive` | 60s | 300s（可配；有真实流量时被 piggyback 跳过） |
| `unknown` | 立即 | 立即 |
| `dead` | **20s** | **30s**（连续失败 >60 次后放宽到 120s，L1 不变） |

**Piggyback**：真实请求成功等价于一次 L2 探活。记录 `last_real_success_at`，
若 `now - last_real_success_at < L2 间隔` 则跳过本周期 L2。
活跃使用时 alive 渠道的 L2 次数接近 0。

**并发控制**：全局 L2 并发上限默认 3；同一 Upstream 的 L2 串行，避免触发站点限流。

### 4.7 可配置项

全局默认 + ModelName 级覆盖，UI 可改：
`probe_prompt`、`probe_max_tokens`、§4.2 全部超时值、
`l1_interval_alive/dead`、`l2_interval_alive/dead`、`fail_threshold`、
`ok_threshold`、`cooldown_s`、`global_l2_concurrency`、`piggyback_enabled`、
`half_open_enabled`。

**探活请求指纹**（§3.6.4）：`probe_headers` 全局模板 + Upstream 级覆盖。
默认模板取自真实 Claude Code 的头集合。改这个的正确方式是从样本一键导入，
而不是手写——手写就又回到了猜。

**样本记录**（§3.6.3）：`sample_enabled`（默认开）、`sample_max_body_bytes`（**0 = 不限**）、
`sample_resp_head_bytes`（**0**）、`sample_resp_tail_bytes`（**0**）、
`sample_keep_count`（**300**）、`sample_keep_days`（7）、`sample_queue_size`（256）。

> 三个字节上限的 `0` 是**不限**，不是「不留」。这三项与其余配置项的
> 「0 视为非法」相反，所以 `Validate` 对它们只校验非负 —— 详见 §3.6.3c。

**有下限校验的项**：真实请求首 Token 超时 ≥ 300s（§4.2），低于则 API 400 拒绝。

另有**全局探活总开关**与**单 Route 手动探活按钮**。

### 4.8 服务一键启停

前端提供一个总开关，控制服务的「运行 / 暂停」。目的是不用时不浪费探活额度。

| 状态 | 探活 | 代理端点 | 管理端点 |
|---|---|---|---|
| **running** | 正常 | 正常 | 正常 |
| **paused** | **全停** | 返回 503 + `X-Relay-State: paused` | 正常（能再点开） |

实现要点：

- 状态持久化到 SQLite，**重启后保持**——暂停时重启不会自动跑起来
- 暂停时停止所有探活定时器，取消进行中的探活请求
- **暂停不杀已建立的流式连接**，让进行中的对话正常收完（否则会丢一次回复）。
  只拒绝新请求
- 恢复时：所有 Route 置 `unknown`（乐观可用），立即全量 L1，再对需要的跑 L2
- 恢复后有个**短暖机窗口**（约 15s），期间即便 L1/L2 未跑完也按 `unknown` 放行，
  避免「刚点开就 503」
- 管理端点始终可用，否则暂停后无法通过 UI 恢复
- 提供 `POST /admin/api/state {"state":"running"|"paused"}`，便于脚本化

## 5. 对原始需求的修正、补充与待确认项

这一节是审视原始设想后列出的问题清单。已在上文落地的写「已处理」，需要你决策的写「待确认」。

### 5.1 需要修正的地方

**a) 「一个 ModelName 配多个中转站」的数据模型会导致配置重复** — 已处理
拆成 Upstream / Route 两层（§2）。一个站配一次，通过 Route 绑到多个 ModelName。

**b) 「先检查中转站是否存活，再发模型请求」——站活着不等于模型活着** — 已处理
公益站最常见的故障恰恰是「站在、某个模型的上游额度耗尽」。所以 L1 只能用来**快速否决**
（省 token），不能用来肯定。判定存活必须靠 L2。这一点原需求的表述隐含了「L1 通过即可用」，
实际不成立。

**c) 「超时 90 秒」需按场景拆分** — 已处理（§4.2）
你后续明确了真实请求首 Token 要 20 分钟。已拆成三套：真实请求 20min、
L2 探活 120s、L1 探活 25s。同一个值不能兼顾「容忍长思考」与「快速判死」。
另按你的要求加了 **300s 硬下限**：低于此值的配置直接拒绝保存，不静默取整。

**d) 「请求内容严格一致」与「改 model」的边界** — 已处理（§3.3）
改动范围收紧为两项：鉴权头（必改）+ body 顶层 `model`（配了映射才改）。
JSON round-trip 必然改字节，故用字节级切片替换；不映射时 body 完全不读改。
响应方向完全不碰。§3.3.6 给出了字节级保真的自动化测试用例。

**e) `/v1/messages/count_tokens` 缺失会导致 Claude Code 异常** — 已处理（§3.1）
M0 实测：**4 个可用站里只有 2 个支持**，另 2 个返回 404。
所以本地兜底实现**不是可选项，是必需项**，且不能按站开关——同一个 ModelName 下
不同 Route 支持情况不同，只能统一本地兜底。

**f) 端点对应关系** — 已按你的更正重写（§3.1）
三种协议都是入站路径 = 出站路径，1:1 直通，不做协议转换。

**g) 死亡渠道的恢复速度** — 已按你的要求改（§4.4）
原稿的指数退避（30s→10m）与「尽快发现恢复」冲突，已改为固定短周期
（L1 20s / L2 30s）+ L1 转通即触发 L2 + 半开放行三条机制并行。

**h) 对 HTTPS 链路的理解错误** — 已修正（§3.3.0）
早前隐含假设「请求内容明文流过网关」。实际是网关**终结** TLS、拿到完整明文、
再另起一条 TLS 发往上游。结论不变（仍只改两项），但边界更清楚：改动能力是完整的，
约束靠纪律与测试守住。同时据此把 §3.3.3 的头处理从「列几个要保留的」改为
**「删除项穷举、其余全量转发」**，并诚实交代了 Go 标准库在头名大小写与头序上
做不到字节级保真（附三条证据说明风险可接受）。

**i) 探活请求「不像 Claude Code」会把活站判成死站** — 已处理（§3.6.4）
M0 实测到按 `user-agent` 前缀白名单拦截的站（非 `claude-cli/*` 一律 401），
以及强制要求 `anthropic-beta: context-1m-2025-08-07` 的站（不带就 400）。
探活请求头因此不能随手写，需要以真实请求为模板 —— 这正是样本记录功能（§3.6）
要解决的问题，两者是同一件事的两面。

### 5.2 原始需求未覆盖、但会实际踩到的边界

**a) 上游返回 429（限流）不等于 dead** — 已处理（§4.3）
冷却而非标死，尊重 `retry-after`，不计入失败计数。

**b) 流式响应中途断流**
上游返回 200 吐了几个 token 后断开。此时无法重试（已写出字节），把断流原样传给客户端，
但计入失败并触发即时探活。Claude Code 会自己重试。

**c) 上游「模型不存在」要单独识别** — 已处理（§4.3 致命类）
配错映射时上游返回 400 `model not found`。UI 要显示「配置错误」而非「服务不可用」，
否则你会一直以为是站挂了。

**d) 探活消耗的 token 应当可见**
UI 展示「今日 L1/L2 次数、估算 token、各 Route 明细」，否则无法判断策略是否过激。

**e) api_key 加密存储**
`ENCRYPTION_KEY` 环境变量 + AES-GCM。密钥丢失则数据不可恢复，需警示 + 提供导出。

**f) 服务暴露公网 = 无鉴权的免费 API 池**
`relay key` 强制设置且校验，不允许空值启动。额外加 IP 白名单或只监听内网 + 反代。
**这条是必须做的**，否则你所有公益站的 key 等于公开。

**g) 暂停状态下的进行中请求**（§4.8）
暂停不能杀掉已建立的流式连接，否则会丢一次完整回复。只拒绝新请求。

**h) 样本库既是资产也是负担**（§3.6.3）
样本含**完整对话原文与你的代码**，且 Claude Code 单请求常有 50KB–1MB。
不封顶会写满磁盘，不脱敏会变成明文 key 库。已定：**单条不截断**
（三个字节上限默认 0 = 不限，完整留下入站/出站请求与响应）、
**最近 300 条 / 7 天滚动**、key 前 4 后 4 脱敏、
有界 channel 满则丢样本（绝不阻塞转发）。

封顶的维度是**条数而不是单条大小**：截断会静默损坏单条样本的可用性
（§3.6.1 的逐字段比对当场失效），而清理只是让更早的样本更早消失，
且 `pinned` 是精确的逃生舱。代价转移到了内存 —— `resp_body` 边转发边攒，
不限长意味着每个在途请求在 RAM 里留一份完整响应，大小由上游决定。
调回非零即恢复封顶，有界模式的代码路径一行没删。

**i) 头名大小写与头序无法字节级保真**（§3.3.3）
Go 标准库收到请求即规范化头名、且 `Header` 是无序 map。这是**真实的保真缺口**，
不是可以糊过去的细节，所以明确写进文档并给了三条「风险可接受」的证据
（HTTP/2 强制小写、公益站从 map 读头、M0 用 curl 探测照常放行 ⇒ 无 JA3/头序指纹校验）。
逃生舱（裸报文 + `utls` 伪装）**现在不做**，等样本记录给出需要的证据再说。

## 6. 技术选型

| 组件 | 选择 | 理由 |
|---|---|---|
| 语言 | Go 1.24+ | 反向代理与流式转发是它的主场；单二进制部署；`httputil.ReverseProxy` 直接可用 |
| HTTP 框架 | 标准库 `net/http` + `chi` | 路由极简，不需要重框架。`chi` 只为中间件链 |
| 存储 | SQLite（`modernc.org/sqlite`，纯 Go 无 CGO） | 单人自用，零运维。健康状态在内存，仅配置与日志落库 |
| ORM | 不用 ORM，手写 SQL | 表就 7 张，ORM 是负担 |
| 前端 | 单页 HTML + Alpine.js + CSS，**全部 `go:embed` 打进二进制** | 管理界面就是几个表格加开关，不值得上构建链。原稿写的是 Tailwind + Alpine **CDN**，M5 改成本地打包，理由见下 |
| 配置 | 环境变量（基础设施）+ 数据库（业务配置，热生效） | 参考 gpt-load 的双层配置 |
| 部署 | Docker Compose（单容器 + 挂载 data 卷） | — |

**为什么前端从 CDN 改成本地打包**（M5 的偏离，原稿写的是 Tailwind + Alpine CDN）：

- **这是自托管网关**，很可能跑在内网、或者访问外网不畅的环境里。首屏依赖
  外网 CDN 意味着「网关本身好好的，但管理界面打不开」—— 而管理界面正是
  出问题时要用的东西
- **Tailwind CDN 是个运行时生成 CSS 的 JS 包**，官方自己就不建议生产用
- 仍然**没有构建链**：不是引入 npm/webpack，只是把两个文件提交进仓库。
  `go:embed` 的部分与原计划一致


gpt-load 的核心抽象是「一个分组 = 一个上游端点 + 一个密钥池」，密钥轮换是它的主线，
而本项目需要的是「一个逻辑模型 = 多个异构上游站」，两者的数据模型正交，改造等于重写调度层。
New API 的请求管线做的是完整的协议解析与重构（为了计费和格式转换），
与「严格透传」直接冲突，拆掉它的管线就没剩什么了。
relay-pulse 的探活思路（真实调用 + 内容校验 + 拒绝假活）值得直接借鉴，但它是纯观测台、
不转发，无法复用代码。

**结构调整说明**（实现时对原稿的偏离，都是刻意的）：

| 原稿 | 实际 | 为什么 |
|---|---|---|
| `runstate/` 独立包 | 并入 `store/` | 总闸状态就是 setting 表里的一行，单独开包只为放两个函数 |
| `sample/retention.go` | 并入 `recorder.go` | 清理由后台 writer 每 50 条触发一次，与写入是同一个循环，拆开要多传一份状态 |
| 无 `livecfg/` | 新增 | SQLite 是单连接，一次转发要读 5 张表，不缓存会与样本落库队头阻塞 |
| `forward.go` = ReverseProxy 封装 | 手写转发循环 | 三段超时要在读 body 的循环里切 deadline，见 §3.3.5 |
| `health/` = 完整状态机 | M2 只有在途额度，M3 长出状态机 | 两者读写同一份 per-Route 状态，拆成两个包只会引入锁的协调问题 |
| `probe/l1.go` + `probe/l2.go` | 合成 `prober.go` | 两级探测共用 URL 拼接、鉴权注入、超时与 ctx 处理，拆开要么重复要么互相 import |
| 无 `probe/reporter.go` | 新增 | 真实请求的结果也要进状态机（§3.5），且必须与探活共用同一套分类器 —— 各写一套的话「429 不算失败」这类规则迟早在一边漏掉 |
| M6 只有 `proxy/retry.go` | 拆出 `proxy/errorpayload.go` | 「200 但载荷是错误」的判定有它自己的一套取舍（§10.7b：宁可漏判也不误判），塞进重试循环会让那段推理埋在控制流里 |
| 无 `store/migrate.go` | 新增 | `CREATE TABLE IF NOT EXISTS` 对**已存在**的表是空操作，加不了列。老库会静默停在旧结构上，而症状是「新字段读出来永远是零值」—— 不报错、不失败 |
| 日志复用 `sample.Recorder` | 独立的 `sample/logrecorder.go` | 形状相同（有界 channel + 单 writer），但开关、保留策略、队列**必须**各一套 —— 理由见 §3.7.2。复用的是形状不是实例 |

## 8. 开发与部署路径：**先本地，后服务器**

理由：透传保真度需要反复对比字节级 diff，本地起一个 echo server 做对照最快；
探活状态机需要造各种故障（超时、假活、429），本地 mock 上游才好造。
服务器上调试要反复重启容器，回环慢。

**本地阶段**（Windows 上开发）：
1. `go run` 起服务，`:18787`
2. 写一个 `mock-upstream` 测试服务器：可切换「正常 / 假活 200 空内容 / 首 token 超时 /
   429 / 401 / 中途断流」六种行为
3. 用真实 Claude Code 指向本地服务 + 一个真实公益站，验证端到端
4. 单测覆盖：字节保真、选路、状态机转换

**服务器阶段**：
1. `docker compose up -d`，只监听 `127.0.0.1:18787`
2. Caddy 反代 + 自动 TLS + IP 白名单
3. ccswitch 指向 `https://your-domain/`

> 也可以全程在容器里开发（`docker run -v ...  golang:1.24`），但编辑-编译回环会慢。

#### 9.1.1 M0 实测结论（6 站，直接决定以下默认配置）

| 结论 | 实测 | 对设计的影响 |
|---|---|---|
| **鉴权** | 可用的 4 站**全部 `x-api-key` 与 `Bearer` 都通** | `auth_style` 默认 `auto` 是安全的 |
| **`/v1/models`** | 6 站全部 200 | `l1_path` 默认 `/v1/models` 可用，L1 无需降级 TCP |
| **模型名原名** | 可用站**全部 200，无一需要映射** | `upstream_model` 默认留空 → **body 零改动**，走 §3.3.2 的纯透传分支 |
| **`count_tokens`** | **仅 2/4 支持**（另 2 站 404） | **必须**本地兜底实现，不能透传（§5.1e） |
| **`/v1/responses`** | 唯一一个有 gpt 且可用的站**支持** | 结论方向对，但**样本量 n=1，M4 前必须复测** |
| **流式真活** | 4 站均返回有效 `content_block_delta` | 无假活站，但探活仍须按 §4.3 校验内容 |
| **首 Token** | 简单 3.3–5.5s；长思考 22.4–32.0s | 校准 §4.2：5 分钟下限 ≈ 9× 余量 |
| **UA 白名单** | **1 站**非 `claude-cli/*` 前缀一律 401 | §3.3.3 全量转发 UA 是**硬要求**；探活也须带（§3.6.4） |

**两个需要你复核的点：**

1. **站点 A 结论与你的经验冲突（矩阵里标 ⚠）**。你标「好用」，脚本判整站不可用：
   所有 claude 模型 503、gpt 500、真假 key 同为 503（说明请求没走到鉴权就被拒）。
   两种可能：探测时该站恰好在故障窗口；或它有比 UA 更严的准入校验。
   **建议**：过一段时间单独重跑 `bash scripts/probe-upstream.sh <base_url> <key> ...`，
   若仍 503 则它进不了初始配置，等样本记录上线后再拿真实请求头比对。

2. **站点 A 的「需 beta:1M」标记很可能是脚本误报**。脚本的判据是
   「非 200 且响应体提到 1m 上下文」，而该站返回的是 503，错误文案里恰好含相关字样。
   证据是脚本自己也报了「追加后仍 $c2」——加上开关并没有解决。
   **所以不要**据此在网关里注入 `context-1m` 头：真实 Claude Code 本就不发这个开关，
   注入反而违反 §3.3 的「不增头」约束。此项标记在该站恢复前不予采信。

#### 9.1.2 M0 覆盖不到、需留到 M2/M3 的检查

M0 用 `curl` 从外部黑盒探测，有三件事它**结构上测不了**，必须在网关自身跑起来后验证：

| 项 | 为什么 M0 测不了 | 何时验 |
|---|---|---|
| 请求头**逐字段**保真 | curl 发的头本就不是 Claude Code 发的头，没有比对基准 | M2，用 §9.2 的 echo server；上线后用 §3.6 样本持续验 |
| 长上下文 / 工具定义下的行为 | 探测 body 是 `1+1=?`，几十字节；真实请求几十 KB 且含 tools | M2 端到端 |
| 真实并发下的限流阈值 | 探测是串行单发 | M3 故障注入 |

### 9.2 透传保真验证（本地，M2）

起一个把**原始字节、头、顺序**全量 dump 的 echo server，比对经过网关前后：

- 不映射时 body `bytes.Equal` 完全一致
- 映射时把 model 值换回原值后 `bytes.Equal` 一致
- 头部差异仅限 §3.3.3 黑名单：逐个头做集合 diff，**多出或少掉任何一个头都算失败**
  （不是「关键头都在就行」——那样会漏掉计划外的注入）
- 头**值**逐字节一致（大小写与顺序按 §3.3.3 已知残缺，单独断言为「仅规范化差异」）
- query string 原样带上（`?beta=true` 不能丢）
- 流式：SSE 事件到达间隔与直连一致（无缓冲）
- 响应体字节完全一致，含 `Content-Encoding`

### 9.3 故障注入验证（本地，M3）—— **已完成**

验证分两层：**单测**（`internal/health`、`internal/probe`、`internal/proxy`）覆盖判定逻辑
与时间条件（时钟可注入，不靠 Sleep）；**冒烟**（`scripts/smoke-m3.ps1`）起真二进制 +
三个 `mock-upstream.py` 靶站，从进程外验证同一组不变量。

两层都要有：单测能被「测试替身写得和实现一样错」骗过，冒烟不会 —— 它走的是
真 HTTP、真 SQLite、真调度循环。

| 场景 | 期望行为 | 验证位置 |
|---|---|---|
| 优先级 1 站 L1 失败 | 该站所有 Route 立即 dead，请求走优先级 2 | 单测 `TestScheduler_L1FailurePropagatesToAllRoutes`；冒烟 9.3b |
| 假活（200 但无内容） | L2 判 dead | 单测 `TestL2_FakeAliveIsUnavailable`；冒烟 9.3c |
| 首 Token 超时 | 判 dead 且**主动断流**不继续耗 token | 单测 `TestL2_FirstTokenTimeout`（断言服务端 ctx 被取消） |
| 429 | 冷却而非 dead，尊重 `retry-after`，不计失败 | 单测 `TestReport_RateLimitedCoolsDownWithoutDying` / `RespectsRetryAfter` |
| 400 model not found | 立即 dead，UI 标「配置错误」 | 单测 `TestClassifyHTTP_ModelNotFoundTakesPrecedenceOverGeneric4xx` |
| 401/403 | 整站立即 dead，UI 标「鉴权错误」 | 单测 `TestL1_Verdicts`、`TestReport_FatalIsImmediatelyDead` |
| 中途断流 | 原样传给客户端 + 计失败 + 触发即时探活 | 单测 `TestHandler_MidStreamFailureKeepsStatus`（M2）+ `ErrStreamBroke` 归 Unavailable |
| 全部 dead | 半开放行一次；仍失败才 503 + `X-Relay-Reason` | 单测 `TestHandler_HalfOpenWhenAllDead` 及同组 4 项 |
| dead 站恢复 | ≤30s 内 L2 察觉；首次成功即转 unknown 可用 | 单测 `TestReport_DeadRouteRecoversToUnknownOnFirstSuccess`；**冒烟实测 1.5s** |
| 站级恢复（L1 转通） | 立即触发该站所有 dead Route 的 L2，≤20s 发现 | 单测 `TestScheduler_L1RecoveryTriggersDeadRoutesL2` |
| 服务重启 | 所有 Route → unknown 且可用，立即全量 L1 | 单测 `TestTracker_UnprobedRouteIsOptimisticallyUnknown` + `TestClaim_UnknownProbesImmediately` |
| 真实请求成功 | piggyback 生效，跳过下一周期 L2 | 单测 `TestClaim_PiggybackSkipsL2AfterRealSuccess`（含 dead 站不适用的反例） |
| **暂停** | 新请求 503 + `X-Relay-State: paused`；探活全停；**进行中的流不断** | 单测 `TestScheduler_PausedStopsAllProbing`；冒烟 9.3g |

| **恢复** | 暖机窗口内按 unknown 放行，不出现「刚点开就 503」 | 单测 `TestScheduler_ResumeResetsState`；冒烟 9.3g |

### 9.4 样本记录验证（本地，M2）

样本功能的失败方式是**悄无声息的**——记漏了、记错了、或拖慢了转发，都不会报错。
所以必须显式验证：

| 场景 | 期望行为 |
|---|---|
| 正常转发 | 样本落库，`in_body` 与 `out_body` 除 model 外 `bytes.Equal` |
| 不映射时 | `in_body` 与 `out_body` **完全** `bytes.Equal` |
| key 脱敏 | 样本里**搜不到**任何完整 key（用真 key 字符串全表 grep 断言为 0 命中） |
| body 1MB（默认不限） | **不截断**，`truncated` 为空，样本里是完整原文 |
| SSE 响应 3MB（默认不限） | **全文入库**，`truncated` 为空，转发给客户端的仍是完整流 |
| 配了非零上限时 | 按上限截断且 `truncated` 标记正确，**转发的 body 仍是完整的** |
| 记录 channel 打满 | 丢样本 + 计数递增，**转发不受影响、不阻塞、不报错** |
| 关闭样本开关 | 零写入，转发路径无额外开销 |
| 保留策略 | 超 **300** 条 / 超 7 天被清理，`pinned` 的不被清 |
| 上游 500 | 样本仍完整落库（失败样本比成功样本更有诊断价值） |
| 客户端中途断开 | `outcome=client_abort`，已收到的部分照常留档 |

最后一条尤其重要：**失败请求的样本不能丢**。恰恰是失败的那次，你才需要知道
「我到底发了什么头过去」。

**两处接缝没按原计划用，理由如下**：

- **`Forwarder.OnFirstByte` 没被 L2 探活复用。** 原计划让 L2 复用 `Forwarder`，
  用这个回调做「收到首个有效事件即断流」。实现时发现不合适：`Forwarder.Forward`
  的签名要求一个 `http.ResponseWriter`（它的职责是把响应写给客户端），而探活没有
  客户端；更关键的是「首字节」不等于「首个**有效**事件」—— 首字节可能只是
  `event: message_start`，那不能证明模型在生成。判活必须解析 SSE 内容（§4.3 的假活），
  而那个逻辑在读循环里，塞进回调等于把判定散落到两处。所以 `probe/prober.go`
  自己写了读循环，与 `Forwarder` 共用的是 `BuildOutboundURL` 与哨兵错误。
  该字段现在**没有赋值方**（M2 起就没有），留着不碍事。
  → **M6 的预测落空了**：这里原本写着「M6 的重试可能会用到」，实际没用到。
  M6 在 `Attempt.Peek` 里多了一处**调用**点（预读到首字节时触发），但仍然
  没有任何地方给它赋值，所以它照旧恒为 nil。真正需要「首字节时刻」的两个
  消费方（TTFT 统计、日志的 `ts_first_byte`）都直接读 `Result.FirstByteAt`
  就够了 —— 那是个字段，比回调少一层间接。**这个字段可以删**，留到 M7
  清理死代码时一并处理，现在删要动 `Forwarder` 的公开结构，收益不值得。
- **`InvalidateTransport()` 仍无调用方。** 原计划「探活判定整站不可用后主动断开连接」。
  实现后判断收益不明：连接池本身有 `IdleConnTimeout`（90s）会自然回收，而站挂掉时
  连接多半已被对端关闭。主动断开省下的是最多 90 秒的空闲连接，代价是要在状态机里
  埋一个跨包回调（`health` → `proxy`）。**不值得**，除非日后观察到死站的连接确实堆积。

**两条不要做的事**（M3 已遵守，M4 起继续有效）：

1. **不要把 `health` 拆成两个包**（比如 `health` + `probe/state`）。状态机与在途额度
   读写同一份 per-Route 状态，拆开就要跨包协调锁。
2. **不要用 `InFlight()` 做并发上限判定**。它只供展示。判定必须走 `TryAcquire`——
   读计数再决定是否占用，两步之间有窗口，并发涌入时会全部通过检查
   （M2 修过这个 bug）。

**M4 的一个待决策** —— **已定：上游优先 + 本地兜底**

原问题是 `count_tokens` 走**本地粗算**（不依赖上游，误差 ±20%）还是
**路由到支持的站**（M0 实测只有 2/4 支持，需要 fallback）。
结论是两者都要，按顺序来：先转发给选中的 Route，上游回 4xx/5xx 或连不上时
降级到本地粗算。

理由：上游给的是真实 tokenizer 的结果，能拿到准确值时用估算值是白白降级；
而 M0 实测半数站不支持，纯转发方案会让那些站下的请求全部拿不到 token 数。
两条路的代码量差别很小（降级分支就是一个 `return 原因字符串`），
没有理由只选一条。

实现要点（都在 `proxy/count_tokens.go`）：

- **4xx/5xx 一律降级，不按 §4.3 分类**。404（没这个端点）、400（参数要求不同）、
  401（该端点单独鉴权）对客户端而言结果相同 —— 拿不到准确值，用估算值。
  而这些失败不回写健康状态，所以也不需要分类。
- **估算刻意偏高**。估高只是让客户端早一点压缩上下文；估低会让请求超出
  上下文窗口而被上游 400 拒绝。两个方向的代价不对称。
- **`tools` 必须计入**。Claude Code 每轮都带完整的 tools schema，
  它常常比对话本身长。漏掉它不是 ±20% 的误差，是数量级的误差。
- **`system` 与 `messages[].content` 两种形态都要接**（字符串 / content block
  数组）。Claude Code 发的是带 `cache_control` 的数组形态；声明成 `string`
  会让一个完全合法的请求拿到 400。这是实现第一版的真实 bug，已有回归测试。

**估算精度的已知缺口**（诚实交代）：

- 算法是「按空白与标点切词，英文词 ×1.3、CJK 字 ×1.5，超长词按 4 字符/token
  折算」，不是 BPE，与真实 tokenizer 有系统性偏差。它只保证一条性质：
  **单调**（上下文越长估值越大）—— 作为预算，单调性是必须的，绝对精度不是。
- **超长词折算是 review 时补的**，起因是一个真 bug：base64 图片没有空白，
  原实现把几百 KB 的图当成「1 个词」算成 1 个 token，而它在 Anthropic 侧
  约合 1400 个（按 `(w×h)/750`）—— 低估上千倍，而且方向正好错：低估会让
  客户端以为上下文还空着，然后发一个超窗口的请求被上游 400 拒掉。
  折算后带图请求进入正确量级，但仍是**按 base64 文本长度**估的，
  与「按图片尺寸计费」不是同一个模型，精确值对不上。
- 尚未与真实 tokenizer 做过数值比对（需要一个支持该端点的站做对照）。
  留到接上真实 Claude Code 后从样本里观察：**同一个请求**先走上游、
  再走本地兜底，两个值的比值就是校准系数。

| `count_tokens` 不记样本 | 刻意不记 | 若 M5 要看它的往返，加**独立的**开关与配额，别挤 300 条的滚动窗口（§3.6.3c） |

### 10.5 M5 PR-A（后端）实际完成范围

M5 拆成两个 PR：**PR-A 只做后端**（补齐 UI 需要的接口面），PR-B 做前端。
这么拆是因为后端能用 curl 独立验收，UI 出问题时不会和后端混在一起定位。

四项里前三项是 M3/M4 明确记着的遗留，不是新需求。

#### 会话 Cookie 登录

`api/router.go` 从 M1 起就写着「M5 上 Web UI 时再换成会话 Cookie」。

- `POST /admin/api/login|logout`、`GET /admin/api/session`
- 令牌 256 位 `crypto/rand`；**内存存储**，重启即全部失效。不落库是刻意的：
  落库要多一张表和一份清理逻辑，还会让「改了 ADMIN_PASSWORD 但旧会话仍有效」
  变成真实问题
- Cookie 带 `HttpOnly` + `SameSite=Strict`
- **不设 `Secure`**：默认监听 `127.0.0.1`，本地 HTTP 访问时带 `Secure` 的
  Cookie 会被浏览器直接丢弃 —— 那会让 §8 明确的主路径（先本地后服务器）
  根本登不上。上公网时 TLS 由 M7 的反代终结，届时应在反代上加
- **Bearer 口令保留不动**：`scripts/smoke-m2.ps1` / `smoke-m3.ps1` 全靠它，
  而那两个脚本是 §9.2/§9.3 验证清单的载体。两条路径校验同一个口令，
  不存在「改了口令还有一条路认旧的」
- 登录失败递进延迟（连错 3 次后每次延迟 1s，成功即归零且成功路径永不延迟）。
  这轮新增的是登录**表单**，而 `ADMIN_PASSWORD` 下限只有 8 字符

**顺带修掉一个既有缺陷**：`ADMIN_PASSWORD` 为空时
`subtle.ConstantTimeCompare("", "") == 1`，于是**不带任何凭据的请求会被判为通过** ——
管理接口能读写所有上游 key（§5.2f），等于全部公开。

M1 起就在，生产上靠 `config.validate`（要求 ≥8 字符）拦着所以不可达。
但鉴权是这个项目里后果最重的判断，不该依赖「调用方一定先校验过」——
明天多一个绕过 `config.Load` 的装配路径就会静默生效。现在鉴权层与登录端点
各自堵死。

发现方式值得记一笔：不是读代码想到的，是**先写了一条「空口令必须全部拒绝」
的测试**，跑出来是红的。写它时以为在做纵深防御，结果它抓到了现存行为。

#### 探活成本统计（§5.2d）

`GET /admin/api/probe-cost`：今日 L1/L2 次数、失败数、估算 token，
含各 Route / 各 Upstream 明细，附带当前探活间隔配置 —— 光看「今天探了
4300 次」判断不了是否过激，要同时知道间隔。

三个不显然的决定：

| 决定 | 理由 |
|---|---|
| 按天分桶 + 60s 周期落库 | 「今日」必须跨重启。纯内存计数在重启后归零，会让「今日 L1 = 12 次」在一天里越报越少 —— **一个会骗人的计数器比没有计数器更糟** |
| L1 记在 Upstream 上，不记在 Route 上 | 一次 L1 被同站多个 Route 共享（`scheduler.beginL1` 收敛），记到 Route 上会把一次请求算成 N 次 |
| 失败单独计数 | 失败的探活同样花钱（请求已发出），而失败占比是策略过激的直接信号：探一个死站 100 次全失败，那 100 次是纯浪费 |

`VerdictIgnore`（探活因暂停/关闭被取消）不计费 —— 请求没真发出去。

估算 token 与 `count_tokens` 的本地兜底用**同一个系数**（4 字符 ≈ 1 token）。
两处对不上的话，同一个 prompt 会给出两个数字。它是**上界**（按 `max_tokens`
的上限计，而判定一出就断流），用于成本估算时宁可高估。

#### 配置变更触发即时探活（§4.5 表格第 3 行）

只在真正影响探活结果的字段变化时触发（改 `name` 不触发 —— §5.2d 刚让这些
请求变得可见，没理由白发）。

`InvalidateUpstream` 一并作废 gate 的旧 L1 结论。**这是最容易漏、后果最难
查的一点**：改 key 前站是 401（L1 失败），改对之后若不作废，`maybeProbe`
会在 `if !s.gate.OK(up.ID) { return }` 处直接跳过 L2 —— 用户明明改对了 key，
界面上却一直显示不可用，而唯一的出路是等一次 L1 周期。

**为什么这个钩子不违反 livecfg 的「不做写后失效」原则**（§10.3 的顾虑）：

`livecfg/source.go` 拒绝写后失效通知的理由是「钩子漏一处就是改了不生效」。
那个判断没有被推翻：

- 配置**生效**仍然只靠 livecfg 的 2s TTL。这个钩子一行配置都不刷新
- 钩子只清探活预占。漏调的后果是「等下一个探活周期」，也就是退回 M3/M4
  的现状 —— 一个纯粹的时间差，不是错误状态

两者代价完全不对称，所以能挂钩子的地方是这里、而不是缓存层。

#### 样本导出探活头模板（§3.6.4 / §10.2 接缝）

`GET /admin/api/samples/{id}/probe-headers`。§10.2 把它推迟到 M5，理由是
「需要 UI 才有『以此为模板』这个动作」。

存在的理由：M0 实测到按 user-agent 白名单拦截的站，探活头长得不像真实
Claude Code 就会 401，于是一个完全可用的站被判死。手写探活头等于猜，
而 M0 已经证明猜会把好站踢出池子。

**导出侧自己过滤鉴权头，不依赖样本已脱敏。** 样本里存的是脱敏值
（`sk-abcd…wxyz`），当成 `probe_headers` 存回去会变成一个**明文的假 key**，
而 `probe_headers` 的优先级高于默认模板 —— 结果是整站探活 401 被判死，
界面显示「鉴权失败」，用户会去查真 key 对不对，完全指错方向。

只返回建议值 + 与默认模板的 diff，**不直接写库**：这份头影响该站所有探活的
成败，静默生效的话一次误导出就能让整站判死。

### 10.6 M5 PR-B（界面）实际完成范围

七个页面：健康看板、上游、模型、路由、样本、探活开销、设置，外加登录页与
顶栏的一键启停开关（§4.8 的前端部分，§10.1 说的「只剩前端开关」到此补齐）。

**技术选型的偏离**（§6 已同步）：原稿写 Tailwind + Alpine **CDN**，实际
全部 `go:embed` 打进二进制。理由是这是自托管网关，很可能跑在内网或访问
外网不畅的环境 —— 首屏依赖 CDN 意味着「网关本身好好的，但管理界面打不开」，
而管理界面正是出问题时要用的东西。仍然没有构建链：Alpine 是一个 44KB 的
文件，提交进仓库，不引 npm。

#### 静态资源刻意不鉴权

`web.Handler` 挂在 `/admin/`，不经过 `requireAdmin`。两个方向都成立：

- **不需要**：这里只有 HTML/CSS/JS，纯前端代码，不含任何配置或密钥。
  数据一律经 `/admin/api/`，那边照常要鉴权
- **不能要**：登录页自己就是静态资源，拦住它的话用户连输口令的地方都没有

`/admin/api/` 与 `/admin/` 并存靠的是 ServeMux 的最长前缀匹配。这个假定
用 `TestMuxPrecedence_APIWinsOverUI` 实测钉住了 —— 若它不成立，所有 API
请求会拿到一份 HTML，而症状是「界面加载后一片空白，控制台报 JSON 解析
失败」，从表象很难定位到路由优先级。

#### 界面上几处刻意的措辞

这些不是文案润色，是防止界面把用户引向错误结论：

| 位置 | 措辞 | 不这么写会怎样 |
|---|---|---|
| 健康看板的 `unknown` | 中性灰，与 `dead` 的红色区分 | `unknown` 是**乐观**状态（视为可用、正常参与选路，§2.4）。标红会让人以为服务坏了 —— 而重启后所有 Route 都是 unknown |
| 不可选路的原因 | 直接显示后端的 `reason` | 后端刻意复述了选路的排除条件，且区分「配置错」与「站挂了」：前者要改配置，后者等它自己恢复 |
| `api_key` 输入框 | 「留空 = 不修改现有 key」 | 后端的 PUT 语义就是留空不改。不说清的话用户会以为留空是清空 |
| `upstream_model` | 「留空 = 不映射，body 一个字节都不改」 | 这是推荐配置（§3.3.2）。不说明的话用户会习惯性填一个 |
| `base_url` | 「不要带 /v1」+ 指向 full_url_mode | 带 `/v1` 是配置时最容易犯的错，症状是 404 且很难看出根因 |
| 估算 token | 标「估算上界，非账单」 | 它是判断策略是否过激用的，当成账单会引出错误的成本结论 |
| `truncated` 标记 | 显式列出哪份 body 被截断 | 默认不限时它恒为空；配了上限之后，看到一个恰好等于上限的 body 无法判断它是本来就这么大还是被砍过 |
| 探活头导出的 `skipped` | 列出被排除的头并说明原因 | 用户看到模板里没有 `Authorization` 时，若不知道那是**刻意**排除的，下一步就是手动加回去 —— 那正是要防的事 |
| `client_abort` | 中性灰而非红色 | 那是客户端自己取消的，不是上游的问题 |

前端的错误提示一律显示**后端原文**。`model/validate.go` 里那些错误是刻意
写给人看的（「base_url 不能带路径…若该站确实用非标准路径，请开启
full_url_mode」），换成「保存失败」就等于把最有用的部分丢掉。

#### 端到端验证抓到的一个 bug

真的起服务、真的登录、真的走一遍界面 —— 这是唯一能证明前端可用的方式。
过程中撞到一个**后端** bug：

**L1 失败时，手动探活的 `l2` 被报成 `"verdict": "ok"`。**

成因是 `health.Verdict` 的零值恰好是 `VerdictOK`（`iota` 的第一个），
而 `ProbeNow` 在 L1 不通时直接返回，`l2` 是未初始化的 `Outcome{}`。
界面上就成了「L1 失败、L2 成功」—— 一个自相矛盾、且让人无法判断这个
Route 到底能不能用的结论。

修法是在 API 层显式区分「未执行」与「执行了且成功」（`l2: null` +
`l2_skipped` 说明），而不是给 `Outcome` 加一个 `executed` 字段 ——
`ProbeNow` 的契约就是「L1 不通就不探 L2」，在 API 层复述它比在探活热路径
上多带一个字段干净。

修完又用假上游验证了反向：**L1 通过时 L2 照常执行**（拿到 `verdict:
fatal`，因为假上游不认识那个模型名 —— 正确行为），确认没有把 L2 整个关掉。

这个 bug 单测抓不到：`outcomeJSON` 单独看没有问题，`ProbeNow` 单独看也
没有问题，错在两者的接缝上，而那个接缝只有真的跑一次才会暴露。

#### 端到端验证的完整结论

用真实进程 + 假上游（`scripts/mock-upstream.py`）跑通：

- 界面加载、静态资源、无任何外部 CDN 引用
- 登录（错口令拒绝、正确口令签发 HttpOnly Cookie、登出后 Cookie 失效）
- 配置 CRUD，校验错误原文透传到前端
- 探活：连不上的站 6 秒内判死、不可选路；假上游就绪后 L1+L2 全通、转 alive
- 即时探活钩子：改 key 触发（预占清零）、只改 name 不触发
- 一键启停：paused 后转发 503 + `X-Relay-State`，管理端点仍可用
  （注意有最长 2 秒的延迟 —— `livecfg` 的 TTL，属既有设计）
- 真实转发 → 样本落库 → 详情三份 body
- **样本里搜不到明文 relay key，也搜不到明文上游 key**
- 探活头导出：不含任何鉴权头，`skipped` 如实回报，真实指纹（user-agent）保留

#### M5 整体 review 抓到的问题

PR-A 与 PR-B 各自 review 过，但**前端从未做过代码 review**（只做了端到端），
而跨 PR 的接缝问题单看一个 PR 也看不出来。补了一轮整体 review：

| 问题 | 严重度 | 说明 |
|---|---|---|
| 登出/掉线不清内存数据 | **高** | `authed=false` 之后 `samples`、`upstreams` 仍在内存里。样本含完整对话原文与代码（§3.6），下一个人在同一浏览器登录会先看到上一次的数据闪现。抽出 `reset()`，401 与登出两条路径共用 |
| 三处 `saveXxx` 的刷新在 `run` 保护之外 | 中 | 那个裸 `await` 一旦失败（会话刚过期、网络抖动）就是未捕获的 promise rejection —— 界面静默不动，用户以为没保存，其实存进去了。把保存与刷新收进同一个 `run` |
| 降级判据靠中文子串匹配 | 中 | `/未接入\|未启用/` 匹配错误文案来识别「探活未启用」。后端改一次措辞前端就误报。改成 `e.status !== 503` |
| `run()` 的成败判据依赖 `null !== undefined` | 低 | `DELETE` 回 204、`api()` 给 `null`，旧判据 `ok !== undefined` 靠这个微妙差别工作。改成返回 `{ok, data}` |
| `togglePin` 自己取反而不用后端返回值 | 低 | 后端将来若给这个操作加条件（置顶数量上限），界面会显示一个没生效的状态 |

**CSRF 面是 PR-B 才产生的**：PR-A 写 `SameSite=Strict` 的注释时还没有界面，
判断依据是「管理接口全是状态变更操作」。引入浏览器后才真正需要这条防线。
补了一组测试（`csrf_test.go`）把边界钉住：26 个端点无凭据时全部 401、
Cookie 确实是 Strict。

剩一个**已知且可接受**的缺口：`decodeJSON` 不校验 Content-Type，跨站表单
理论上能把 JSON 当 `text/plain` 提交到 `/login`。可接受是因为攻击者要构造
它就得已经知道口令（知道了直接登录即可），且响应的 `Set-Cookie` 跨站读不到 ——
唯一效果是 login CSRF，而这个网关只有一个账号，「登入攻击者的账号」与
「登入自己的账号」是同一件事。**引入多账号时这条就不成立**，
`TestCSRF_LoginAcceptsNonJSONContentType` 的注释里写了这个失效条件。

#### 前端契约测试

`internal/web/app.contract.test.js`，用 `node` 直接跑（不进 CI，CI 里没有 node）。

为什么值得加：`run()` 的返回形状被 15 个调用点依赖，漏改一处不会报错 ——
那个调用点会拿到一个**永远为真**的对象，于是失败的操作看起来成功了。
JS 没有编译器帮忙查这个，而在浏览器里点一遍既慢又容易漏。

写这份测试时，骨架本身出过一个值得记的错：`t()` 用 `try/catch` 包 `async`
函数但**没有 await**，于是 catch 永远不触发，**所有断言都无条件打印 ok**。
第一次跑变异验证时，失败的用例先报了 `ok`、然后进程以未处理的 rejection
崩掉 —— 能发现纯属侥幸。改成顺序 `await` 之后重跑三个变异（reset 漏清
samples、run 失败也返回 ok、503 当真错误弹出），三个都被正确报成失败。

这件事本身是个提醒：**新写的测试骨架也要先证明它会失败**，
否则「全部通过」可能只是没在测。

#### 最后一轮 review：两个被证伪的怀疑

前几轮按「PR-A 后端 → PR-B 前端 → 跨 PR 接缝」走过，最后一轮换角度看
**一直没被怀疑过的地方**。结果是两个怀疑都被实测推翻，一个新工具留了下来。

**怀疑一：界面的 3 秒自动刷新会拖垮 SQLite 的单连接。**

`getHealth` 每次读三张表且**绕过 livecfg 的缓存**直读 `s.st`，而 livecfg
存在的全部理由就是「单连接、不缓存会与样本落库队头阻塞」。M3 时
`getHealth` 只被冒烟脚本偶尔调，PR-B 的自动刷新把它变成了持续负载。

推理链看着成立，实测把它推翻了：**25 条 Route 时每轮只花 127 微秒**，
占 3 秒刷新间隔的 0.004%。这些表只有几十行，SQLite 读它们是微秒级。
接 livecfg 反而引入 2 秒陈旧度而收益为零。

不改代码，但把量化结论留在 `TestGetHealth_QueryCostUnderAutoRefresh` 里 ——
否则下次还会有人（包括我）产生同样的疑虑，再排查一次。

**怀疑二：`TrimPrefix(path, "/admin")` 对不匹配的输入原样返回。**

读代码时像个隐患（`/adminfoo` 会被剥成 `foo`）。实测下来剥出的路径在
`static/` 里找不到，FileServer 给 404，与「本来就不该处理」的结果一致。
同样只加测试不改代码（`TestHandler_PathPrefixEdges`）。

#### 绑定检查器

`internal/web/bindings.check.js`，交叉核对 `index.html` 里的 285 个 Alpine
绑定与 `app.js` 的实际定义。

为什么需要：Alpine 对不存在的属性是**静默渲染空白**的，对不存在的方法
则要到点击时才在控制台抛错。拼错一个名字没有任何编译期提示 —— 界面上
就是一处空白或一个不响应的按钮，而 864 行 HTML 靠肉眼比对不现实。

它的**盲区要说清楚**：查得到顶层标识符拼错（`sampleFilter` → `sampleFiter`）
与调用不存在的方法，**查不到属性访问拼错**（`upForm.api_key_masked` →
`...maskd`）—— 那需要知道每个对象的运行时形状。这类错误的表现是
「某一个字段显示为空」，比整块空白隐蔽但影响也小，靠端到端覆盖。

变异验证过两次（拼错属性名、调用不存在的方法），都精确抓到。

### 10.7 M6 实际完成范围

分五个提交：三块地基 → 重试循环 → 请求日志 → REST 端点 → 诊断视图，
外加端到端冒烟。

#### a) 能重试的前提：把「拿到响应」与「交给客户端」拆开

原先的 `Forward` 一拿到响应头就 `WriteHeader` —— 状态码一旦发出，5xx 与 429
就再没法换站了，而那两类恰好是 §3.5 明确列为可重试的。所以拆成
`Send` / `Commit` / `Discard` 三段，重试的全部空间就在 Send 与 Commit 之间。

「已写出字节后不得重试」这条**不需要**判断：结构上到不了 —— 判定发生在
`Commit` 之前，而 `Commit` 是唯一会写字节给客户端的地方。

#### b)「200 但载荷是错误」为什么不能用子串匹配

`probe/sse.go` 判假活用的是 `bytes.Contains(data, "\"error\"")`。那在**探活**里
安全：prompt 是我们自己定的 `1+1=?`，模型不会回一段含 error 的内容。

但真实流量的内容是用户的对话，而**流式响应是逐 token 到达的** —— 模型解释报错时
「error」单独成一个 chunk 完全正常，于是 `"text":"error"` 里出现了未转义的
`"error"`。子串匹配会把这种响应判成错误，丢掉重发，再丢掉，直到次数耗尽。

两个方向的代价**极不对称**：

| | 后果 |
|---|---|
| 假阳性（好响应判成错误） | 丢掉一个已生成好的答案，token 白花，用户多等一轮，**而且不报错** —— 表现为「偶尔慢一倍」，没人会想到是网关自己丢的 |
| 假阴性（漏判错误响应） | 把上游的错误原样传给客户端 = M5 的现状，没有退化 |

所以规则是「**证据确凿才算错误**，拿不准一律放行」：只认顶层的 `error` 键与
`type == "error"`，不认内容里的任何字样。`content_block_delta` 的顶层键是
type/index/delta，用户文本嵌在 `delta.text` 里，结构上够不到顶层 ——
这正是子串匹配做不到的区分。

`probe/sse.go` **刻意没改**（`CLAUDE.md` 规则 6：只清理自己改动造成的孤儿）。
两处判据不同是有理由的，在注释里写清了，免得日后有人来「统一」它们。

#### c) 每次尝试必须从入站原文重建出站产物

出站请求由四样东西拼成：改写后的 body（model 映射）、注入了上游 key 的请求头、
拼好的 URL、该站的 Transport（可能带自己的 proxy）。这四样**全部**是
per-Upstream 的。

复用上一次尝试的产物就是**把 A 站的 key 发给 B 站** → B 站必然 401 →
B 站被判死。一个好站因为我们的 bug 被踢出池子，而日志里显示的是
「B 站鉴权失败」，排查方向完全跑偏。

`dispatch` 的入参只有 `pre.body`（入站原文）与 `cand`，就是为了让这件事在
**结构上做不到**，而不是靠记得。

#### d) 资源账：三处容易静默泄漏的地方

1. **并发额度逐次占用、逐次归还**。攒到函数出口统一还的话，一次三连重试会
   同时占住三个站的额度，把 `max_concurrency` 当场翻三倍 —— 而配它的通常是
   「多开一路就限流甚至封号」的公益站。
2. **`Discard` 排水时把错误响应的开头留进 `ErrBody`**。不多读一个字节：那段
   排水本来就要做（让连接还回池子），只是把目的地从 `io.Discard` 换成缓冲区。
   少了它，`ClassifyHTTP` 只能看状态码 —— 而「500 + body 里写着 rate limit」
   （Anthropic 的 529 overloaded 就是这个形态）会被判成故障而累计判死，
   本该只是冷却 60 秒。
3. **`ReportResult` 必须在 `Discard` 之后调**。反过来的话回写拿到的永远是空
   body。这是实现时踩到的真实顺序 bug，两条测试变红才发现。

#### e) `retryable` 要在 `Peek` 之后**再看一次**错误

`Peek` 自己可能产生错误：上游回了响应头却迟迟不吐 body（首 Token 超时），
或吐了头就断开。只在函数开头读一次 `res.Err` 的话，这一整类故障会带着 200
走完提交路径，客户端拿到一个 504 而不是换站重试 —— 而「响应头回得很快、
body 一个字节都不来」正是公益站最常见的挂法。

同样在实现时踩到，靠 `TestRetry_RetryableConditionsSwitchStation` 的
「响应头已回但 body 卡死」子测试抓到。

#### f) 变异验证

每一条都先 `grep` 确认变异**物理存在于文件里**，再跑测试 —— 这是 M5 学到的
教训（`python - <<EOF` 在 Git-Bash-on-Windows 上静默 no-op，三次「变异通过」
全是假的）。

| 变异 | 结果 |
|---|---|
| 复用上一次尝试的 `outHeader` | 2 条变红。其中一条抓到完整后果链：A 的 key 到了 B、B 回一个带 key 的 401、那个 key 又未脱敏地进了 `route_health.last_error` |
| 无视 `retryable` 判定 | 5 条变红（4xx 被重试、200 被重试） |
| 结构化判错改成子串匹配 | 4 条变红（token 边界、`"error":null`、嵌套 error…） |
| 日志清理按行切而非按组 | 1 条变红，`grp-2` 只剩 2 行 |
| 「没重试过的失败」也算进 `failed_after_retry` | store 与 api 两层同时变红，自洽性断言直接抓到「1 + 2 != 2」 |

#### g) 端到端冒烟抓到的东西

`scripts/smoke-m6.ps1`，39 项。它验证的是单测**看不到的接缝**：单测里
「A 站的 key 不发给 B 站」是用假的 Candidate 断言的，而真实链路上这个头要经过
`PrepareOutboundHeaders` → Transport → 真实 TCP，中间任何一处缓存或复用都会
让它成立不了。

两个站配**不同**的 key，从**站那一侧**观察（mock 记下收到的 `x-api-key`）——
网关自己的样本是脱敏后的，看不出收到的到底是谁的 key。

顺带在 mock 里抓到一个真 bug：`do_POST` 若不读走请求体就返回错误，残留的 body
会被 HTTP/1.1 keep-alive 的下一次请求当成请求行解析，Python 回
**501 Unsupported method**。表现是「偶尔一个请求的状态码莫名其妙」，而真正的
原因在**上一个**请求里。`dead` 场景原本也有这个隐患，一并修了。
改完跑 m2/m3 确认无回归 —— mock 是三个脚本共用的。

#### h) 诊断视图

列表按 `req_id` 聚组，代表行取**最后**一次尝试（客户端实际拿到的那个）。
取第一次的话，一个「先失败后成功」的请求会显示成失败 —— 正好把重试的价值
显示反了。

后端刻意返回**平铺**的行而不是嵌套结构：那样翻页、筛选、统计都是普通 SQL，
嵌套要么多查一轮要么在 SQL 里拼 JSON。归组放在前端，因为它纯粹是展示需要。

五张统计卡片。「救回来的」是唯一能证明重试有价值的数字，「尝试总数 − 请求数」
是它的开销 —— 两个数放在一起才能判断值不值得。

`runtime` 新增日志的丢弃计数：丢掉的行会让那五个数字**偏低**（分母少了），
而一个不知道自己不准的统计比没有统计更糟。

  此前后端有这些项但 UI 改不了 —— 一个存在却调不到的配置项等于没有。

  而这恰恰是 §3.7 那张表存在的理由。
- **日志表的长期增长没有实测**。默认 5000 条 / 7 天，按一行几百字节估算是

#### k) M6 review 修掉的三处（含一处工具盲区）

三处都是**静默**失败 —— 不报错、不崩，只是给出一个错的答案：

1. **「只看重试过的」复选框是死的。** `index.html` 绑的是
   `logFilter.retriedOnly`，`app.js` 读的是 `only_retried`。Alpine 对 `x-model`
   的行为是**凭空创建**那个属性，于是勾选写进了一个没人读的字段。
   后端的 `only_retried` 参数一直是好的。

2. **日志页的丢弃计数是陈旧的。** 那个横幅是「上面五个统计数字偏低」的唯一
   警告，可 `runtime` 只由 `loadHealth()` 填、自动刷新又只在健康看板生效。
   于是刷新日志页会得到新算的统计配上页面加载时的丢弃数 —— 而丢弃恰恰
   发生在高负载时，也就是用户正盯着这一页的时候。`loadReqLogs` 现在一并拉
   `/runtime`。

3. **`retried` 用行数判、而不是用 `attempts` 列判**（详见 §3.7.5）。丢行时
   低估重试效果，且低估发生在最需要这个统计的时段。

第 1 条真正值得记的不是那个拼写，而是**它在 `bindings.check.js` 存在的前提下
仍然进了主干**：检查器的注释里白纸黑字写着「查不到属性访问拼错」，而这条 bug
正落在那句话里。已扩展检查器覆盖 `x-model` 的写入目标（只对 `logFilter` 这类
初始即为对象字面量的宿主下结论，`settings`/`upForm` 等要等接口才成形的仍跳过），
并**把两个前端检查接进了 CI** —— 原先「CI 里没有 node」的判断对 ubuntu-latest
早已不成立，而只靠「有人记得手跑」的检查等于没有检查。

两项修复都做了变异验证：把 bug 塞回去确认变红，还原后变绿。

**未改的一处**：`nextCandidate` 把含阻塞预读的 `retryable` 排在纯内存的
`selectFor` 之前，于是单 Route 部署下仍会先阻塞预读、之后才发现无站可换 ——
响应头因此被压到首字节之后才发出（长思考实测 22–32s）。功能无损（预读字节由
`Commit` 原样重放），但 `Peek` 原注释「等于零额外等待」是不准确的，已改正并写明
代价。真要调换顺序，得连带处理 `SelectExcluding` 内部 `TryAcquire` 占的并发额度
（提前选路后若判定不重试就必须归还），那是另一笔资源账，留待有真实延迟数据时再定。

### 10.8 M7 review 修掉的四处 —— 全是**检查器自己**在骗人

四处的共同点：被检查的部署清单是对的，**检查它的工具是坏的**。
后果比一条断言失败更糟 —— 屏幕上打印的是 `[PASS]` 和「全部通过」。

1. **空 ACME 邮箱那条检查从来没跑到 `caddy validate`。**
   `smoke-m7.ps1` 是 CRLF 的（`.gitattributes` 强制 `*.ps1 eol=crlf`），
   而它内嵌的 here-string 被原样交给 alpine 容器里的 `sh -ec`。
   alpine 的 `/bin/sh` 是 **busybox ash，不容忍任何 `\r`** —— `then\r`
   不是关键字 `then`，整段脚本报

   ```
   /bin/sh: syntax error: unexpected end of file (expecting "then")
   ```

   之后一行都不执行。这条断言正是「公网 profile 到底能不能起来」的唯一门禁。

   **这一条是 CI 抓到的，不是本地 review 抓到的。** 本地只看出了其中一种表现
   （`sed ... \` 续行后面跟 `\r`，报 `sed: can't read r`），因为开发机的
   MSYS `sh` 恰好**容忍**行尾 `\r` —— 于是本地怎么试都复现不出真正的根因。
   第一版修复只去掉了那个续行，必要但远不充分。
   现在所有送进容器 shell 的 here-string 一律先过 `ShLF` 去掉 `\r`。

2. **`check-entrypoint.sh` 的变量检查只认 `${VAR}`，不认裸 `$VAR`。**
   它是专为「`DB_PATH` 从未赋值」那个真实 bug 写的，可同一个 bug 换成
   `chown "$MISSING" ...` 的裸写法就整个漏过去。实测注入裸变量后检查器全绿。

3. **「chown 目标必须是绝对路径」是个恒真断言。** 它跑的是检查器里**自己重抄
   的一份** `DB_PATH=...`，而不是 `entrypoint.sh` 的真实代码。把 entrypoint
   的默认值改成相对路径 `relay-gate.db` 之后，它照样 `[PASS]`。
   现在从真实脚本里 `grep` 出那行赋值再展开，并且不带 `RELAY_DB` 跑 ——
   验的是真实部署走的那条默认路径。

4. **`.dockerignore` 的检查用子串匹配，注释掉规则照样通过。**
   `grep -F '.env'` 会被 `.env.local` 那一行满足，`grep -F 'data/'` 会被
   `#data/` 自己满足。于是把两条排除规则注释掉之后检查器仍然全绿 ——
   而它守的是「明文对话原文与三项凭据不进构建上下文」。改成剥注释后**整行精确**
   匹配（`grep -qxF`）。

#### 变异验证

每一条都先确认变异**物理存在于文件里**（改完回读字节，不信 `sed` 的退出码 ——
这是 M6 的教训），再跑检查器：

| 变异 | 修复前 | 修复后 |
|---|---|---|
| 裸 `$MISSING_MODE` 未赋值 | 全绿 | 变红 |
| `${DB_PATH}` 未赋值（原始 bug 形态） | 变红 | 变红（无回归） |
| `DB_PATH` 默认值改成相对路径 | 全绿 | 变红 |
| `.env` 注释成 `#.env` | 全绿 | 变红 |
| `data/` 注释成 `#data/` | 全绿 | 变红 |
| 把 here-string 直接交回 `sh -ec` | 无此检查 | 变红 |
| 以上全部还原 | — | 全绿 |

#### 新增的第三方防线

`check-deploy.sh` 加了一条：**凡是把 here-string 交给容器 `sh -ec` 的地方，
都必须先过 `ShLF`**（判据是 `sh -ec @'` 这种直接喂 here-string 的写法为零）。

第一版的判据写的是「CRLF 脚本里不能有反斜杠续行」，按字节匹配 `5c 0d 0a`。
那个判据本身是准的（用正则不行 —— 实测在 MSYS 下 `grep -E '\\$'` 对根本不以
反斜杠结尾的行误报 168/401 行，`awk '/\\\r$/'` 则一条都不报），但它**盯错了
东西**：真正的不变量不是「别用续行」，而是「别把 `\r` 送进 busybox」。

#### 这一轮真正的教训

**开发机的 shell 比目标环境宽容，于是本地验证会给出假的绿灯。**
MSYS `sh` 容忍行尾 `\r`，busybox ash 不容忍。四条 finding 里有三条能在本地
用变异测试证伪，唯独最要命的那条不能 —— 它只在 CI 的 Linux runner + alpine
容器里现形。这也正是「M7 的容器验证必须进 CI」的直接理由：
本机禁用 Docker 不只是操作限制，本机**根本不是那个运行环境**。

#### 仍未解决

- 最新版 `smoke-m7.ps1` 的容器端到端**已在 CI 跑通**（GitHub Actions 的
  `container` job，全部断言 PASS）。本机仍不具备也不允许 Docker 环境，
  容器验证一律以 CI 为准。
- 从 M4 拖到现在的两项仍未做：**`/v1/responses` 复测**与
  **`count_tokens` 估算校准**，都需要真实流量。

#### 一个悬案就此了结（以及它没解决的那半个）

`deploy/Caddyfile` 的 `transport http` 里写了 `read_timeout` / `write_timeout`，
本轮本机查证不了它们是否为合法子指令（WebFetch/WebSearch 全被网关拦掉，
两个专门去查文档的子代理也都以 429 失败，没拿回任何结论）。

修好第 1 条之后，「RELAY_ACME_EMAIL 留空时 Caddyfile 仍合法」这条断言
**第一次真正执行**并通过。这证明的是:整份 Caddyfile 能过 `caddy validate`，
而 Caddyfile 适配器对无法识别的子指令是**报错**的 —— 所以那两个指令确实被
这个版本的 Caddy 接受，公网 profile 不会因为它们而启动即退出。

**但 validate 只证明「解析器接受」，不证明「运行时语义是注释里写的那个」。**
「首 Token 等 20 分钟不被掐断」要真实的长思考流量才能确认 —— 与 §9.1.1 那两项
（`/v1/responses` 复测、`count_tokens` 校准）一样，属于接上真实流量后才能收尾的。
接上之后如果长思考仍被中途掐断，第一个该看的就是这里:超时该配在
`transport http` 内，还是 global options 的 `servers { timeouts { ... } }`。

这仍然是把容器验证放进 CI 的价值:一个读文档读不出（这轮还真就读不到）的结论，
让真实的 Caddy 二进制给出了答案 —— 哪怕只是答了一半。

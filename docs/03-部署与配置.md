# 服务器部署与配置（公网 + 多中转站）

面向的场景：**一台有公网 IP 的 Linux 服务器**，手里有**多个**中转站，
希望本机（或任何网络下的）Claude Code 通过域名接进来。

每一步都给了可复制的命令。示例里的 `relay.example.com`、`api-a.example.com`、
`sk-xxx` 都是占位符，替换成你自己的。

> 只在本机自用、不需要域名的话，看 [README 的快速开始](../README.md#快速开始) 就够了，
> 不用读这篇。

## 最终形态

```
                        公网
                          │
                     :443 │ TLS（Caddy 自动申请证书）
                          ▼
   ┌──────────────────────────────────────────────┐
   │  服务器                                       │
   │                                              │
   │   Caddy ──────────────▶ relay-gate           │
   │   ├ /admin*  IP 白名单   （只绑 127.0.0.1）   │
   │   └ /v1/*    relay key                       │
   │                            │                 │
   └────────────────────────────┼─────────────────┘
                                │
                 ┌──────────────┼──────────────┐
                 ▼              ▼              ▼
              站 A(P1)       站 B(P2)       站 C(P3)
              健康 ✅         健康 ✅         判死 ❌（不投递）
```

关键点：**relay-gate 自己只绑 `127.0.0.1`**，公网流量一律经 Caddy。
所以管理面的 IP 白名单不可能被绕过——直连那个端口从公网根本进不来。

## 0. 前置条件

| 项 | 要求 | 怎么确认 |
|---|---|---|
| 服务器 | Linux，公网 IP，1 核 512MB 起 | 单二进制 + SQLite，不吃资源 |
| 域名 | 一个可改 DNS 的域名 | Caddy 申请证书要它 |
| 端口 | 80 与 443 可从公网访问 | ACME HTTP-01 校验走 80 |
| 你的出口 IP | 用于管理面白名单 | `curl -s ifconfig.me` |

软件依赖：`git`、Docker、Docker Compose V2。如果走
[8.2 用 API 批量配](#82-用-api-批量配)，另需 `curl` 与 `jq`：

```bash
sudo apt-get update && sudo apt-get install -y git curl jq
```

先记下你的出口 IP，第 3 步要用：

```bash
curl -s ifconfig.me
# 203.0.113.45
```

> [!NOTE]
> 家宽多数是动态 IP，会变。变了之后你会**进不去管理界面**（转发端点不受影响）。
> 应对办法见 [12. 故障排查](#12-故障排查)。

## 3. 生成凭据并填 .env

```bash
cp .env.example .env
```

### 3.1 生成三项必填凭据

**分三条单独执行**，把输出记下来——尤其 `ENCRYPTION_KEY`：

```bash
openssl rand -hex 32
# 8f3a2c9e1b7d4f6a0c5e8b2d9f1a4c7e3b6d8f0a2c5e9b1d4f7a0c3e6b8d1f4a

echo "rk-$(openssl rand -hex 24)"
# rk-2f8a1c4e7b0d3f6a9c2e5b8d1f4a7c0e3b6d9f2a5c8e1b4d

openssl rand -base64 24
# kJ8mNp2QrS5tUv7WxY0zAb3CdE6fGh9I
```

> [!CAUTION]
> **`ENCRYPTION_KEY` 丢了，已存的上游 key 全部无法解密**，只能一个个重填。
> 它不是可以随手轮换的东西——改这个值等同于清空所有上游 key。
> **现在就把它单独存进密码管理器**，别只留在服务器上。

三项的分工，别搞混：

| 变量 | 是什么 | 谁用 |
|---|---|---|
| `ENCRYPTION_KEY` | 加密**上游站 key** 的密钥（AES-GCM） | 只有 relay-gate 自己 |
| `RELAY_KEYS` | relay-gate **发给客户端**的 key | Claude Code 填这个 |
| `ADMIN_PASSWORD` | 管理界面登录口令 | 你登录用 |

`RELAY_KEYS` **不是**任何中转站的 key。上游站的 key 稍后在管理界面里填，
存进数据库并加密，不放在 `.env` 里。

### 3.2 编辑 .env

```bash
nano .env      # 或 vim
```

填成这样（把值换成你上一步生成的）：

```bash
# ── 必填三项 ──────────────────────────────────────
ENCRYPTION_KEY=8f3a2c9e1b7d4f6a0c5e8b2d9f1a4c7e3b6d8f0a2c5e9b1d4f7a0c3e6b8d1f4a
RELAY_KEYS=rk-2f8a1c4e7b0d3f6a9c2e5b8d1f4a7c0e3b6d9f2a5c8e1b4d
ADMIN_PASSWORD=kJ8mNp2QrS5tUv7WxY0zAb3CdE6fGh9I

# ── 可选 ────────────────────────────────────────
RELAY_PORT=18787
TZ=Asia/Shanghai
VERSION=v1.0.0

# ── 公网模式（--profile public 必填）────────────────
RELAY_DOMAIN=relay.example.com
RELAY_ACME_EMAIL=you@example.com
RELAY_ALLOW_IPS=203.0.113.45
```

几点说明：

- **`RELAY_KEYS` 可以配多个**，逗号分隔——给不同设备发不同的 key，
  哪个泄露就只吊销那一个：
  ```bash
  RELAY_KEYS=rk-laptop-2f8a1c4e...,rk-phone-9d3b7f1a...
  ```
- **`RELAY_ALLOW_IPS` 空格分隔，支持 CIDR**：
  ```bash
  RELAY_ALLOW_IPS=203.0.113.45 198.51.100.0/24
  ```
- **`RELAY_ACME_EMAIL` 可以留空**，Caddy 会用匿名账号申请证书。
  代价是证书快到期时收不到任何提醒，而过期的表现是客户端全面报错。建议填。
- **`TZ` 影响探活成本的「按天」分桶**。不设的话容器只认 UTC，
  「今日 L1 次数」会在东八区早上 8 点才清零。

> [!WARNING]
> **`RELAY_ALLOW_IPS` 留空 = 管理界面全部 403**，这是刻意设计的，不是 bug。
> 忘了配的后果应该是「我进不去」（立刻发现、自己动手修），
> 而不是「全世界都能进我的管理界面」（永远不会发现）。
> 转发端点不受这个限制，它靠 relay key 鉴权。

### 3.3 检查 .env 没有 Windows 换行

如果你在 Windows 上编辑过 `.env` 再传上去，务必确认：

```bash
file .env
# .env: ASCII text                      ← 正确
# .env: ASCII text, with CRLF line terminators   ← 有问题！
```

有 CRLF 就修掉：

```bash
sed -i 's/\r$//' .env
```

> [!CAUTION]
> **这是最坑的一个坑。** `.env` 带 CRLF 时，`ENCRYPTION_KEY` 的值末尾会多一个 `\r`。
> 它照样通过长度校验、服务照常启动、上游 key 也能正常加解密——
> 直到你在别处用同一份 `.env` 重新部署，那时 `\r` 没了，**密钥实际变了，
> 所有已存的上游 key 全部解不开**。

## 4. DNS 解析

到域名服务商加一条 A 记录，指向服务器公网 IP：

```
类型   名称     值               TTL
A     relay    198.51.100.10    600
```

等生效，然后确认解析对了：

```bash
dig +short relay.example.com
# 198.51.100.10
```

解析没生效就启动 `--profile public` 的话，Caddy 申请证书会失败
（ACME 需要从公网访问到你的 80 端口）。

## 5. 防火墙

只需要放开 80 和 443。**`18787` 一定不要放开**——它只绑 `127.0.0.1`，
放开也没用，但别给自己留误解。

```bash
sudo ufw allow 22/tcp      # 别把自己关在外面
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status
```

```
Status: active
To                         Action      From
--                         ------      ----
22/tcp                     ALLOW       Anywhere
80/tcp                     ALLOW       Anywhere
443/tcp                    ALLOW       Anywhere
```

> [!WARNING]
> **Docker 的端口映射会绕过 ufw/firewalld。** 如果有人把 `compose.yaml` 里的
> ```yaml
> ports:
>   - "127.0.0.1:${RELAY_PORT:-18787}:18787"
> ```
> 改成 `"18787:18787"`，Docker 会插一条 iptables 规则把端口**直接暴露到公网**，
> 而 `ufw status` 显示一切正常——你在防火墙里看不到。
> 那等于把管理界面和所有上游 key 公开。
> 仓库里有 `scripts/check-deploy.sh` 守着这一行。

## 7. 验证部署

三条都要过再往下走。

**① TLS 与健康检查**

```bash
curl -s https://relay.example.com/healthz
```

```json
{"status":"ok","state":"running","version":"v1.0.0"}
```

`/healthz` 不需要任何凭据，它报的是**进程活着**，不代表有可用上游
（那要看健康看板）。

**② 转发端点要 relay key**

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  https://relay.example.com/v1/messages \
  -H 'content-type: application/json' \
  -d '{"model":"x","max_tokens":1}'
# 401
```

带上 key 应该不再是 401（此时还没配上游，会是别的错，正常）：

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  https://relay.example.com/v1/messages \
  -H "x-api-key: rk-2f8a1c4e7b0d3f6a9c2e5b8d1f4a7c0e3b6d9f2a5c8e1b4d" \
  -H 'content-type: application/json' \
  -d '{"model":"x","max_tokens":1}'
# 503   ← 没有可用上游，符合预期
```

**③ 管理面白名单生效**

从**白名单内**的机器（就是你自己）：

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://relay.example.com/admin/
# 200
```

从**白名单外**（找台别的机器，或用手机流量）：

```bash
curl -s https://relay.example.com/admin/
# 403 —— 管理界面仅限白名单 IP。设置 RELAY_ALLOW_IPS 后重启 Caddy。
```

两个都对上，才说明白名单真的在起作用。**只测第一个是不够的**——
白名单配错方向时第一个照样 200。

## 8. 配置多个中转站

数据模型是三层，理解它才能配对：

```
Upstream（物理站）        ModelName（逻辑模型）
   站 A ──┐                    │
   站 B ──┼─── Route ─────► claude-opus-4-6
   站 C ──┘   (优先级/权重)
```

- **Upstream** = 一个中转站，**全局配一次**
- **ModelName** = 客户端请求里写的那个 `model` 值
- **Route** = 把两者绑起来，带优先级。**Route 才是健康状态的最小单位**——
  「A 站的 opus 挂了但它的 gpt 还活着」只有在这个粒度上才能表达

两种配法都给出来：界面适合上手，API 适合批量。

### 8.1 用管理界面配（推荐）

浏览器打开 <https://relay.example.com/admin/>，用 `ADMIN_PASSWORD` 登录。

**第一步：加中转站**（「上游」页 → 新增）

| 字段 | 站 A 填什么 | 说明 |
|---|---|---|
| 名称 | `站A` | 自己认得就行 |
| Base URL | `https://api-a.example.com` | **根地址，不要带 `/v1`** |
| API Key | `sk-站A的真实key` | 存进库时 AES-GCM 加密 |
| 鉴权风格 | `auto` | 两个头都发，实测可用站都接受 |
| 启用 | ✅ | |

站 B、站 C 同样操作。

> [!IMPORTANT]
> **Base URL 不能带 `/v1`。** 出站路径由入站请求决定，带了会拼成
> `/v1/v1/messages` → 404，而且这个 404 很难看出根因。
> 所以在保存时就会被拒绝：
> ```
> base_url 不能带路径（收到 "https://api-a.example.com/v1"）。填根地址即可，
> 出站路径由入站请求决定；若该站确实用非标准路径，请开启 full_url_mode
> ```

**第二步：加逻辑模型**（「模型」页 → 新增）

| 字段 | 填什么 | 说明 |
|---|---|---|
| 名称 | `claude-opus-4-6` | 客户端 `model` 里写的值 |
| 协议 | `anthropic` | 对应 `/v1/messages` |
| 匹配模式 | `exact` | 精确匹配 |
| 启用 | ✅ | |

**第三步：建路由**（「路由」页 → 新增），一个模型对每个站各建一条：

| 模型 | 上游 | 优先级 | 权重 |
|---|---|---|---|
| claude-opus-4-6 | 站A | **1** | 100 |
| claude-opus-4-6 | 站B | **2** | 100 |
| claude-opus-4-6 | 站C | **3** | 100 |

**优先级 1 最高**。请求优先投 P1；P1 全部判死才降到 P2。
同优先级多个站时按 `weight` 加权随机分流。

> 想让两个站**均摊**流量，就把它们设成**同一个优先级**、权重都给 100。
> 优先级不同 = 主备；优先级相同 = 负载均衡。

### 8.2 用 API 批量配

管理 API 接受 `Authorization: Bearer <ADMIN_PASSWORD>`，没有 CSRF token，
可以直接脚本化。

先设两个变量：

```bash
ADMIN='kJ8mNp2QrS5tUv7WxY0zAb3CdE6fGh9I'
BASE='https://relay.example.com'
```

**加三个站**（`jq` 用来取回自增 ID）：

```bash
UP_A=$(curl -s -X POST "$BASE/admin/api/upstreams" \
  -H "Authorization: Bearer $ADMIN" -H 'content-type: application/json' \
  -d '{
        "name":       "站A",
        "base_url":   "https://api-a.example.com",
        "api_key":    "sk-站A的真实key",
        "auth_style": "auto",
        "enabled":    true
      }' | jq -r .id)

UP_B=$(curl -s -X POST "$BASE/admin/api/upstreams" \
  -H "Authorization: Bearer $ADMIN" -H 'content-type: application/json' \
  -d '{"name":"站B","base_url":"https://api-b.example.com","api_key":"sk-站B的key","auth_style":"auto","enabled":true}' | jq -r .id)

UP_C=$(curl -s -X POST "$BASE/admin/api/upstreams" \
  -H "Authorization: Bearer $ADMIN" -H 'content-type: application/json' \
  -d '{"name":"站C","base_url":"https://api-c.example.com","api_key":"sk-站C的key","auth_style":"auto","enabled":true}' | jq -r .id)

echo "站A=$UP_A 站B=$UP_B 站C=$UP_C"
# 站A=1 站B=2 站C=3
```

创建成功的响应长这样——注意 **`api_key` 被脱敏了**，管理接口永远不回显真 key：

```json
{
  "id": 1,
  "name": "站A",
  "base_url": "https://api-a.example.com",
  "auth_style": "auto",
  "full_url_mode": false,
  "enabled": true,
  "l1_path": "/v1/models",
  "created_at": 1785722811460,
  "updated_at": 1785722811460,
  "api_key": "*********",
  "api_key_is_set": true
}
```

**加逻辑模型：**

```bash
MN=$(curl -s -X POST "$BASE/admin/api/model-names" \
  -H "Authorization: Bearer $ADMIN" -H 'content-type: application/json' \
  -d '{
        "name":       "claude-opus-4-6",
        "protocol":   "anthropic",
        "match_mode": "exact",
        "enabled":    true
      }' | jq -r .id)
echo "模型 id=$MN"
```

响应会补上探活默认值：

```json
{
  "id": 1,
  "name": "claude-opus-4-6",
  "protocol": "anthropic",
  "match_mode": "exact",
  "is_fallback": false,
  "probe_prompt": "1+1=?",
  "probe_max_tokens": 1,
  "enabled": true,
  "created_at": 1785722811472,
  "updated_at": 1785722811472
}
```

**建三条路由（优先级 1/2/3）：**

```bash
for pair in "$UP_A:1" "$UP_B:2" "$UP_C:3"; do
  up="${pair%:*}"; prio="${pair#*:}"
  curl -s -X POST "$BASE/admin/api/routes" \
    -H "Authorization: Bearer $ADMIN" -H 'content-type: application/json' \
    -d "{
          \"model_name_id\":   $MN,
          \"upstream_id\":     $up,
          \"priority\":        $prio,
          \"weight\":          100,
          \"max_concurrency\": 0,
          \"enabled\":         true
        }" | jq -c '{id, upstream_id, priority}'
done
```

```json
{"id":1,"upstream_id":1,"priority":1}
{"id":2,"upstream_id":2,"priority":2}
{"id":3,"upstream_id":3,"priority":3}
```

**确认配置：**

```bash
curl -s "$BASE/admin/api/routes" -H "Authorization: Bearer $ADMIN" | jq -c '.[]'
```

### 8.3 一个模型名，多个协议

如果你还要用 OpenAI 协议的站，**再建一个 ModelName**（协议不同就是不同的逻辑模型）：

```bash
curl -s -X POST "$BASE/admin/api/model-names" \
  -H "Authorization: Bearer $ADMIN" -H 'content-type: application/json' \
  -d '{"name":"gpt-4o","protocol":"openai-chat","match_mode":"exact","enabled":true}'
```

三种协议对应关系：

| `protocol` | 端点 |
|---|---|
| `anthropic` | `POST /v1/messages` |
| `openai-responses` | `POST /v1/responses` |
| `openai-chat` | `POST /v1/chat/completions` |

**入站路径 = 出站路径，不做协议转换。** 客户端打哪个端点，就转发到上游的同名路径。

### 8.4 前缀匹配与兜底

不想为每个模型名单独建配置时，有两个办法：

**前缀匹配**——`match_mode: "prefix"`，把 `claude-` 开头的全部收进来：

```bash
curl -s -X POST "$BASE/admin/api/model-names" \
  -H "Authorization: Bearer $ADMIN" -H 'content-type: application/json' \
  -d '{"name":"claude-","protocol":"anthropic","match_mode":"prefix","enabled":true}'
```

**兜底**——`is_fallback: true`，任何没匹配上的 model 都走它（每协议至多一个）：

```bash
curl -s -X POST "$BASE/admin/api/model-names" \
  -H "Authorization: Bearer $ADMIN" -H 'content-type: application/json' \
  -d '{"name":"兜底","protocol":"anthropic","match_mode":"exact","is_fallback":true,"enabled":true}'
```

匹配顺序是：**精确 → 前缀（最长优先）→ 兜底 → 404**。

所以同时配了 `claude-opus` 与 `claude-opus-5` 两个前缀时，
入站 `claude-opus-5-thinking` 会命中更具体的 `claude-opus-5`。

## 9. 验证选路与健康

配完之后**先看健康看板**，别急着接客户端——配错了的话，从客户端那头看到的
只是一个笼统的错误。

### 9.1 健康看板

```bash
curl -s "$BASE/admin/api/health" -H "Authorization: Bearer $ADMIN" | jq
```

```json
{
  "routes": [
    {
      "route_id": 1,
      "model_name": "claude-opus-4-6",
      "upstream": "站A",
      "priority": 1,
      "weight": 100,
      "enabled": true,
      "state": "alive",
      "selectable": true
    },
    {
      "route_id": 3,
      "model_name": "claude-opus-4-6",
      "upstream": "站C",
      "priority": 3,
      "enabled": true,
      "state": "dead",
      "selectable": false,
      "reason": "判死：配置或鉴权错误（401 Unauthorized）"
    }
  ],
  "summary": { "total": 3, "selectable": 2 }
}
```

看两个字段就够了：

- **`selectable`** —— 「现在这一刻选路会不会考虑它」的最终答案
- **`reason`** —— 不可选时的人话原因

> [!NOTE]
> **`state: "unknown"` 是可用的**，不是「有问题」。这是乐观策略：
> 重启后所有 Route 都是 unknown，否则一重启就全站不可用。
> 判断能不能用请看 `selectable`，不要看 `state`。

`reason` 的几种典型值：

| reason | 含义 | 怎么办 |
|---|---|---|
| `判死：配置或鉴权错误（...）` | key 错、URL 错 | 改配置。等它自己恢复没用 |
| `判死：服务不可用（...）` | 站真的挂了 | 等探活自动恢复 |
| `限流冷却中` | 撞到 429 | 等冷却结束 |
| `Upstream 已手动停用` | 你自己关的 | 打开它 |

### 9.2 手动探活单个站

配完立刻想知道某个站通不通，不用等探活周期：

```bash
curl -s -X POST "$BASE/admin/api/routes/1/probe" \
  -H "Authorization: Bearer $ADMIN" | jq
```

成功：

```json
{
  "route_id": 1,
  "l1": { "verdict": "ok", "status": 200, "ttft_ms": 0 },
  "l2": { "verdict": "ok", "status": 200, "ttft_ms": 1840 },
  "state": "alive"
}
```

L1 不通时 L2 会被跳过（站都连不上，探模型只是白等一次超时）：

```json
{
  "route_id": 3,
  "l1": { "verdict": "fatal", "status": 401, "ttft_ms": 0, "error": "401 Unauthorized" },
  "l2": null,
  "l2_skipped": "L1 未通过，已跳过 L2（站连不上时探模型只是白等一次超时）",
  "state": "dead"
}
```

**两级探活的分工**：L1 是传输层（打 `/v1/models`，零 token），
L2 是模型层（真发一次 `1+1=?`，约 1 token）。
L1 通了才探 L2——这样绝大多数探活是不花钱的。

### 9.3 打一次真实请求

```bash
curl -s https://relay.example.com/v1/messages \
  -H "x-api-key: rk-2f8a1c4e7b0d3f6a9c2e5b8d1f4a7c0e3b6d9f2a5c8e1b4d" \
  -H 'content-type: application/json' \
  -d '{
        "model": "claude-opus-4-6",
        "max_tokens": 64,
        "messages": [{"role":"user","content":"说三个字"}]
      }' | jq
```

通了就说明整条链路（TLS → Caddy → relay-gate → 选路 → 上游）都对了。

### 9.4 验证故障自动切换

这是这个项目存在的理由，值得亲手验一次。把优先级最高的站停用：

```bash
curl -s -X PUT "$BASE/admin/api/upstreams/$UP_A" \
  -H "Authorization: Bearer $ADMIN" -H 'content-type: application/json' \
  -d '{"enabled":false}'
```

再打一次 9.3 的请求——**应该照常返回**，因为流量已经落到站 B。
在「请求日志」页能看到它走了哪个站。

验证完记得打开：

```bash
curl -s -X PUT "$BASE/admin/api/upstreams/$UP_A" \
  -H "Authorization: Bearer $ADMIN" -H 'content-type: application/json' \
  -d '{"enabled":true}'
```

> `PUT` 是**部分更新**：没提供的字段保持原样。
> 尤其 `api_key` 留空表示「不改 key」——因为你 GET 拿到的是脱敏值，
> 不能当真 key 回写。

## 10. 接入 Claude Code

在**你自己的电脑**上（不是服务器）设两个环境变量：

```bash
export ANTHROPIC_BASE_URL=https://relay.example.com
export ANTHROPIC_AUTH_TOKEN=rk-2f8a1c4e7b0d3f6a9c2e5b8d1f4a7c0e3b6d9f2a5c8e1b4d

写进 shell 配置持久化：

cat >> ~/.zshrc <<'EOF'

```

Windows PowerShell：

```powershell
[Environment]::SetEnvironmentVariable('ANTHROPIC_BASE_URL', 'https://relay.example.com', 'User')
[Environment]::SetEnvironmentVariable('ANTHROPIC_AUTH_TOKEN', 'rk-2f8a...', 'User')
# 重开终端生效
```

然后正常启动：

```bash
claude
```

> [!IMPORTANT]
> **两个都设会让请求直接失败（401），不是"其中一个生效"。**
> SDK 会把 `x-api-key` 和 `Authorization` 两个头一起发出去，API 拒收。
> 如果你之前设过 `ANTHROPIC_API_KEY`，先取消它：
> ```bash
> unset ANTHROPIC_API_KEY
> ```
> **注意 `ANTHROPIC_API_KEY=""` 不算取消**——空值仍然占着优先级位置，
> 照样会被当成"设了"。必须真的 `unset`。

凭据解析顺序是 `ANTHROPIC_API_KEY` → `ANTHROPIC_AUTH_TOKEN` → 本地登录凭据，
先命中的生效。网关三个位置都认（`x-api-key` / `Authorization: Bearer` / `Api-Key`），
所以只设 `ANTHROPIC_API_KEY` 指向网关同样能用——**二选一，别同时设**。

> [!TIP]
> 如果你本机用 `claude` 登录过官方账号，Claude Code 可能提示凭据冲突。
> 保留一个即可：想走网关就用环境变量并在 Claude Code 里 `/logout`。

**确认真的走了网关**：随便问一句，然后去管理界面的「请求日志」页看有没有新记录。
没有就说明请求没打过来。

## 11. 日常运维

### 备份

**只需要 `data/` 一个目录**——上游配置、样本、请求日志、健康历史全在里面。

```bash
docker compose stop relay-gate
tar czf ~/relay-backup-$(date +%F).tar.gz data/
docker compose start relay-gate
```

停机再备是为了避开 SQLite 的 WAL 半写状态。停机窗口只有几秒。

不想停机的话，用一个**临时容器**做 SQLite 在线备份（不要往运行中的容器里
`apk add`——那会污染容器、需要出网，且容器重建后就没了）：

```bash
docker run --rm -v "$PWD/data:/data" alpine:3.21 sh -c \
  'apk add --no-cache sqlite >/dev/null && \
   sqlite3 /data/relay-gate.db ".backup /data/online-backup.db"'

mv data/online-backup.db ~/relay-online-$(date +%F).db
```

> [!CAUTION]
> **`data/` 与 `ENCRYPTION_KEY` 必须一起备份，且分开存放。**
> 只有 `data/` 没有密钥 = 上游 key 全是解不开的密文；
> 两者放同一个地方 = 一起泄露时加密等于没做。

加个每天自动备份（注意 cron 里的 `%` 要转义）：

```bash
crontab -e
```

```cron
0 4 * * * cd /home/you/relay-gate && tar czf /home/you/backups/relay-$(date +\%F).tar.gz data/ && find /home/you/backups -name 'relay-*.tar.gz' -mtime +14 -delete
```

### 升级

```bash
cd relay-gate
git pull
docker compose --profile public up -d --build
```

数据库迁移在启动时自动跑。升级前先备份。

### 改配置

改 `.env` 后必须重建容器（`restart` 不会重新读 env_file）：

```bash
docker compose --profile public up -d
```

改管理界面里的配置（上游、路由、设置）**即时生效，不用重启**。

### 临时停止转发

不想停容器、只想暂停转发（比如额度快用完了）：

```bash
curl -s -X POST "$BASE/admin/api/state" \
  -H "Authorization: Bearer $ADMIN" -H 'content-type: application/json' \
  -d '{"state":"paused"}'
# {"state":"paused"}
```

暂停期间转发端点返回 503 并带 `X-Relay-State: paused` 头。
**这个状态跨重启保持**——一个你刻意停掉的网关不会在容器重启后偷偷开始转发。

恢复：

```bash
curl -s -X POST "$BASE/admin/api/state" \
  -H "Authorization: Bearer $ADMIN" -H 'content-type: application/json' \
  -d '{"state":"running"}'
```

## 12. 故障排查

### 管理界面 403

最常见的原因是**你的出口 IP 变了**（家宽多为动态 IP）。

```bash
curl -s ifconfig.me                       # 当前 IP
grep RELAY_ALLOW_IPS .env                 # 白名单里写的
```

对不上就更新再重建：

```bash
sed -i "s/^RELAY_ALLOW_IPS=.*/RELAY_ALLOW_IPS=$(curl -s ifconfig.me)/" .env
docker compose --profile public up -d
```

**IP 经常变**的话，两个办法：把整段家宽网段加进白名单（`198.51.100.0/24`），
或者干脆不暴露管理面，改用 SSH 隧道：

```bash
# 本机执行，然后浏览器开 http://127.0.0.1:18787/admin/
ssh -L 18787:127.0.0.1:18787 you@your-server
```

隧道方式最安全——管理面完全不经公网。

### 证书申请失败

```bash
docker compose logs caddy | grep -iE 'error|failed'
```

| 现象 | 原因 |
|---|---|
| `no such host` | DNS 没生效，`dig +short 你的域名` 确认 |
| `timeout during connect` | 80 端口没开，或云厂商安全组没放行 |
| `too many certificates` | 撞上 Let's Encrypt 限流（同域名每周 5 张）。等一周，或先用 `--profile` 默认模式调试 |

云服务器要注意：**除了 ufw，云厂商控制台的安全组也要放行 80/443**。
两层都要开。

### 容器起不来

```bash
docker compose logs relay-gate | tail -20
```

| 日志 | 原因 |
|---|---|
| `缺少必需的环境变量` | `.env` 没填全，照错误提示补 |
| `unable to open database file (14)` | `data/` 权限问题，见下 |
| `bind: address already in use` | 18787 被占，改 `RELAY_PORT` |

数据目录权限问题：

```bash
ls -ld data/
sudo chown -R 10001:10001 data/
docker compose --profile public up -d
```

正常情况下 entrypoint 会自动修属主，需要手动处理说明容器是以非 root 启动的
（比如你在 compose 里加了 `user:`）。

### 所有站都判死

```bash
curl -s "$BASE/admin/api/health" -H "Authorization: Bearer $ADMIN" \
  | jq '.routes[] | {upstream, state, reason}'
```

- `reason` 里带 **401/403** → key 填错了，或 `auth_style` 不对，试试改成
  `x-api-key` 或 `bearer`
- `reason` 里带 **404** → `base_url` 多半带了 `/v1`
- 全部 **connection refused / timeout** → 服务器出网有问题，
  或者站真的都挂了。在服务器上直接 `curl` 一下上游确认

容器内测试出网：

```bash
docker compose exec relay-gate wget -qO- https://api-a.example.com/v1/models
```

### 长思考被中途掐断

如果公网模式下长回复总在几分钟处断掉，而本机直连（`127.0.0.1:18787`）正常，
那就是 Caddy 的超时。`deploy/Caddyfile` 里已经放宽到 30 分钟：

```caddyfile
transport http {
    response_header_timeout 30m
    read_timeout 35m
    write_timeout 35m
}
```

这段配置通过了 `caddy validate`（CI 每次都验），但**运行时行为尚未用真实长思考流量验证过**。
真遇到这个问题，第一个该看的就是这里——可能需要改在 global options 的
`servers { timeouts { ... } }`。遇到了请开 issue。

### 请求日志与样本

排查「某次请求到底发生了什么」，管理界面的两个页面比日志有用得多：

- **请求日志** —— 每次尝试一行，含被重试丢弃的那些。能看到走了哪个站、
  重试了几次、每次的状态码
- **样本浏览器** —— 完整留档入站请求、实际出站请求、上游响应。
  用来核对「透传到底改没改字节」

> [!WARNING]
> **样本含明文的完整对话原文。** 库文件权限是 0600，但别把 `data/` 随便拷来拷去，
> 也别在 issue 里贴样本内容。

### 关键 Settings

全部字段见管理界面的「设置」页，这里只列最常调的。

| 字段 | 默认 | 说明 |
|---|---|---|
| `real_first_token_sec` | `1200` | 真实请求首 Token 超时。**硬下限 300** |
| `real_total_sec` | `1800` | 必须 ≥ 首 Token 超时 |
| `l2_first_token_sec` | `120` | 探活首 Token 超时，与真实请求**独立** |
| `l1_interval_dead_sec` | `20` | 死站 L1 重探周期 |
| `l2_interval_dead_sec` | `30` | 死站 L2 重探周期 |
| `fail_threshold` | `2` | 连续失败几次判 dead |
| `ok_threshold` | `2` | 连续成功几次升 alive |
| `retry_max_attempts` | `3` | **总尝试次数**（含第一次），上限 5 |
| `sample_enabled` | `true` | 样本留档 |
| `request_log_enabled` | `true` | 请求日志 |

> [!NOTE]
> **「容忍长思考」与「快速判死」能同时成立**，靠的就是探活超时与真实请求超时分开。
> 想让死站更快被发现，调 `l2_first_token_sec`，
> **不要**调 `real_first_token_sec`——后者调小会把正常的长思考拦腰砍断，
> 还会因此把好站判死。所以它有 300 秒的硬下限，低于这个值直接拒绝保存。

## 14. 已有 nginx + 证书的服务器（一键脚本）

**这个场景**：服务器上已经有一个 nginx 占着 80/443，证书与自动续期都已就位
（典型如：一台腾讯云 Ubuntu 上 nginx 容器同时反代多个域名，certbot 容器
定期续期）。前 13 章的 Caddy 方案要独占 80/443 并自己申请证书，和现有
架构直接打架——所以这里**不起 Caddy**，改由现有 nginx 反代。

> [!IMPORTANT]
> 章节 14 的路径是「**不用编辑任何文件**」：域名、IP 白名单这些默认值都写在
> 脚本里，凭据由脚本随机生成。中转站、模型、路由这些**业务配置本来就是
> 网页管理界面**配的（见 [8.1](#81-用管理界面配推荐)）。
> 唯一需要你动手的是一次 DNS 解析。

### 14.1 与 Caddy 方案的区别

| | 前 13 章（Caddy） | 本章（nginx 一键脚本） |
|---|---|---|
| TLS 与证书 | Caddy 自动申请 | 复用现有证书，certbot 扩 SAN |
| 反代入口 | `relay-gate-caddy` 容器 | 现有 nginx 容器 |
| 网关绑定 | `127.0.0.1:18787` | 相同 |
| 管理面保护 | Caddy `remote_ip` 白名单 | nginx `allow` 白名单 |
| 改动面 | 无 | 新增 1 个 conf + 扩 1 张证书 |
| 适合 | 新服务器、没有在跑的东西 | 已有 nginx + 多域名证书 |

安全性与 Caddy 方案等价：网关容器只绑 `127.0.0.1`，**公网无法直连**，
白名单不会被绕过。

### 14.2 前置条件

- 已有 nginx（容器或宿主机），80/443 正常服务，`proxy_pass` 能到宿主机端口
  （nginx 容器需加 `--add-host host.docker.internal:host-gateway`）
- 已有 certbot（容器或宿主机）和一张含现有域名的证书
- 本机可执行 `curl` / `docker` / `git` / `openssl`
- 转发端点与管理面的公网入口都走一个**新子域名**（如 `relay.ienvie.top`）

> [!WARNING]
> **「新域名 → 新 location」是两个方案的唯一共同形状。** 别把网关挂到
> 已有站点（如 `sub2api.example.com`）的路径下——location 嵌套与证书
> 都会变得难维护。新开一个子域名，独立 server 块，干净利落。

### 14.3 一次 DNS 解析（唯一要你动手的）

到 DNS 控制台（腾讯云 DNSPod 网页）给主域加一条 A 记录：

| 主机记录 | 记录类型 | 记录值 |
|---|---|---|
| `relay` | A | 服务器的公网 IP |

解析生效后（通常几分钟），`dig +short relay.ienvie.top` 应返回该 IP。

### 14.4 一条命令部署

**白名单先查好**：管理面只允许你的 IP 访问。在你**自己电脑**上执行：

```bash
curl -s ifconfig.me
# 203.0.113.4   ← 记下这个，填到下面命令的 RELAY_ALLOW_IPS
```

> [!IMPORTANT]
> **填的是你自己电脑的出口 IP，不是服务器的。** 在服务器上执行
> `curl ifconfig.me` 拿到的是服务器自己的 IP —— 拿它当白名单，
> 你从家里/办公室访问管理界面必被 403。脚本会强制要求
> `RELAY_ALLOW_IPS` 非空，空值直接中止，不会留「管理面全开放」的状态。

在服务器上执行（把 `<你电脑的出口IP>` 换成上一步查到的）：

```bash
RELAY_ALLOW_IPS="<你电脑的出口IP>" \
  curl -sSL https://raw.githubusercontent.com/279814/relay-gate/main/scripts/deploy-nginx.sh | sh
```

脚本做的事（每一步都有输出）：

1. `git clone`（或 `pull`）仓库到 `$HOME/relay-gate`，生成 `.env`——
   三项必填凭据（`ENCRYPTION_KEY` / `RELAY_KEYS` / `ADMIN_PASSWORD`）
   用 `openssl rand` 随机生成，文件权限 0600
2. 构建并启动 relay-gate 容器（**不启 Caddy**，不碰 80/443 的现有占用）
3. 生成 nginx 反代配置并 reload：
   - 80 先开 `/.well-known/acme-challenge/` 验证口（证书下来前 443 用现有证书，老站不受影响）
   - `/admin` 按 IP 白名单（`RELAY_ALLOW_IPS`，必填），兜底 `deny all`
   - 转发端点不限 IP，靠 `RELAY_KEYS` 鉴权
   - 长思考不掐断：`proxy_read_timeout 35m` + `proxy_buffering off`
4. `certbot --expand` 把新域名并入现有证书（`--cert-name` 固定证书名，
   **老域名一个不少**，现有自动续期 cron 不用改）
5. 自验证：`/healthz` 200、管理面白名单外 403、证书 SAN 含新域名

**改默认值重跑**（比如想让家里和公司两个 IP 都能进管理面）：

```bash
RELAY_ALLOW_IPS='203.0.113.4 198.51.100.0/24' \
  curl -sSL https://raw.githubusercontent.com/279814/relay-gate/main/scripts/deploy-nginx.sh | sh
```

脚本环境变量：`RELAY_DOMAIN`（默认 `relay.ienvie.top`）、`RELAY_ALLOW_IPS`
（**必填**，自己电脑的出口 IP，空格分隔，支持 CIDR）、`RELAY_DIR`（默认
`$HOME/relay-gate`）、`NGINX_CONTAINER`（默认 `nginx`，空 = 宿主机 nginx）、
`CERTBOT_CONTAINER`（默认 `certbot`，空 = 宿主机 certbot）、`CERT_LIVE`
（默认 `/etc/letsencrypt/live/ienvie.top`，即现有证书的 live 目录）。

### 14.5 配置中转站（网页操作，无文件编辑）

管理界面：`https://relay.ienvie.top/admin/`，用 `.env` 里的 `ADMIN_PASSWORD` 登录。
流程与 [8.1](#81-用管理界面配推荐) 完全一样，三步：

1. **上游**页 → 新增：每个中转站一条（名称 / Base URL 根地址不带 `/v1` / API Key / 鉴权风格 auto）
2. **模型**页 → 新增：客户端请求里写的 `model` 值（如 `claude-opus-4-6`，协议 anthropic）
3. **路由**页 → 新增：把每个模型 × 每个站绑起来，填优先级（1 最高，主备）
   与权重（同优先级 = 加权分流）

配完管理界面的「健康看板」会显示每个站/模型的状态，[9.3](#93-打一次真实请求)
给了一条真实请求示例可直接验证。

### 14.7 运维差异（对比前 13 章）

| 操作 | Caddy 方案 | 本章方案 |
|---|---|---|
| 升级 relay-gate | `cd ~/relay-gate && git pull && docker compose build && docker compose up -d` | 相同 |
| 管理面白名单换 IP | 改 `.env` + 重启 Caddy | 编辑生成的 conf 的 `allow` 行 + reload nginx |
| 证书续期 | Caddy 自动 | 现有 certbot cron（已含新域名） |
| 看转发日志 | `docker logs relay-gate-caddy` | `docker logs nginx` + `docker logs relay-gate` |
| 网关重启用哪条 | `docker compose --profile public up -d` | `docker compose up -d`（不起 Caddy） |

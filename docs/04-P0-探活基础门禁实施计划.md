## 1. P0 交付结果

P0 完成后必须同时得到以下可独立验收的结果：

1. 真实请求、L1、L2、`count_tokens` 共用同一个 EndpointResolver 和 TransportManager；
2. `l1_connect_sec` 与 `l2_connect_sec` 真正覆盖 DNS、TCP、代理 CONNECT 和 TLS 建连阶段；
3. `/v1/models`、`/v1/messages`、`/v1/responses`、`/v1/chat/completions`、`/v1/messages/count_tokens` 都能由版本化 Probe Recipe 描述；
4. 支持完全自定义、多值请求头和任意字节请求体，Secret 只通过引用渲染；
5. SSE、NDJSON、普通 JSON 使用统一增量解析器，HTTP 200、`error:null`、ping、空 delta 和 `output_tokens:0` 不会被误判为成功；
6. Reachability、EndpointCapability 和 RouteHealth 不再混为一个状态；
7. Active 调度满足站内串行、全局限流、single-flight、完成后计时和 jitter；
8. Lazy 模式不会产生任何周期合成请求；
9. CalibrationRun 的每个候选都是可见、单独计费的 ProbeExecution，没有隐藏重试；
10. 管理 API 和页面可以配置 Endpoint、Recipe、Probe Secret、主动/懒探活，并查看执行、能力与成本；
11. 旧配置继续工作，未审核迁移项不会被静默猜测或静默发布；
12. 离线 fixture 100% 通过，在线矩阵能把“原生客户端也失败”和“网关兼容性回归”分开。

P0 不交付 RecoveryGate、三档真实请求重试、Keyring、IP HTTPS、内容安全扫描或流量转换。这些分别属于 P1–P4。P0 只为它们留下已确认的数据字段和接口，不实现空壳服务。

`legacy_exact` 只由 schema 1→2 migration 创建，管理 API 禁止新建、修改或清除 NeedsReview；Endpoint 只引用 `legacy_full_url`，完整 URL 由现有 Cipher 加密保存，读取 API 和 ProbeSnapshot 只给 ID/revision/mask/fingerprint。Resolver 在单次真实 Attempt 前按 expected revision 解密，对它不拼 canonical path，但仍执行 scheme、Host、Secret 和 query 保真校验；synthetic 按下文规则 fail closed。P0 UI 只显示只读迁移诊断，审核转换、同源 override 编辑和多 Endpoint 拆分完整流程都属于 P1。`ProbeUpstreamConfig` 刻意没有 APIKey；ProbeSnapshot 中也只使用该类型。

`model.Settings` 按规范增加 `RealResponseHeaderSec`、`RealFirstByteSec`、`RealFirstSemanticSec`、`L2ResponseHeaderSec`、`L2FirstByteSec`、`L2FirstEventSec`、`L2FirstSemanticSec`、`L2IdleSec`、`CountTokensConnectSec`、`CountTokensTotalSec`。旧 JSON 的 `real_first_token_sec`、`l2_first_token_sec`、`count_tokens_sec` 只由 Store 专用 `DecodeLegacySettings` 白名单兼容解码器读取并展开：它从默认值基底开始，新键优先于旧键，拒绝未知键；保存时只写新字段。不得给 `model.Settings` 自定义 `UnmarshalJSON`，否则会绕过管理 API 外层 `DisallowUnknownFields`；API 使用只含新字段的 DTO，并明确拒绝 legacy key。默认值和硬下限逐项使用 `docs/01-需求与设计.md` 第 7.4 节，不允许以同一个 timeout 替代多个阶段。

旧全局 `probe_enabled` 只在 v2 legacy decoder/backfill 中读取，用于一次性生成每 Upstream ProbeMode；v3 运行时和管理 API 不再接受或查询该键。Scheduler 的唯一长期探活决策是 Upstream.ProbeMode，服务总闸只看 RunState，禁止保留第三个全局布尔真相。P0-17 在所有调用迁移后删除 Settings.ProbeEnabled 与旧 scheduler 分支，但 v1/v2 migration reader 仍能解析历史 JSON。

### 4.3 EndpointResolver

新增 `internal/outbound/resolver.go`：

~~~go
type ValueResolver = probetemplate.ValueResolver
type ResolvedValue = probetemplate.ResolvedValue

type ResolveInput struct {

    ResolveLegacyURL(ctx context.Context, id, expectedRevision int64) (plain []byte, err error)

type Resolver struct{ /* hasher */ }

func NewResolver(hasher RequestURLHasher) *Resolver
func (r *Resolver) Resolve(ctx context.Context, in ResolveInput) (ResolvedTarget, error)

~~~

解析器只接受 `http` 或 `https`，拒绝 userinfo 和 fragment。override 必须与 `base_url` 的 scheme、hostname 和有效端口相同。FixedQueryTemplate 保留常量字节、顺序、重复键和空值；占位符只能完整占据 `name=<placeholder>` 的 value，不能出现在参数名、值片段或裸 query 中。渲染时对占位符原始字节按 RFC 3986 unreserved 集做 percent-encode（大写十六进制，空格为 `%20`，非 UTF-8 按原 byte 编码），因此 Secret 中的 `&`、`=`、`#`、`%` 不能改变 query 结构。渲染后的固定 query 放在前，入站 RawQuery 原样放在后；两者均非空时只插入一个 `&`，不解析、不排序、不去重。legacy_exact 的已捕获 RawQuery 不再次编码。

`ResolvedURLHash` 是配置语义的 SHA-256：canonical 输入包括 scheme、authority、escaped path、配置的 FixedQueryTemplate、Secret 引用名与 revision、RequestHost，不含 Secret 明文，也不含每个客户端请求不同的 IncomingRawQuery。legacy_exact 不把解密后的 path/query 输入裸 SHA，而只纳入 LegacyFullURL ID、revision 与其 keyed fingerprint；低熵 query 不能形成离线枚举 oracle。`RequestURLHash` 只作为单次 execution/log 的不可逆证据，使用由现有加密根经域分离派生的 HMAC-SHA-256 对最终实际 URL 求摘要，格式携带 digest key ID；禁止用裸 SHA-256。它不进入 EndpointCapability 身份。这样 query 配置改变会失效 Capability，而普通客户端 query 不会把一个端点抖成另一份全局能力状态。

`ResolvedValue`/`ValueResolver` 是 `probetemplate` 类型别名，保证 Store、Resolver 和模板渲染共享一份值契约且不存在 `store→outbound→probetemplate→store` 环。Resolver 只消费该窄接口，不拥有模板语言。

`outbound.Provider` 满足 TargetProvider，只从 EndpointConfigSource 取得单个 Endpoint，再把调用方固定的 Upstream/Values 与统一 LegacyURLResolver 交给 Resolver；它不自行选 Route、Recipe、模型或认证。P0-03 使用 Store-backed EndpointConfigSource，P0-10 改为同代 ConfigBundle adapter；两者共享同一 Provider/Resolver，不复制 URL 规则。

持久化只有一个固定 query 来源：`URLOverride` 列规范化为同源且不含 query/fragment 的 URL，原始 fixed query 只存 `FixedQueryTemplate`。管理 API 若只在 url_override 中提交 query，service 按第一个 `?` 机械拆分并逐字节保存 RawQuery；若同时提交 URL query 与 FixedQueryTemplate 则返回 400，禁止隐式拼接。读取 API 返回规范化后的两个字段。legacy_exact 不做此拆分，而以加密 exact URL 走独立兼容分支。

SecretRevision 按 Name 排序后编码，并同时包含 Secret ID、current revision 与 resolved 状态；同名删除重建即使 revision 又从 1 开始也必须得到不同 Token，unresolved required ref 不能因名称相同被视为复活。SemanticRevision 同时编码 EndpointID 与 EndpointRevision；Endpoint 被删除后同 kind 新建，即使 revision 又从 1 开始，旧在途结果也只能 config_stale。Observation Token 使用带格式版本的稳定二进制编码再做 SHA-256。调用方必须先用实际 EvidenceKind、Endpoint、TimeoutProfile 从同一 Settings snapshot 构造 policy；非法组合失败，不能退回全局 hash。`ProbeSettingsFingerprint` 只编码该 Attempt 实际阶段预算、parser 版本/上限与 Capability 三类 TTL，绝不编码 Reachability 连续阈值；`ReachabilitySettingsFingerprint` 只编码同一 Attempt 实际 effective connect/header/outer-total 预算与连续成功/失败阈值，绝不编码 Capability TTL。任一侧 policy 改变都不能使另一侧 token 变化。全局并发、调度间隔、jitter、piggyback、sample/log/保留期和真实请求重试等不改变一次已完成证据的字段不使状态失效；修改别的 Endpoint/purpose timeout 也不误伤当前结论。Expectation 持久化 PolicySelector，Store 用 DB-current Settings 重建同一 policy 后再比较 fingerprint。setting 行的单调 revision 只用于管理 API 乐观并发。P0 的 `RequestTransform` 固定为 0，但字段从第一版就存在，避免 P4 改变 Token 格式。Store、livecfg、probe 和 health 都调用 `revisioncodec`，Store 不得导入 health/probe。

`NewProbeEvidenceHash` 对“事务前不可变输入”使用独立格式版本和显式字段白名单：两份 expectation、两份 reduction policy、ObservationOrder、完整 Decision（含 success/semantic/normal-end/partial/candidate disposition、RetryAfterUntil 与 observed usage）、identity/target、TLS/GotConn/响应阶段时间、字节/Token计数、URL hash、ExpectedCancel、real shape hash/不可学习 reason与 observer incomplete 证据。它明确排除 EvidenceHash 自身、两个 ApplyDisposition 和任何 DTO 派生值；nil expectation 与 not-applicable、learnable 与 unavailable 有固定且不同的编码，slice 排序规则固定，禁止直接 hash Go struct/JSON。新增持久字段时必须显式决定是否提升 evidence format，并更新 golden vectors。

两个 `CostEvidenceFrom...` 是唯一允许的 delta 映射。execution 只接受 synthetic trigger：`SentAtMS>0` 表示实际进入 RoundTrip并令 Requests=1，否则 Requests及全部 outcome/Token delta为 0；已发送时 Decision.Success→Succeeded=1，ErrorIgnored→Canceled=1，其余→Failed=1，三者恰有一个为 1；EstimatedInputTokens/ObservedOutputTokens 取持久 execution 非负值，`ExpectedCancel && SemanticSeen` 才令 CanceledAfterSemantic=1，PiggybackL2Saved 固定 0。piggyback 输入固定 Requests/outcome/Token delta全 0、PiggybackL2Saved=1。映射拒绝 real_traffic、客户端 count_tokens、非法枚举、负数和自相矛盾值。

`NewProbeCostEvidenceHash` 使用独立 domain `relay-gate/probe-cost-evidence/v1` 和 `ProbeCostEvidenceV1` 字段声明顺序的稳定二进制编码；DayUTC 必须是规范 UTC `YYYY-MM-DD`，Route/Upstream 使用规范零值。哈希明确排除 event ID、execution ApplyDisposition、阶段时间、DTO 派生值和其他不进入 daily rollup 的字段；同 event ID 只比较 format version+hash。codec 提供每个纳入字段、nil/zero边界和两个映射器的 golden vector；改变任一纳入字段必须改变 hash，改变任一排除字段不得改变 hash，字段增删或语义变化必须升级版本，不能直接 hash Go struct/JSON。

SemanticTarget 的 upstream scope 要求 UpstreamID 非零、RouteID 为零，不混入 ModelName/Route revision；route scope 要求 RouteID 非零并校验其 UpstreamID，一并纳入 ModelName/Route revision。Snapshot 与 Store 使用同一个 Validate/规范编码，禁止以 routeID=0 或“随便挑一条 Route”代表站级能力。

Store 只负责在事务内锁定/读取 current row、校验 expectation/order、调用注入的纯 reducer 并持久化返回值；阈值、TTL、错误分类和状态转换由 health/probe 层的 reducer 实现，Store 不导入 probe/health、不自行承载探活业务规则。Reducer 必须无 I/O、确定性、不可持有事务外引用；panic/error 使整个事务回滚。两份 reduction policy 来自同一 Settings snapshot：Reachability 只含连续成功/失败阈值，Capability 只含三类 TTL，分别参与自己的 fingerprint，互不因无关字段变化而失效。

同一 `(upstream, endpoint)` 允许多个 family/shape candidate 和历史行；身份唯一键使用 `(upstream_id,endpoint,client_family,shape_hash)`，`Revision` 是可执行 shape/status/Secret refs 的语义与乐观并发版本，另以 partial unique index 保证每个 `(upstream_id,endpoint)` 至多一个 `status=tested` 的 active fallback。Learner 不能 UPSERT 覆盖 tested 行；相同 candidate shape hash 只原子增加 typed model/API 可观测的 `LastSeenAt/SeenCount`，这种 telemetry 写不增加 Revision，因此繁忙站的同形状真实请求不会让在途 explicit profile test 无故 stale；不同 shape、Secret refs 或 status 改变必须产生新语义 revision/identity。每个 `(upstream,endpoint,family)` 最多保留 8 个未测试 candidate、每个 Upstream 最多 64 个、数据库全局最多 2048 个。上限在同一个 SQLite 写事务中计数；达到时只可原子替换 `LastSeenAt` 最旧且没有 execution/active ref 的未测试 candidate，不存在可替换行就丢弃新 candidate并增加受限诊断计数。重启仍受数据库计数约束；tested、disabled、有测试历史和 immutable execution 引用的行绝不自动删除或覆盖。active Secret refs 只跟随 tested binding。上述上限是 P0 固定常量，P4 若开放配置必须同时进入 Settings/API/UI/测试。

`internal/health/observation_reducer.go` 提供满足 `observation.StateReducer` 的纯 Reachability/Capability 状态转换；`internal/health/reachability.go` 与 `internal/probe/capability.go` 分别管理站级和 Endpoint 热 Registry/effective read。五态只持久化 unknown/supported/unsupported/transient_error/config_error；过期由 `ExpiresAt <= now` 派生，不写第六种 stale 状态。

每个 synthetic 或真实 Attempt 在发送前从进程级 `ObservationSequencer` 取得严格递增的正整数 `ObservationOrder`。Store 以 singleton `observation_sequence.high_watermark` 原子预留 4096 个序号块；Sequencer 只分配已持久预留的值，并在剩余 512 个时后台预取下一块，进程崩溃允许留下 gap但绝不复用。real observer 遇到本地 block耗尽/预留失败时立即 no-op并增加 capacity 诊断，不能为拿序号阻塞真实请求；synthetic 则在写 socket 前返回内部不可用且不发送。状态事务除校验 revision/token 外，还要求新 order 大于目标行 `LastObservationOrder`：同 token 的旧慢失败晚于新成功完成时记为 `superseded`，不能覆盖新状态。配置失配记为 `config_stale`，两者必须分开诊断。sequence watermark 不参与 execution janitor，故清理历史不会使重启复用 order；execution 在 P0-13 固定保留窗口内可查询，被 publish/profile/calibration 引用的记录不清理。

`SemanticExpectation.BindingFacts` 有四个显式模式。resolved/real_traffic_context 必须填写 `ResolvedLayer`，并只编码实际影响选择的层：命中 Route 时只记录 Route binding；命中 Upstream 时记录“Route active binding 不存在”+Upstream；命中 tested profile 时记录 Route/Upstream active binding 都不存在+profile；命中 embedded 时记录三层 DB binding 都不存在+不可变 manifest identity。被更高层遮蔽的低优先级 binding 完全忽略，因此编辑它不会误使当前 Capability stale；高优先级 absence 则是受验证的事实，新 publish 会让旧 fallback 立即 stale。explicit_test 保存被 preview/test 的 recipe/version 与 parent row revision，不要求它已发布；explicit_profile_test 保存被测试 candidate 的 profile ID/revision/status，不把它误当当前 tested fallback；real_traffic_context 只表示能力状态的当前 binding 上下文，不声称真实客户端请求字节由该 Recipe 生成。真实 execution 另存 sanitizer 产生的 RealRequestShapeHash，UI/成本不得把 binding context 显示为“执行的模板”。Store 在同一个结果写事务中按模式和 ResolvedLayer 重读并精确比较这些 DB facts，再用 `revisioncodec` 计算 DB-current token。embedded identity/revision 来自同一进程内不可变 manifest；只有 resolved/real_traffic_context 模式下声明的高优先级 absence 仍成立时才可沿用 expectation 中的 embedded identity。Store 只验证规范 facts，不导入 built-in/probe，也不自行实现第二套 RecipeResolver。publish 只接受 BindingExplicitTest 且 execution 的 ExplicitRecipeID/VersionID 与目标完全一致；profile 升级为 tested 只接受 BindingExplicitProfileTest 且 ID/revision 完全一致。ProbeObservation 里的两份 expectation 是写回门禁原始输入；Store 将它们的诊断 revision、token 与完整 RecipeBindingFacts 展平写入 execution，并拒绝任何与 execution 同名字段不一致的记录，使重启后的 publish/current-state 复核不依赖内存对象。

写回门禁之外还必须有读侧失效：Reachability 用行内 PolicySelector 从 current Settings 重建 fingerprint，再与 NetworkRevision/token 一并比较，不同即 effective unknown；Capability 同样按行内 selector 重建当前 SemanticRevision/token，或 TTL 过期时派生 unknown。ConfigPublisher.Refresh 成功时按依赖索引把这些旧正结论从内存 Registry 移除，Scheduler、selector adapter 和管理 API 都只消费 effective state；SQLite 历史行保留原 state/token 供诊断，DTO 同时给 `current=false`/`expired`，不能把旧 supported/reachable 继续当当前事实。Secret、Endpoint、Auth、Recipe、Profile、相关 Settings/Network 修改后，在新探活完成前必须立即呈现 unknown。

`BodyShapeJSON` 只能保存字段名、JSON 类型、字段存在性和批准的枚举/布尔值；`BodyTemplate` 必须把 model/prompt/session 等动态值替换为受支持占位符，并删除 system/tools/metadata/文件/未知字符串值，任何无法安全物化的 shape 只可诊断、不可执行。数据库约束无法独自证明安全，写入前必须经 learner sanitizer，读取后再次校验再参与 Recipe 解析。

- 真实转发仍可读取最后一份 routing snapshot，保持既有保可用语义；
- `ProbeSnapshot` 返回 `config_snapshot_unavailable`，Scheduler 不发送公网请求；
- API 明确返回“配置已持久化但尚未激活”的 503 诊断，不能谎报回滚；后续读取或调度会继续刷新；
- 不在 API 层做“SQLite 提交 + 内存发布”的伪原子承诺。

这仍不是最终防线。`ExecutionRecorder` 在同一个 SQLite 写事务中：先保存 execution，再读取该目标当前全部 DB revision 与 RecipeBindingFacts，调用 `revisioncodec` 校验 current token，最后按 Reachability/Capability 各自的 revision、token 和 ObservationOrder 决定 applied、config_stale、superseded 或 not_applicable。因此即使管理写入已提交而内存刷新尚未完成，旧结果也不能污染新状态。Store 暴露的是一次一致读取，而不是由 health/probe 在事务外散读多张表：

~~~go
type SemanticRevisionReader interface {

}
~~~

Probe 开始时从同一 `ProbeSnapshot` 固定 Endpoint、Auth、Recipe、Secret revision 和 Observation Token；Upstream API Key、Probe Secret、legacy full URL 只在执行前按 expected revision 解密，若读取到的 revision 不匹配快照则不发送请求并返回 `config_snapshot_stale`。这些明文只存在于单次 Attempt 值对象，快照不保存 APIKey/Secret/legacy URL 明文，日志也不打印整个快照。

这里的迟到门禁只保护 P0 新增的 Reachability/EndpointCapability 与 execution 关联，不重置或继承既有 RouteHealth，也不改变 Route 修改 ModelNameID 的行为。Route 语义失效、旧健康清除和真实请求状态应用属于 P1；P0 不能借 Observation Token 提前改写那条选路状态机。

`ClientRequestShape` 只含安全 header template、query 名称/安全常量/Secret 占位符，以及 body 字段名、JSON 类型、合法布尔/枚举和字段存在性；不含原始业务 body/query。Learner 只接收 Real 模式正常成功；认证值、messages/system/tools/metadata 值、文件内容和未知字符串值在进入 Learner 前已经删除。候选 profile 必须保持 candidate，不能直接参与周期调度。

真实成功同时调用 Capability observer，并通过 `last_real_ok_at` 推迟 Active Route 的下次 L2；真实失败只按 P0 统一分类写观察，P1 才重构完整 RouteHealth 和重试策略。

## 5. P0 数据库版本与迁移

### 5.1 迁移运行器

当前 `Store.Open` 先执行 `schema.sql`、再执行 ad-hoc `migrate`，会在备份前改变旧库。P0 必须先修复启动顺序：

1. 用专用连接设置连接级 `foreign_keys=ON`、`busy_timeout`，只读粗检数据库是否为空或版本过高，不执行任何 DDL/PRAGMA journal mutation；
2. 空库按 0001→0002→0003 建立最终 schema 3，不需要备份；非空无版本库只做只读指纹识别，M2/M6 等已知 variant 记为 source schema 0 + SourceVariant，未知结构直接拒绝，识别阶段绝不 normalization/DDL；
3. 非空库按“每次只跨一个版本”的循环执行：0→1 normalization、1→2 expand、2→3 cutover 各是独立边界。每轮在数据库当前 journal mode 下 `BEGIN IMMEDIATE` 取得写锁，锁内重读 source version/完整指纹，消除双进程 TOCTOU；任意两个边界禁止合在一个事务或共用一份备份；
4. 每个 source→target 边界都在锁内用 `modernc.org/sqlite` driver connection 的 `NewBackup`/`Step`/`Commit` 创建包含当前 WAL 可见状态的一致快照，写 manifest 临时文件并 fsync+原子 rename；备份与 manifest 校验成功前不执行该边界 DDL；
5. 按 SourceSchema/SourceVariant 选择只读 validator：schema 0 对每个 M2/M6 variant 重验精确结构指纹、全量解密 upstream API key并验证对应 pre-P0 ReaderContract；schema 1 全量解密 upstream API key；schema 2 还必须覆盖 probe_secret、legacy_full_url 和该版本全部密文列、required/active ref、immutable version 与 binding 约束。任一项失败都回滚并拒绝迁移；
6. 在该轮同一个 SQLite 事务中执行且只执行目标版本脚本和数据搬迁；legacy normalization 的第一笔 DDL 与标 schema1 都必须发生在原始 variant backup 成功之后；
7. 执行该版本对应的 `foreign_key_check`、行数、唯一/CHECK/trigger、明文 Secret 范围扫描和全量密文解密验证；v2 允许 legacy Probe 配置列保留原值但要求所有新安全配置列合规，v3 要求 P0 管理的配置表、legacy Probe 列、migration quarantine 与新 execution/diagnostic 列扫描零命中。`sample`/`request_log` 是用户明确要求保留的原始流量证据域，P0 不伪称其明文为配置泄漏，也不纳入此零命中 gate；validator 只报告行数、权限/访问边界和“待 P5 信封加密迁移”风险，不读取或输出内容；
8. 把该轮目标 `schema_version` 作为事务最后一条 SQL 写入，然后才 `COMMIT`；不存在“先提交、后写版本”的 crash gap。COMMIT 后重新进入下一轮并重新备份；
9. 全部版本完成后、连接池开放前，在事务外设置并验证 `PRAGMA journal_mode=WAL`；migration SQL 不包含 journal_mode，连接级 pragma 仍由 DSN/连接初始化负责；
10. `Store.Open` 在任何 migration/连接池前取得数据库同目录的进程生命周期独占锁：Unix 使用 flock、Windows 使用 LockFileEx，锁 handle 持有到 Store.Close；第二实例、锁路径 symlink/reparse、无法验证的文件系统或锁丢失一律拒绝监听。该锁同时兑现 ObservationSequencer 的单副本前提，不能只依赖 HTTP 端口冲突；
11. 任一步失败都不启动 HTTP 监听，保留原库和各阶段备份供恢复；另一进程只有在前一实例退出并释放生命周期锁后才能重新打开，随后必须重读版本，已完成的单步迁移幂等跳过。只有最终 schema 3 二进制可用于 P0 生产部署，中间 commit 的 schema 2 binary 只用于开发/迁移测试。

### 5.2 Schema version 2：expand，不破坏旧 reader

`0002_p0_probe.sql` 完成以下结构：

- `upstream` 增加 `probe_mode`、`host_override`、`tls_server_name`、row `revision`、`network_revision` 与 `credential_revision`；
- `model_name`、`route` 增加 row `revision` 与 `capability_revision`；
- `setting` 增加逐 key 的 `revision`，`settings` 值语义更新时单调加 1；`run_state` 行使用自己的 revision，状态更新不改变 settings revision；
- 新建 `legacy_full_url`，按 Upstream 唯一保存加密 URL、mask/fingerprint、可空 inferred_endpoint、needs_review 和 revision；新建 `upstream_endpoint`，唯一键 `(upstream_id, endpoint)`，保存 URL/row revision 与独立 auth_profile_revision，legacy_exact 只能以 FK 引用前者；URL/query 改变增加 Endpoint revision，AuthMode/认证模板改变同时增加 Endpoint row revision 与 auth_profile_revision；
- 新建 `probe_secret`，唯一键 `name`，保存 `value_enc`、keyed fingerprint、revision；
- 新建 `recipe_version_required_secret`/`client_profile_required_secret` 保存不可变版本或 candidate 声明的规范 secret name。历史 required 行同时保存 nullable `resolved_secret_id` FK（ON DELETE SET NULL）以及不受 FK action 影响的 `bound_secret_id_snapshot`、bound revision/fingerprint/name；删除后原 ID 快照仍在，同名重建不会自动复活。再以 `endpoint_active_secret_ref`、`recipe_active_secret_ref`、`client_profile_active_secret_ref` 表达当前可执行 binding，并以 RESTRICT 阻止删除。模板/profile 写入、publish/test/disable 与 active refs 切换都在各自主体事务中完成，禁止运行时重新扫 JSON 猜依赖；
- 新建 `probe_recipe`，用 nullable `upstream_id REFERENCES upstream` 与 `route_id REFERENCES route` 加 CHECK 保证恰好一个非空；两个 partial unique index 只约束 status 非 archived 的 `(upstream_id,endpoint)` 与 `(route_id,endpoint)`，并包含 status、pinned、draft/published version、last_publish_forced、last_test_execution_id、published_at、row revision 和 active_binding_revision；后者初始化为 1，只在实际解析 binding 改变时增加。archive 原子释放 active Secret refs并使 Resolver 忽略该 binding，但保留 version/publish 指针作历史；P0 不支持 unarchive，同 scope+endpoint 可随后创建新的 draft Recipe；
- 新建不可变 `probe_recipe_version`，内容包含受限 Method；
- 新建 `client_probe_profile`，允许同站同 Endpoint 的多个 family/shape candidate/history；`(upstream_id,endpoint,client_family,shape_hash)` 唯一，`last_seen_at/seen_count` 是进入 typed Store/API 但不增加语义 Revision 的 telemetry，并用 partial unique index 限制每站每 Endpoint 至多一个 tested active fallback；
- 新建 `probe_execution`，分别保存 recipe_binding_use、recipe_id、recipe_storage、recipe_source provenance、DB version/profile/template 判别联合及 revision，并以 CHECK/FK 约束与 binding use/storage 匹配；将两份 expectation 的 target、EndpointID、全部诊断 revision、完整 RecipeBindingFacts、双 token/fingerprint、evidence hash、observation_order、Reachability/Capability 两个 ApplyDisposition、observer_incomplete/reason 展平保存。完整 Decision 的 final/success/semantic_seen/normal_end_seen/partial/candidate_disposition、estimated_input_tokens/observed_input_tokens/observed_output_tokens，以及 TLS-handshake start/done、GotConn 与后续阶段时间都必须落列，使 reducer、明细保留期内的成本对账和 Calibration 崩溃恢复只依赖 immutable execution。TriggerRealTraffic 必须使用 real_traffic_context，并以 CHECK 保证“learnable=true+RealRequestShapeHash”或“learnable=false+受限 shape_unavailable_reason”恰有一种；Recipe identity 只标 current binding context，其他 trigger 禁止该 use/shape 字段。incomplete=true 要求非空受限 reason，但 disposition 由仍可靠的 status/transport evidence 分别决定，不能用 CHECK 强制双 not_applicable；config_stale/superseded 汇总值只由 DTO 对两个 disposition 做 OR 派生，不在 DB 再存重复 bool；
- 新建 `calibration_run` 与 `calibration_candidate`，candidate 保存 disposition/finished_at；`AdvanceCalibrationAfterExecution` 与成功 commit 都以 execution 为唯一分类来源原子推进状态；
- 新建 `probe_cost_daily`，以 UTC day+trigger+Recipe source+Endpoint+Route/Upstream 规范零值组成唯一键，另保存 `piggyback_l2_saved`；新建短小的 `probe_cost_event(event_id PRIMARY KEY,day_utc,event_kind,evidence_version,cost_evidence_hash)` 作为与 daily 同寿命的去重水位，domain-separated event ID 同时覆盖 synthetic execution 与无 execution 的 L2 piggyback skip，不保存请求内容。execution 首次成功插入时在同一事务先插入 execution cost event，只有 event 新插入才对 synthetic trigger 累加请求数、成功/失败/取消、estimated input、observed output 与首语义取消；重复 ID 只有 `ProbeCostEvidenceV1` 的 format version+hash 完全相同才是幂等，不同则返回 `ErrIdempotencyConflict`。real_traffic 和客户端 count_tokens 永不进入该表。`RecordProbePiggybackSaving` 使用同一门禁幂等增加节省次数；另建 singleton `probe_cost_retention_watermark(closed_through_day_utc)`，所有 cost 写事务先检查其日期未被关闭；
- 新建 singleton `observation_sequence`，只保存单调 high_watermark；以 `BEGIN IMMEDIATE` 原子预留固定序号块，禁止依赖可被 retention 删除的 execution MAX恢复唯一性；
- 新建 `upstream_reachability` 并保存 evidence policy selector、settings fingerprint 与 last_observation_order；
- 新建 `endpoint_capability`，同样使用 upstream_id/route_id 二选一 FK 和 partial unique index，不把不可校验的 scope_type/scope_id 当外键；除 token/hash 外保存 evidence policy selector、EndpointID、upstream、endpoint、model、route、auth、recipe binding、settings、probe-secret-set、request-transform 各诊断 revision及 last_observation_order，并保存只由 current real success 单调推进的 last_real_ok_at/last_real_ok_token；
- 为全部管理列表建立与 filter+keyset 顺序匹配的复合索引：配置资源以各 filter 前缀接 `id`，RecipeVersion 以 `(recipe_id,version,id)`，Execution 以 `(sent_at_ms,id)` 及常用 endpoint/upstream/route/state/error/trigger 前缀，Capability 以 `(observed_at,scope...,endpoint)` 及 filter 前缀，Reachability 以 state/current 依赖接 upstream_id，Profile/Calibration 以 `(created_at,id)` 及 scope/state 前缀，ProbeCost 以 `(day_utc,trigger,origin,endpoint,route_id,upstream_id)` 及 filter 前缀，cost-event 清理以 `(day_utc,event_id)`；索引 SQL 与查询计划由测试锁定，不能在列表中使用 offset 或全表读后内存过滤。

`probe_recipe_version` 的 UPDATE 和 DELETE 由 SQLite trigger 拒绝；archived 是 recipe binding 的状态，不回写不可变版本。`probe_execution` 只存哈希、阶段时间、状态码、分类、脱敏详情、字节与 Token 估算，不存完整请求/响应正文。

version 2 只做加法表/列、兼容 backfill 和 revision 初始化：不得清空 probe_headers/probe_prompt，不得改写 full_url BaseURL/full_url_mode，不得删除 legacy 索引/列。P0-02 二进制仍使用旧 proxy/Prober，必须可在 version 2 库上保持原行为；P0-03 至 P0-16 的新代码只读新结构或显式兼容结构，但生产部署门禁禁止发布任一中间提交。管理员写旧字段的显式兼容 adapter 保留到 P0-14 API 全部切换；新增 revision-aware 方法必须用不同 Go 名称，旧签名 adapter 仍可编译且每次旧写入也正确双写并增加 revision，P0-17 才在全调用扫描后删除 adapter。旧 CreateUpstream adapter 必须在一个事务中同时创建五个 canonical Endpoint：messages/count_tokens、responses/chat_completions、models，AuthMode 按旧显式 auth_style 机械映射，auto 只映射 migration-only real兼容；任一 Endpoint 失败则 parent 一并回滚，防止中间提交产生 Resolver 无法使用的新站。

P0 不改写 legacy UNIQUE 约束，也不引入配置软删除。Upstream、ModelName、Route、Endpoint 的 DELETE 必须带 expected_revision。删除服务在一个事务中先区分 owned-current 子配置与不可丢历史：若存在 execution、immutable version（包括 migration 物化的 legacy_compat）、Capability 历史或外部 Route 等历史/引用则返回 409，提示 disable/archive；只有完全没有 immutable/history 的主体，才可先按固定子→父拓扑删除 migration 自动生成的空 binding、active refs、Endpoint 与 legacy URL 后硬删。Recipe 只允许 archived，不删除不可变 version；因此已有 legacy_compat version 的迁移实体不能以“从未人工发布”为由绕过历史门禁。Probe Secret 只在没有 active ref 时物理删除；历史 required-secret 的 `resolved_secret_id` 置空，同时保留 bound ID snapshot/revision/fingerprint/name，故同名 Secret 重建后旧 RecipeVersion 仍不能直接发布，必须生成并测试新 version。这避免重建 legacy 父表和 DELETE trigger/CASCADE 冲突。

### 5.3 Schema version 3：P0-17 原子 cutover

`0003_p0_cutover.sql` 只能在 P0-17 所有新 reader/writer、Resolver、Executor、Scheduler、API 和 UI 均通过门禁后加入。它在独立 schema2→3 backup 之后执行最终一致性检查，确认每个活动 Route/Upstream 都能从新 Endpoint/Recipe/Auth（含只读 legacy compatibility 标记）解析；同一事务先清理 legacy Probe 明文、把 full_url BaseURL 改为安全 origin或不可路由占位、清 `full_url_mode`、停止旧 Cost 写入并写 cutover marker，再完成全部校验，最后一条 SQL 才写 `schema_version=3`，随后 COMMIT。任何活动配置无法无损落到新结构都回滚，服务不监听。最终二进制支持 v1→v2→v3 连续升级和 v2→v3；中间 P0 commit 不允许用于生产部署。v3 可以保留只读 `legacy_exact` 与 `legacy_auto_real_only` 兼容记录以维持真实流量，但不能由 API 新建/修改，synthetic 对未校准项 fail closed。这里仅做安全存储 cutover 并逐字节保持旧真实语义，不确认、拆分或改变 legacy binding；用户审核转换与移除流程仍全部属于 P1。

### 5.4 Legacy 数据规则

- 旧 `probe_headers` 中的已知认证头或与该 Upstream API Key 完全相同的值转换为 `{{UPSTREAM_API_KEY}}`；
- 不把 Upstream header Recipe 与 ModelName body Recipe拆成两个互相遮蔽的 binding。v2 针对每个现有 Route 及其实际 Endpoint 物化一份完整只读 `legacy_compat` version：严格复现旧默认头、该 Upstream 的 probe_headers、该 ModelName 的 probe_prompt/probe_max_tokens、旧 model 映射和 query；Anthropic Route 同时覆盖 messages 与 count_tokens 的既有真实兼容形状。多个 Route/ModelName 各自独立，正常 UA、beta 与协议头包含在同一组合 version；models 的 L1 策略单独作为 Upstream-scope recipe；
- 认证类名称中含无法识别的高熵值、或值命中 Secret 扫描但无法安全转换时，迁为 `legacy_quarantined`，不可执行；
- 旧 `probe_prompt`、`probe_max_tokens` 进入对应协议的 legacy recipe version；
- `full_url_mode=false` 在 v2 创建五个 canonical Endpoint；旧 `l1_path` 非空时机械地迁为 models Endpoint 的同源 URL override，空时保留“HEAD base 只判 Reachability”的 L1 策略，不能静默改成 `/models`；v2 仍保留 legacy 列原字节供旧 reader；
- legacy HEAD-base 以及无法证明返回模型列表的自定义 l1_path 永远只产生 Reachability evidence，Capability disposition=not_applicable；只有 canonical/明确 models Recipe 且解析到 ModelListRecognized 才更新 models Capability；
- `full_url_mode=true` 在 v2 一律把旧完整 URL加密复制到 `legacy_full_url` 并标 NeedsReview，但不改 `upstream.base_url/full_url_mode`。按现有 Route 的真实兼容协议集建立引用同一记录的 legacy_exact Endpoint：Anthropic 至少 messages+count_tokens，OpenAI 按实际 responses/chat，models 仍按旧 L1 规则；单协议写 InferredEndpoint，多协议标 `LegacyCompatRealOnly`，零 Route 只保留记录。v3 才把 `upstream.base_url` 改为不含 userinfo/fragment/query 的安全 origin并清 full_url_mode；无法解析安全 origin时使用不可路由占位、停用 Upstream并保留加密记录。真实转发对全部已用协议（含 count_tokens）继续逐字节使用 exact URL；多协议 synthetic 返回 `legacy_full_url_needs_review`、不发网络。P1 才审核并拆成 canonical 多 Endpoint；
- 旧 `auth_style=bearer/x-api-key` 在 v2 机械映射为单一 AuthMode；`auto` 映射为 API 不可创建的 `legacy_auto_real_only`，真实请求暂时保持旧双头兼容，所有 synthetic 候选必须通过可见 Calibration 后才变为单头；不得在 migration 中猜测；
- 旧全局 `probe_enabled=false` 把全部现有 Upstream 映射为 Lazy，`true` 映射为 Active；新建 Upstream 使用当时新默认。升级、重启和 pause/resume 都不得让原先关闭探活的站突然产生 synthetic 请求；

所有 Page 方法共用 `internal/store/page.go` 的版本化 cursor codec、limit 校验和 filter fingerprint；它们只选择 DTO 允许的列，Secret 列表绝不读取/返回密文。所有带 `expectedRevision` 的写入使用 `UPDATE ... WHERE revision=?`，零行更新返回 `store.ErrRevisionConflict`，管理 API 映射为 409。P0-02 新增的 revision-aware Upstream/ModelName/Route/Settings 方法使用不同名称，旧签名和非分页 List adapter 保持源码兼容、双写新表并递增 revision；P0-14 迁完 handler，P0-17 扫描后才删除旧 adapter，Go 中不伪造重载。

依赖「当前时刻」的 filter（目前只有 `CapabilityFilter.Expired`）必须把判定时刻在首页固定下来并随 cursor 传递，Store 侧用 `encodePageCursorAt`/`decodePageCursorAt`。理由是 keyset 分页的后续页只读游标之后的行：若每页重新取当前时间，翻页途中恰好过期的行会在它本该出现的那一页之前被排除，于是永远读不到 —— 表现为静默漏项且不报错，而 cursor 指纹不含时间也不会把它判成失效。该时刻不参与 filter 指纹（它是同一次翻页的延续，不是 filter 变了）。

`ListRoutesPage` 按 `id` 而非 `ListRoutes` 的 `(model_name_id, priority, id)` 排序：`priority` 可重复，且 schema 2 只有 `idx_route_model_name(model_name_id)` 单列索引，按 priority 做 keyset 会退化成 `USE TEMP B-TREE FOR ORDER BY`（已实测）。选路顺序仍由 `ListRoutes` 负责。**P0-14 迁移管理端 Route 列表时必须处理这个差异**：直接换成分页版本会把 UI 上的 Route 顺序从「按优先级」变成「按创建顺序」，对一个以优先级路由为核心的产品，用户会据此误判当前选路顺序。两条可行路径 —— DTO 带上 priority 由前端排序，或在 schema 3 增加 `(model_name_id, priority, id)` 索引后改用三段 cursor（实测该索引下过滤与全量两种组合都走 covering index、无 temp B-tree）。不要在 P0-02 已合并的 `0002_p0_probe.sql` 上追加索引：`migrateToDevelopmentSchema` 在 `version == 2` 时直接返回，已升级的库不会补建。

`CommitProbeObservation` 是 P0-10 起 synthetic 与真实被动观察的唯一生产入口：在一个事务中插入 execution，并独立应用两个证据。只要收到合法 HTTP 响应，就比较 ReachabilityExpectation 的 ReachabilityRevision/token、DB-current 对应值与 ObservationOrder；若 Decision 还有 Endpoint Capability 结论，再比较完整 DB-current SemanticExpectation/token/order。通过门禁后才调用注入的纯 StateReducer，Store 只持久化 reducer 返回的新行。两者可以分别 applied、config_stale、superseded 或 not_applicable；事务把 disposition 写回 execution，并只对 ApplyCurrent 返回深拷贝的 committed row（含 token+LastObservationOrder）。ResultRecorder 以同一 token 且更大 order 的 CAS 刷新内存 Registry，回调/commit 返回顺序反转也不能让旧行覆盖新行。P0-09 的临时 `ExecutionOnlyRecorder` 只调用 InsertProbeExecution，不应用状态；P0-10 main 必须替换为 ResultRecorder。禁止保留只返 bool 的 `ApplyPassiveCapability`，也禁止在生产路径拼接 `InsertProbeExecution` + `SaveCapability` 形成伪原子操作。publish/force publish 在同一事务重验 execution 非 config_stale/superseded、RecipeVersion/target 完全一致且 token 仍 current；Endpoint/Auth/Route/Model/Secret/Settings 任一在 test 后改变都返回 409 要求重测。

`BindingExplicitTest` 与 `BindingExplicitProfileTest` 只证明 draft/candidate 在测试时的 freshness，不代表当前 Resolver binding：它们的 Reachability evidence 仍可按独立网络 expectation应用，但 Capability disposition 固定为 not_applicable，绝不改 active Capability/Registry/LastObservationOrder。publish/promote validator 不要求这类 execution 的 Capability=ApplyCurrent；它直接重验 explicit expectation/facts、Decision 成败和 DB-current target/version/profile。只有 `BindingResolved` 与 `BindingRealTrafficContext` 能更新 live Capability。publish/promote 在原子切换 binding 后立即让旧 active Capability effective unknown并安排一次新的 resolved 验证；显式测试本身无论成功或失败都不能污染仍在服务的旧 published/tested binding。

execution ID 同时是 observation 幂等键。Insert/Commit 遇到已存在 ID 时，先比较版本化 evidence hash（不含 disposition）；完全相同则返回已保存结果且不再次运行 reducer/增加连续计数，不同则返回 `ErrIdempotencyConflict`。这样 COMMIT 已成功但调用方只看到连接错误时，持久层重放不会重复应用；Executor 本身仍不自动重发上游请求。

## 6. 通用测试循环

每个任务严格使用同一个循环：

1. 先添加能证明目标行为且当前失败的测试；
2. 运行该测试并确认失败原因正是缺失行为，不是测试编译错误；
3. 写最小实现使目标测试通过；
4. 运行所属 package 全部测试；
5. 运行 `go test ./...` 与 `go vet ./...`；
6. 并发任务在 Linux CI 运行对应 `go test -race -count=1`；
7. 检查 `git diff --check`、Secret 扫描和暂存文件范围；
8. 形成一个可单独 revert 的提交。

P0 不通过删除旧测试来取得绿灯。若旧测试锁定了被规范推翻的语义，先把该测试改成新规范的反例并确认旧实现失败，再替换实现。

`AttemptRequestView` 只在 `PrepareAttempt` 同步调用期间有效。proxy 在最终出站 Route/Endpoint/header/query/body 已确定但尚未写 socket时，只传 `AttemptTarget` 和该只读视图；Config facts 全部从这次真实 Attempt 已固定的 routing/outbound bundle 复制，proxy 不构造 token、不解析 Recipe，也不实现第二套 sanitizer。routing snapshot 与 ProbeSnapshot 由一次 ConfigPublisher refresh 以同一 Generation 原子发布。probe factory 同步取得 ProbeSnapshot，先要求 generation 与全部实际 revision/fingerprint/ResolvedURLHash 精确匹配，再通过同一个 RecipeResolver 的 snapshot adapter 得到该代 binding context/BindingFacts，调用 Snapshot expectation builder、分配 ObservationOrder；这些配置身份步骤失败才返回 no-op Observer、永远 KeepAttempt 的 RetryDecider和 nil Trace，绝不把旧配置字节贴上新 token。

只要 instrumentation 含有效 expectation，factory 就创建一个 Attempt 专属 `outbound.AttemptTrace`，把同一指针同时交给 Observer 私有状态和 `AttemptInstrumentation.Trace`。proxy 只负责在实际发送的 request context 上调用 `outbound.WithAttemptTrace` 后执行该次 RoundTrip，不读取或解释 trace；Observer 在 `Finish` 后读取同一指针的深拷贝 Snapshot，并与 SentAt/DoneAt 一起写入真实 `ProbeExecution`。这样新连接、复用连接、TLS 中途失败和 GotConn 前 connect error 都使用第 4.4 节同一计时规则；no-op instrumentation 的 Trace 必须为 nil，不能制造“已观测但全零”的伪证据。

请求学习是随后独立的可选步骤：sanitizer 在有界预算内尝试把 view 降为 `model.ClientRequestShape`，返回 `learnable=true+safe shape` 或 `learnable=false+受限 reason`，两者都必须在返回前丢弃原始 Header/RawQuery/Body 引用。ShapeHash/RealRequestShapeHash 只对排序规范化后的安全 shape做带域、带格式版本的 SHA-256，不含被删除的业务值或 Secret；相同安全形状跨重启稳定。body truncated、未知业务字符串、无法安全替换或 sanitizer failure 只禁止 Learner/shape hash，不影响已构造 expectation 的 status/event健康 observer与 RetryDecider；它们照常解析响应并把 execution 标为 shape unavailable。只有 snapshot/facts/order 等健康身份准备失败才全 no-op。整个 PrepareAttempt 不阻断、延迟或改变真实请求，依赖仍是 proxy→health interface、probe→health implementation，不出现 proxy↔probe cycle或 proxy 复制 RecipeResolver。

真实 retry 在客户端尚未 commit 时仍需要同步判断受限 Peek 前缀。proxy 只调用中立 RetryDecider；probe 实现复用同一 Decoder/Classifier，在固定 CPU/字节预算内只对结构化、已完整识别且现有重试规则允许的错误返回 TryNextRoute。普通 2xx semantic/未决前缀、解析失败、预算超限或 decider panic 一律 KeepAttempt，避免因旁路失败制造重复模型调用。该 decider 不等待异步 observer，也不改变 P0 的重试次数/幂等策略；P1 才重构完整真实重试。P0-17 删除旧 classifyPayload/errorpayload 前，必须证明 retry.go 已只依赖此接口。

真实响应旁路由进程级 `TrafficObserverManager` 统一限流，而不是为无界并发请求各自无条件起 goroutine：固定 32 个 full-observer lease、16 MiB 全局在途复制字节预算和 1024 项有界 persistence queue。抢不到 full lease 时仍创建不复制正文的 status/transport-only instrumentation并标 `observer_capacity`，绝不等待；已完成 observation 以非阻塞方式进入单独持久化 worker 队列，队列满只增加 dropped counter并丢弃这次旁路写回，不阻塞真实响应或占用 SQLite 主链。persistence worker 使用 Manager 的服务生命周期 context，而不是客户端 request context；Finish 后客户端 context 取消不会丢掉已入队证据，shutdown 才按有界 drain规则停止。`ProbeRuntimeStats` 暴露当前 lease/bytes/queue 和 capacity/persistence/candidate drop 累计值，不含请求数据；进程重启计数归零并明确标为 since-start 诊断。

取得 full lease 的 Attempt 使用固定容量、固定累计字节上限的非阻塞 copy queue和单 worker：TryHeaders 深拷贝受限 header，TryChunk 先从全局字节预算预留、在调用内复制获准长度后按顺序入队，绝不持有 proxy buffer；worker 消费或终止时归还预算。任一复制预算、队列、解压输出或 CPU deadline 超限立即原子标 `observer_incomplete`、停止接收后续正文观察但仍原样转发。Finish 只记录终态并关闭队列，不等待 worker；worker 依序 drain 后提交一次结果并释放 lease。所有回调 panic 被隔离，关闭/并发 Finish 幂等，进程 shutdown 在固定期限内停止接收、drain 队列后强制丢弃剩余旁路。P0 每 Attempt 固定队列 32 项、累计压缩输入 256 KiB、解压输出 1 MiB 和版本化 CPU deadline；不新增半套可配置项，P4 若开放配置再同步扩展 Settings、fingerprint、API 与 UI。incomplete execution 只保存枚举原因和已可靠取得的结构化证据，不保存原始错误或部分正文：已收到任意合法 HTTP header 仍可应用 Reachability；404/405、401/403、429/5xx 等纯 status 结论仍按 Classifier 作用域应用；2xx 因 capacity/队列/解压/正文不完整而缺少 semantic 时 Capability=not_applicable，不能覆盖既有结论；header 前 transport failure 仍可按网络错误更新 Reachability；只有 PrepareAttempt 本身失败、没有 expectation/order 时两者都不应用。

每个 Attempt 正常情况下仍独立产生 observation；资源饱和是显式可见的降级，不通过采样悄悄改变成功/失败阈值。为使 P0 自动生成的高频运行数据保持有界，固定保留策略由后台 janitor 小批执行：real_traffic execution 最多保留 7 天且全局最多 50,000 行；scheduled/recovery 等未被当前 binding 引用的自动 synthetic 最多保留 90 天且全局最多 200,000 行；独立 manual execution 最多保留 90 天且全局最多 50,000 行；calibration 明细默认保留 90 天。前三类分别由 `ProbeExecutionRetention` 的 cutoff/cap 表达，不能把 manual 暗含进 automatic。当前 Recipe publish/test、ClientProfile tested、正在运行的 Calibration、当前选中 candidate 或其他 active FK 引用的 execution 受保护。terminal 的 failed/canceled/interrupted CalibrationRun 以及已被后续成功 run 取代、且不再被当前 Recipe/Profile/Endpoint 引用的 succeeded run，在 90 天后由同一事务按 candidate→run→unreferenced execution 拓扑裁剪；不可变 RecipeVersion 不删。这样 Calibration FK 只保护仍在保留窗或仍具当前语义的证据，不形成永久增长豁免。删除 execution 明细前，其 synthetic 成本已经由 domain-separated cost event 与 daily rollup 恰好一次固化；piggyback saving 使用另一 event kind。daily rollup 与全部 cost event 都固定保留 730 天。`PruneProbeCostHistory` 先在独立短事务把 singleton `closed_through_day_utc` 单调推进到已超过 730 个完整 UTC 日的 cutoff；从该提交起，execution rollup 与 piggyback 写入遇到 `day_utc <= watermark` 都作为已关闭窗口幂等 no-op，绝不重建 daily/event，`ListProbeCostDaily` 也立即排除已关闭日期。随后每个事务合计最多删除 500 个 watermark 内的 daily 或 event data row，顺序、崩溃和重启不影响幂等；singleton 水位不回退、不删除。janitor 不改仍在保留窗的 rollup，也不删当前 Reachability/Capability。execution、calibration 与 cost 清理各批最多 500 个 data row、低优先级调度且失败只告警，不能阻塞 proxy或探活写入。管理员显式创建的 immutable RecipeVersion 不承诺自动有界；P2 的正式 audit_event 负责需永久保留的管理员审计，P4 才把明细保留策略开放为设置。

1. 所有写入拒绝未知字段和尾随第二个 JSON 值；
2. `body_text`/`body_base64` 互斥；header 使用有序数组和 values 数组；
3. Secret 写入接受明文，读取永不返回明文或密文，只返 mask/fingerprint/revision/is_set；
4. preview 绝不解析 API Key/Probe Secret 明文：只编译模板并把所有 Secret 占位符替换为固定、与真实长度和值无关的 redacted marker，返回脱敏 URL/header、`redacted_template_body_bytes`、带域和格式版本的 `redacted_template_hash`、占位符清单与区间成本；不得把这些字段命名或展示为真实出站 body hash/bytes。低熵 Secret、多次 preview 和不同权限响应均不能形成长度/hash oracle；实际 execution 只存 keyed URL/request evidence hash。Route-scope 从 binding 推导 RouteID并拒绝不一致输入，Upstream-scope 的模型端点必须给 RouteID且验证属于该站，才能解析 UPSTREAM_MODEL/脱敏 URL/成本；

6. 所有更新要求 `expected_revision`，冲突返回 409；
7. 8. config_error 返回 400/409，内部错误不泄露上游 body 或 Secret；
9. paused 下允许管理 CRUD/preview，禁止 scheduled/manual/calibration 执行；`/admin/api/state` 只调用 RunStateAdmin，要求 expected_revision。正常 pause 响应前 synthetic 已 drain；提交后 drain 超时/error/panic 返回 503 `code=pause_drain_pending,persisted=true,state=paused,new_revision` 且后台继续，绝不返回假回滚；resume 使用渐进调度；
10. Lazy manual calibration 明确标 manual，不改变 probe_mode；
11. API 层只编排 service，不重复实现 Resolver、Template 或 Classifier；

13. Refresh 失败时返回 503，响应保留既有 `error` 字段并增加 `code=config_activation_pending`、`persisted=true`、资源 ID 与新 revision；重放相同 expected_revision 得到 409，客户端应先 GET 新 revision，不能误以为数据库已回滚；
14. 配置 pending 期间 Scheduler 不发送 Probe；旧 routing snapshot 仍可服务真实流量，迟到 execution 由 DB-current token 门禁；
15. Client Profile 读取只返回 sanitizer 后 shape；test 用 BindingExplicitProfileTest 固定 candidate ID/revision/status并恰好发送一次，只有该 expectation 仍 current 的成功 execution 能原子转为唯一 tested binding，失败仍为 candidate；启用/禁用都触发 Refresh，pending 期间不发送 synthetic，迟到 token 不应用；
16. Recipe version 列表与单项 GET 支持页面刷新后恢复全部 draft/published 状态，不依赖前端内存；
17. Settings API 只接受新字段 DTO，拒绝 legacy/unknown key；RunState 使用独立 revision，状态写不改变 Settings revision；
18. P0 不做 SQL down migration。代码未合并时按提交 revert；schema3→2 恢复必须使用 manifest 指定的 P0 v2-compatible reader，退整个 P0 到 pre-P0 binary 只能恢复最初 schema1/legacy backup并明确放弃此后新配置。

恢复程序使用数据库同目录、0600 的版本化 `restore-intent.json` 状态机消除文件替换 crash window：停止监听/后台写入并证明全部 SQLite handle 已关闭；按 SourceSchema validator 校验 manifest、backup SHA-256、cipher ID、该 schema 全部密文列/ref invariant 与 PairedBuildID；将 backup 复制到同目录临时文件、权限+fsync后只读执行 integrity_check/全量解密；原子写 intent=`prepared` 并 fsync目录；把当前 db/-wal/-shm 成组移动到唯一隔离目录后更新 intent=`isolated` 并 fsync；原子 rename 已验证临时库到正式路径并更新 intent=`installed`；确认正式路径没有旧 sidecar、重新校验并 fsync目录后写 `complete`，最后才删除 intent。任何阶段都不删除隔离现场。

`Store.Open` 在判断“空库”或执行 migration 之前必须先检测 restore intent；prepared/isolated/installed 任一未完成状态都按记录的绝对目标、hash和 phase安全续做或 fail closed，绝不能把中间缺失的正式 db 当空库创建 schema3。intent 损坏、路径越界、symlink/reparse、文件 hash不符或配对 reader不符都保持停机。Windows 同样依赖该状态机，在任何 move/rename 前证明 handle关闭。测试在 intent写入、隔离每个文件、rename、sidecar清理、目录fsync和complete各边界注入 crash，重启后只能得到完整旧组或完整恢复组，不能启动空库或混用 WAL。

恢复不是一段只能被启动器“续做”却无法发起的伪流程。最终二进制必须提供离线入口（命令在任何 `Store.Open`/listener/worker 前分派）：

~~~text
relay-gate db check-backup --database <absolute-db> --manifest <absolute-manifest>
relay-gate db restore      --database <absolute-db> --manifest <absolute-manifest> --execute --accept-data-replacement --accept-reader-contract <exact-value-from-check>
~~~

`check-backup` 只读完成 manifest/hash/cipher/source-schema validator、路径与 paired-reader contract 检查，并输出必须逐字确认的 ReaderContract/PairedBuildID；`restore` 还必须取得与 Store.Open 相同的生命周期锁、确认没有服务进程/SQLite handle、要求 `--accept-reader-contract` 与 manifest 完全相等、创建已验证临时库和 `prepared` intent，再调用同一可重入状态机直至 complete，最后只输出隔离目录、恢复 schema 与所需配对 binary，不自动启动服务、不删除现场。缺 `--execute`、`--accept-data-replacement` 或精确 reader contract，manifest/backup realpath 不在数据库同目录的受控 `backups/` 子树，目标为 symlink/reparse，或任一校验失败时零文件替换。README 给出“暂停容器→备份当前目录→check→确认配对 image/binary 可用→restore→按输出启动配对 binary→健康检查”的完整命令和 schema3→2、schema1 两种后果；恢复测试覆盖 dry-run、授权缺失、错误配对和每个 crash point。

# 压缩请求显式重编码

补齐已批准需求 §6.7；默认严格透传行为保持。选择现有不可变声明式规则 `request_reencode` 作为显式授权，作用域仍为发布的 Route + Endpoint，不新增全局开关、第二份配置或数据库迁移。规则无参数，表示对入站 gzip/br 在有界解码后按同一编码重写；UI 明确说明该绑定退出严格字节透传。Shadow 不授权真实改写。

解码副本沿用唯一 model 校验。选择候选后通过唯一 Resolver 确定 Endpoint，再检查该请求开始时捕获的发布版本；未授权的模型映射/正文转换作为本地跳过，不消耗网络 Attempt。严格模式候选全部不适用时返回既有固定 415。半开恢复也在实际出网前完成检查，未出网跳过不消耗唯一真实半开试探。

复用同一请求准备函数处理模型流量和 count_tokens：从入站原文重新建立各 Attempt 的 body/认证；需要重编码时，以有界解码副本进行 model 映射、声明式规则及认证保护，再按原 gzip/br 编码。保护层固定实际 Content-Encoding/Content-Length，不能由规则伪造。每次重试均从入站原文开始，fail_open 保持该候选已映射的请求，fail_closed 本地跳过。原始压缩体和解码体受现有限额约束；需要重编码的工作副本及编码产物另受 8 MiB 上限，失败不发送。未需要正文改动的严格绑定仍逐字节发送原压缩体。

回归以真实本地 HTTP 上游收到的编码字节、解码后 model/正文、认证和请求数为准：gzip/br 显式授权与默认拒绝；影子/其他 Endpoint 不授权；头转换不改变压缩字节；fail_open/fail_closed；压缩炸弹/产物上限；多 Route 重试不叠加映射或泄漏凭据；中途 publish/rollback 不修改现请求授权。count_tokens 共用准备规则但保留自身预算、无 RouteHealth 写回及本地估算。

不把 HTTP 头大小写/顺序视为可保持的应用层字节合同，不改变响应压缩路径。实现后复核是否引入多余抽象，保持请求准备函数单一职责。

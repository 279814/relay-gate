# Transform 管理收口设计

依据 docs/01 §15、§17 与 docs/04 的原合同继续实现，不改变原生协议、显式绑定和请求开始时固定版本的边界。

先关闭已复现的事务一致性问题：UpdateDraft 的持久化失败必须还原内存草稿；发布/Shadow 到已被其他 Set 占用的绑定时，必须在追加不可变历史前拒绝，失败操作不能被下一次成功保存带入数据库。复用现有 Registry 锁、SQLite snapshot 事务和局部撤销，不引入通用事务平台或第二份配置缓存。

管理收口随后采用显式 expected_revision：Set（草稿及生命周期）与 Binding 分别保留持久单调版本，首次绑定要求显式版本 0；发布同时检查操作者看到的 Set 和 Binding，不能由服务器代取新版本。发布历史保持不可变，回滚只改指针；禁用阻止新请求采用，归档禁止新写入/绑定并保留历史及引用。在途请求继续使用已经捕获的规则，真实语义变化在同一 Store 事务失效健康证据。

列表复用类型化游标与同事务 count/page，默认50、最大200；页面冲突保留草稿，显式重载后再操作。原预算变更继续明确确认提高，正式审计复用 audit_event。迁移编号在 Canary14、样本视图15之后协调为16；不改历史12/13 DDL或reader合同。

验证先红后绿：持久化拒绝/绑定占用、并发CAS、重启后版本与生命周期、错误后无孤儿历史、不可变回滚、请求中发布/禁用、纯文本分页与退出登录旧响应隔离。所有源码和完整组合检查通过后再合入；公网、多日及真实上游验收保持单独证据。

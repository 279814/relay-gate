# 旧版本新建库的规范化修复

2026-10-23，ECS 部署数据的只读快照在隔离、断网、无端口发布的候选容器中启动失败。原部署身份与健康不变，验证前后原数据库和 WAL 哈希一致；候选容器已清理，未发送真实模型或邮件请求。

副本的原始结构指纹是已支持的 `legacyM6CurrentFreshFingerprint`：`65687b7c654be8f076091ebb211f5fb78f264e13795176d696c2b1e96f003993`。失败发生在 0→1 规范化后的检查，而非旧库首次识别：版本表沿用了升级路径的 DDL 拼写，得到 `c4e14689affff21aa41de1bb3f8ca8710b775c86dcbf2d385d43b53dbaed03fe`，与该新建库路径的既有规范指纹不符。使用仓库已有 `legacy-v1.sql`，新建库的 pre-index/current 两种状态均可复现同一失败。

修复只针对这两个已识别的来源指纹，创建与冻结 `0001_legacy.sql` 完全一致的版本表 DDL，使规范化进入既有 `schemaV1FreshFingerprint`。其余旧升级路径保持原 DDL。没有新增结构白名单，没有修改迁移文件或已有指纹，也不进行任意 SQL 空白归一化。

完整迁移回归扩展为六种来源状态，使用公开历史 SQL 与合成加密凭据，验证最终结构、密文保留、到当前 schema 每个边界唯一且连续的备份、原始来源指纹以及新建库路径的 schema 1 规范指纹。修复前两个新建库案例均失败，修复后六种来源均通过。后续仍须完成修复提交的全库/CI、ECS 新副本复验和最终版本验收；此修复不代表全部故障注入、真实公网或多日验收已完成。
